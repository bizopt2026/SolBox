# 저장과 동시성 규칙 (solbox/docs/rules/저장과-동시성.md)

다루는 것: 고침 표시·폼 표·쓰기 잠금·한 트랜잭션·`get_db`. 읽을 때: 폼·POST·저장 로직을 고칠 때.

솔박스 `CLAUDE.md` 에서 옮긴 영역별 규칙이다 (2026-11-25). 묶음(베타) 순서와 글은 그대로 두었다. 뒤 묶음이 앞 묶음의 규칙을 바꾼 경우가 많으니 **아래쪽(뒤 묶음)이 정본**이다. 글 속의 "위/아래 베타 X" 는 다른 영역 파일에 있을 수 있다: 어느 묶음이 어느 파일에 있는지는 `docs/rules/README.md`.

## 베타 C 묶음이 바꾼 규칙
- 폼 표(`guards.Once`): 같은 표라도 폼 내용 해시(`form_tokens.body_hash`, `_tok` 뺀 칸·올린 파일은 이름+크기만, `guards.form_digest`)가 다르면 새 제출이다(끝난 줄을 새 제출이 이어받는다). 요청 세션이 커밋한 뒤에는 예외가 나도 표를 풀지 않고 목록 주소로 끝낸다(`Once.keep`, 중복 방지). 저장 상태를 스스로 되돌리는 라우터(올리기 저장)만 `once.sticky = False`.
- `guards.check_rev` 가 통과하면 세션에 저장 직전 검사를 걸고, 첫 쓰기 flush 직전에 쓰기 잠금을 잡은 뒤 줄을 다시 읽어 표시를 견준다. 그 사이 바뀌었으면 `StaleWrite`(409). 모든 고치기 라우터가 `check_rev` 를 쓰므로 따로 더할 것이 없다 (슬라이드 저장은 `fresh=` 로 장 표시를 다시 계산하고 `_lock_proposal` 이 먼저 잠근다).

## 베타 E 묶음이 바꾼 규칙
- 쓰기 잠금: 잠금 대기 초과(`OperationalError`)는 충돌이 아니라 `guards.WriteBusy`(503, "잠시 후 다시 시도")이고, 읽은 뒤 다른 쓰기가 커밋된 경우(`SQLITE_BUSY_SNAPSHOT`)와 줄 표시가 다를 때만 `StaleWrite`(409). 두 오류 화면은 "저장하지 않았습니다" + 뒤로 가기 버튼(`data-history-back`, 브라우저가 쓰던 폼을 되살린다; 단추는 `hidden` 으로 그리고 JS 가 보이게 한다, JS 가 없으면 `<noscript>` 안내). 번호 표시(`idmarks`)의 잠금 단계도 같다 (새 기록이라 `StaleWrite` 는 없고 항상 `WriteBusy`).

## 베타 F 묶음이 바꾼 규칙
- 쓰기 잠금 대기 초과는 어디서든 503: SQLite "잠김"(`guards.is_busy_error`: BUSY·LOCKED 와 하위 코드) `OperationalError` 는 `main._operational_error_handler` 가 `WriteBusy` 와 같은 "잠시 후 다시 시도" 화면으로 보낸다 (그 밖의 `OperationalError` 는 500). 만들기의 폼 표 차지(`Once.claim`)·결과 적기·지우기도 잠금에 막힐 수 있어, 못 풀었으면(`release`) 표를 기억해 뒀다가 같은 표로 다시 오면 이어받고(`_ABANDONED`: 집합에서 빼는 것이 관문이라 한 제출만 이어받는다, 베타 G), 결과 적기·`keep` 이 잠겨 실패해도 응답은 보낸다.

## 베타 G 묶음이 바꾼 규칙
- 쓰기는 한 트랜잭션: 제안 대화 메시지는 `start_job(rows=[…])` 로 AI 작업과, 올리기 "다시 정리"의 고친 메모는 `start_analysis(note=…)` 로 정리 작업과 함께 커밋한다 (잠금에 막혀 503 이어도 메시지·메모만 남지 않는다). 새 POST 가 "저장 + 작업 넣기" 를 하면 둘을 같은 커밋에 넣는다 (제안 건 만들기도 `start_job` 이 새 제안 건을 작업과 한 커밋에 넣는다. AI 꺼짐이면 제안 건만 저장한다). 기록을 두 번 이상 커밋하는 POST 는 아래 "베타 H" 의 네 가지 예외와 "베타 I" 의 다섯째 예외뿐이다 (시험이 아니라 POST 라우터와 그 라이브러리 호출을 훑어 본 결과).
- 폼 표 이어받기(`guards._take_abandoned`): 잠금 때문에 못 푼 표의 기억(`_ABANDONED`)에서 빼는 데 성공한 제출 하나만 이어받는다. DB 열이 아닌 프로세스 안 기억이다(풀지 못한 순간 DB 가 잠겨 있어 열을 적을 수 없다). 다른 프로세스에는 보이지 않는다. 표를 지울 때(`purge_tokens`) 남은 기억도 치운다.

## 베타 H 묶음이 바꾼 규칙
- 쓰기는 한 트랜잭션(보충): 제안 건 만들기는 제안 건·방향 작업을 `start_job` 한 번에 커밋한다(잠금에 막히면 제안 건도 남지 않고 같은 폼 표로 다시 내면 하나만 생긴다). 기록을 둘 이상 커밋하는 POST 의 예외 넷: ① 솔루션 자료 여러 개 올리기(`files.upload_files`, 파일마다 커밋: 저장된 파일이 하나도 없는 채로 막히면 503, 앞에 저장된 파일이 있으면 503 이 아니라 "저장하지 못한 파일" 알림. 건너뛴 중복·큰 파일은 저장이 아니다: 베타 I), ② 올리기 묶음 만들기(묶음 저장 뒤 작업 폴더 준비·정리 시작은 따로 커밋하고 실패해도 묶음은 "올림" 상태로 남는다), ③ 올리기 묶음 저장(`intake.apply`: "저장 중" 선점을 먼저 커밋하고, 기록은 한 트랜잭션으로 저장하며 실패하면 선점만 푼다), ④ 폼 표의 차지(`Once.claim` 의 표 줄 커밋)·결과 적기(`Once.done`)와 지식 사본 갱신(기록 커밋 뒤라 실패해도 저장은 남는다). ⑤ 베타 I: 올리기 "다시 정리"(`POST /intake/{id}/analyze`)의 작업 폴더 준비(`ensure_workdir` → `prepare_workdir`)는 올린 파일의 읽기 상태(`IntakeFile.read_status`)를 따로 커밋한다: 이어서 `start_analysis` 가 잠금에 막혀 503 이어도 읽기 상태는 갱신돼 있다 (파일을 읽어 본 결과일 뿐 사용자가 쓴 값이 아니고 다음 시도가 다시 계산한다. 메모는 여전히 정리 작업과 한 트랜잭션).

## 베타 I 묶음이 바꾼 규칙
- 솔루션 자료 여러 개 올리기(`files.upload_files`): 진짜 SQLite 쓰기 잠금 아래에서 `WriteBusy`(번호 표시 잠금)와 `OperationalError`(저장·커밋 잠금)를 같이 잡는다. **저장된 파일이 하나도 없는 채로** 막히면 503, 앞에 저장된 파일이 있으면 200 "저장하지 못한 파일: …(앞의 파일은 저장했습니다)". `_save_upload` 는 `saved`/`too_big`/`duplicate` 를 돌려주고 건너뛴 중복·큰 파일은 저장으로 세지 않는다. `db.rollback()` 이 로그인 사용자 줄을 낡은 값으로 만들어 닫힌 세션에서 오류 화면이 `DetachedInstanceError`(500)가 되던 것은 `get_db` 가 세션을 닫기 전에 사용자 줄을 한 번 다시 읽어 막는다(`db._keep_user_loaded`): 라우터가 스스로 `rollback()` 한 뒤 `WriteBusy`·`StaleWrite` 를 내는 어느 화면에도 같다.
- 쓰기는 한 트랜잭션(베타 I): 올리기 "다시 정리"(`POST /intake/{id}/analyze`)는 메모와 정리 작업을 한 트랜잭션으로 저장하지만, 그 앞의 작업 폴더 준비(`prepare_workdir`)가 파일 읽기 상태를 따로 커밋한다 — 다섯째 예외(위 베타 H 의 예외 목록 ⑤).

## 베타 J 묶음이 바꾼 규칙
- `get_db` 닫기(`db._keep_user_loaded`)의 사용자 줄 다시 읽기는 `session.no_autoflush` 안이다: 롤백 뒤 세션에 남은 새 줄이 닫는 길에서 INSERT 되어 쓰기 잠금에 막히지 않는다 (`tests/test_beta_j.py` 가 진짜 `BEGIN IMMEDIATE` 아래에서 본다).

## 영업 B 묶음이 바꾼 규칙 (2026-11-26)
- 두 번 커밋하는 POST 의 ⑥번째 예외: 활동 기록 만들기·고치기·원문만 저장은 활동 기록을 커밋한 뒤 영업기회 AI 분석 작업을 따로 커밋한다(`activities.review_linked` → `opportunity_ai.request_review` → `queue.enqueue`). 두 번째 커밋이 쓰기 잠금에 막히면(`OperationalError`·`WriteBusy`) 되돌리고 로그만 남긴다: 활동 기록은 이미 저장됐으니 503 "저장하지 않았습니다" 를 보이지 않는다 (분석은 영업기회 화면의 [다시 분석]으로 다시 할 수 있다).
- 확인 항목 켜기(`POST /opportunities/{id}/checks`)가 다른 탭과 같은 항목을 동시에 켜 유일 제약에 걸리면 되돌리고 상세로 돌아간다 (이미 켜져 있다).
