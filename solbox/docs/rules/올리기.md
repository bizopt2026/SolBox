# 올리기 규칙 (solbox/docs/rules/올리기.md)

다루는 것: 글 붙여넣기·사진 붙여넣기·명함 파일 가져오기. 읽을 때: `intake`·`cardfile`·`cardplan` 을 고칠 때 (기본 구조는 CLAUDE.md "올리기 구조").

솔박스 `CLAUDE.md` 에서 옮긴 영역별 규칙이다 (2026-11-25). 묶음(베타) 순서와 글은 그대로 두었다. 뒤 묶음이 앞 묶음의 규칙을 바꾼 경우가 많으니 **아래쪽(뒤 묶음)이 정본**이다. 글 속의 "위/아래 베타 X" 는 다른 영역 파일에 있을 수 있다: 어느 묶음이 어느 파일에 있는지는 `docs/rules/README.md`.

## 베타 T 묶음이 바꾼 규칙
- **사용자 요청 2026-11-23: "올리기에서 텍스트 붙여넣기로도 자료를 입력할 수 있도록."** `POST /intake` 는 새 선택 칸 `pasted_text`(글)·`pasted_title`(제목, 60자까지)를 받는다. 병렬 길을 만들지 않았다: `intake.paste_upload` 가 글을 메모리 안 UTF-8 `.txt` 업로드 하나(`UploadFile`)로 바꿔 `create_intake(…, pasted_text, pasted_title)` 의 업로드 목록 맨 앞에 넣고, 그 뒤는 올린 `.txt` 파일과 완전히 같다(같은 저장 위치·크기 제한 `max_upload_mb`·`MAX_FILES` 에 포함·읽기·작업 폴더·정리). 파일 이름은 `<제목>.txt`(제목은 줄바꿈 같은 제어 문자를 공백으로 줄이고 올린 파일 이름과 같은 `clean_name` 으로 거른 뒤 60자까지, 이미 `.txt` 로 끝나면 덧붙이지 않음), 제목이 비면 `붙여넣은 글 <YYYY-MM-DD HH:MM>.txt`(서버 시각). 줄바꿈은 `\n` 으로 통일하고 앞뒤 공백은 자르지 않는다. 공백뿐인 글은 없는 것으로 본다.
- 한도: `intake.MAX_PASTE` = 200,000자(`MAX_NOTE` 옆, 줄바꿈 통일 뒤 글자 수), 넘으면 400 "붙여넣은 글은 200,000자까지 올릴 수 있습니다."(`PASTE_TOO_LONG`)와 함께 쓴 글·제목을 그대로(이스케이프해서) 채운 폼을 다시 그리고 아무것도 저장하지 않는다. 파일도 글도 없으면 400 `NO_FILES` = "파일을 고르거나 글을 붙여넣어 주세요."(예전 "올릴 파일을 선택하세요."를 바꿨다; 브라우저 `required` 는 뺐고 서버가 "파일 또는 글 하나 이상"을 본다). 글은 맨 앞에 두므로 파일이 `MAX_FILES` 개 이상이면 잘려 나가는 쪽은 마지막 파일이고(기존 "한 번에 20개까지" 안내) 글은 남는다. 폼 표(`_tok`)·`Once` 는 그대로(`pasted_*` 칸도 내용 해시에 든다). 커밋 횟수·AI 꺼짐 처리(보관만)도 그대로고 새 커밋은 없다.
- 화면: `intake/_dropzone.html` 이 파일 영역 아래에 "글 붙여넣기"를 더한다 — 전체 화면(`zone_id == 'intake'`)은 제목 칸 + 글 칸(8줄) + 글자 수 `n / 200,000자`, 홈 카드(`home`)는 접힌 `<details>` 안에 글 칸만(글이 있으면 펼쳐서 다시 그림). 글자 수는 `app.js` 의 `[data-paste]` 보강이고 JS 가 없어도 동작한다(서버가 센다). 상세 화면에서는 붙여넣은 글이 보통 `.txt` 문서 파일로 보인다(바뀐 것 없음). 요청이 multipart 가 아니면(`application/x-www-form-urlencoded`, 브라우저 폼은 항상 multipart) 한글 20만 자는 퍼센트 부호화로 starlette 의 칸 크기 한도(1MB)를 넘을 수 있다.
- 시험: `tests/test_beta_t.py`. 바꾼 기존 시험: `tests/test_intake_upload.py`(두 곳)·`tests/test_beta_b.py`(한 곳)의 오류 문구.

## 베타 Z 묶음이 바꾼 규칙
- `intake/_dropzone.html` 은 `max_paste`·`max_paste_title` 이 없으면 200000·60 을 쓴다 (`default(…, true)`). 이미 떠 있는 옛 프로그램(스냅숏 전)이 새 화면 파일을 읽는 이번 경우를 살린다.

## 베타 AA 묶음이 바꾼 규칙
- **사용자 요청 2026-11-24: 명함 사진 붙여넣기(B)와 명함 앱 내보내기 파일 가져오기(D).** 휴대폰은 서버에 닿지 않아 두 길을 골랐다. 결정은 `docs/ontology.md` 19장 (담당자(인물) 대상 유형은 더하지 않았다).
- **B. 사진 붙여넣기**: `intake/_dropzone.html` 아래에 힌트 줄(`data-dropzone-hint`, JS 가 보일 때만)이 있고 `app.js` 의 `[data-dropzone]` 이 문서의 `paste` 를 듣는다. 클립보드의 사진은 `붙여넣은 사진 N.<확장자>`(N 은 지금 고른 이름의 가장 큰 번호 + 1)로 이름 지어 끌어다 놓기와 같은 `add()` 로 실제 `<input type=file>` 에 더한다 (`DataTransfer`, 서버·엔드포인트 변화 없음, 크기·개수는 기존 경고와 서버 검사 그대로). 글만 있는 붙여넣기와 글칸에 글+사진이 함께 오는 붙여넣기는 건드리지 않는다 (글 붙여넣기 칸으로 보내지 않았다). 고른 파일 목록에 "빼기" 단추가 더해졌다. 전체 화면과 홈 카드 모두. 브라우저 시험은 Playwright 로 `ClipboardEvent` 를 보내 입력칸에 들어가고 POST 로 묶음이 생기는 것까지 봤다 (카카오톡에서 실제로 복사한 사진은 해 보지 못했다).
- **D. 명함 파일 가져오기** (`/intake/cards`, 로그인한 누구나, 폼 표 `Once`): `app/cardfile.py`(파서: vCard 2.1/3.0/4.0·csv UTF-8/BOM/CP949·xlsx 첫 시트, 머리글 낱말 `SYNONYMS`, 열 지정 `build_mapping`, `parse_card_file(경로) -> (열 매핑, 카드, 문제)`)와 `app/cardplan.py`(정리안 만들기)가 AI 없이 `Intake.plan` 을 직접 만든다. 묶음은 `Intake.source = "cards"`(새 열, `migrate.py` 가 시작 때 더함)이고 AI 작업을 만들지 않는다: `start_analysis` 는 거절하고(`False`), `POST /intake/{id}/analyze` 는 400, 화면은 "정리 시작"·"다시 정리"를 그리지 않는다. 한도: 파일 `max_upload_mb`, 명함 `cardfile.MAX_ROWS` = 2,000 (넘으면 400 오류, 묶음을 남기지 않는다: `intake.purge_new`). 이름·회사 열을 못 찾으면 묶음은 "올림" 상태로 남고 상세에 열 지정 단계(`POST /intake/{id}/cards-map`, 조건부 UPDATE 라 연타해도 한 번)가 나온다. 확인 대기의 "열 다시 고르기"(`POST …/cards-remap`)는 열 지정 단계로 되돌린다.
- 정리안: 기존 항목 종류를 그대로 쓰고(`add_contact`·`new_customer`·`new_partner`·`unplaced`) 항목마다 `from_cards: True`. 등록된 곳에 있으면 `add_contact`(대상은 화면에서 고정 글), 없으면 새 회사 한 항목에 담당자 줄이 여러 줄(`contact`)이다. 새 회사 기본 분류는 올릴 때 고른다(`default_kind`), 항목마다 `{키}__as`("분류": 고객/파트너, `intake.item_values` 의 `as_kind`, `intake.entity_kind`)로 바꿀 수 있다 — 이 읽기는 AI 항목에도 같지만 화면 칸은 명함 항목에만 있다. 같은 이름이 고객과 파트너에 모두 있으면 고객에 넣고 파트너 항목은 처음부터 제외. 항목의 `skip_default`/`skip_note` 는 확인 화면의 처음 제외 표시와 안내다 (`review_cards`). 회사 이름이 없는 명함은 `unplaced` 항목의 `lines`(읽을 수 있는 줄)로, 연락처 정보가 없는 명함은 등록된 회사일 때만 같은 곳으로. 직책 칸은 `부서 직함`, 전화 칸은 `휴대폰 / 유선`, 팩스·집 전화는 메모. 항목이 많아 대상 선택 칸을 항목마다 그리지 않는다.
- **유래·AI 생성 표시**: 이 길로 만든 기록의 `origin_type` 은 새 값 `import`(`ontology.ORIGIN_IMPORT`, "파일 가져오기", `origin.import_origin`), `origin_id` 는 올리기 묶음 번호. `is_ai_generated` 는 `intake`·`research` 만 참이라 "AI 생성" 배지·사본 줄이 붙지 않는다 (`AI_GENERATED_ORIGINS` 에 넣지 않았다). `ORIGINS_OF_INTAKE`(intake·import)로 R22 관계(`ORIGIN_PARENTS`)·상세 "유래:" 줄·목록 "올리기" 구분(`_common.origin_bucket`)이 함께 따라간다. 올리기 묶음을 지우는 길은 없지만 생기면 `clear_dangling` 을 두 값 모두에 불러야 한다. 명함 파일은 묶음 하나의 파일이라 한 고객에 묶이지 않는다 (`IntakeFile.target_*` 를 채우지 않는다). 연락처 줄 끝 출처 글은 `(명함 파일, 날짜 올리기)`(`intake.contact_source`).
- 확인 화면: 맨 위 "명함 n장을 읽어 m건으로 정리했습니다 …"(`plan_summary`), "읽은 방법" 카드(어느 열이 무엇이 되었나·쓰지 않은 열·합친 수·같은 파일을 이미 가져왔는지), "모두 포함·모두 제외"(`app.js` `.skip-all`, 모든 확인 화면에 있다), 카드 머리는 "새 회사"·"정리하지 못한 명함". 개인 정보: 올린 파일은 다른 올리기처럼 `uploads/intake/<번호>/` 에 남고 묶음을 버려도 지워지지 않는다 (기존 규칙).
- 시험: `tests/test_beta_aa.py` (파일은 모두 이 시험이 만든 가짜 값). 바꾼 기존 시험: `tests/test_ux_notices.py`(새 POST 세 개를 알림 표에), `tests/test_origin.py`(원 코드 목록에 `import`).
