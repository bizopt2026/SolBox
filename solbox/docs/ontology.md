# 솔박스 온톨로지 (기준 문서)

- 작성일: 2026-11-20
- 상태: 기준 문서 (단위 1~5 구현을 마친 뒤의 상태). 문서와 코드가 다르면 코드가 맞다: 정의의 기준은 `app/ontology.py`, 따라가는 엔진은 `app/relations.py`, 일관성은 `tests/test_ontology.py`·`tests/test_related.py` 가 검사한다. 2·10·12·13장은 결정 과정을 남긴 기록이다.
- 범위: `solbox/` 의 현재 기능에 실제로 쓰이는 대상·관계·행위만 다룬다. 쓰이지 않는 것은 9장 "확장 여지"에만 적는다.

## 1. 솔박스가 다루는 것

솔박스는 솔루션 사업 담당자들이 쓰는 사내 웹 시스템이다. 파트너에게서 솔루션을 발굴해 단계별로 관리하고, 고객·파트너와의 활동을 기록하며, 고객과 하는 프로젝트(옛 "기존 사업")에 맞는 솔루션 조합을 제안서로 만들고, 매주 시장·기술·정책 동향을 조사한다.

여기서 온톨로지는 다음 네 가지를 한곳에 정의하고 코드 전체가 그 정의를 따르게 하는 것을 뜻한다: **대상 유형, 속성, 관계, 행위.** 새 기술은 도입하지 않는다 (8장).

## 2. 현황에서 찾은 문제 (작업 전의 상태를 적은 기록. 현재 상태는 2.5)

이 장의 2.1~2.4 는 온톨로지 작업을 시작하기 **전**의 코드·화면을 적은 것이라 "기존 사업"·"수요 단서" 같은 옛 이름이 그대로 나온다. 지금의 이름과 상태는 2.5 와 3장 이후를 본다.

### 2.1 같은 개념이 다른 이름으로 쓰이는 곳

| 개념 | 쓰이는 이름 | 위치 예 |
|---|---|---|
| Business | "기존 사업" / "사업" / "사업명" | 메뉴·제목은 기존 사업, 지식 사본(`knowledge.py`)과 고객 상세의 버튼은 사업 |
| Proposal | "제안" / "제안 건" / (PPT는 "제안서") | 메뉴·목록은 제안, 홈·솔루션 상세는 제안 건 |
| Intake | "올리기" / "묶음" / "올리기 묶음" / "올린 묶음" / "올린 파일" | `intake/detail.html` 한 화면에 세 가지가 섞임 |
| SolutionFile | "자료" / "자료 파일" / "솔루션 자료" | `_files.html`, `sources.py`, `knowledge.py` |
| Solution.summary | "한 줄 소개" / "한 줄 요약" | 화면 vs 지식 사본 |
| Solution.applicable_types | "적용 가능 유형" / "적용 대상" / "적용 가능 사업 유형" | 화면 vs 지식 사본 vs 설계 문서 |
| Activity.date | "일자" / "날짜" | 화면 vs 지식 사본 |
| Activity.summary_md | "정리본" / "정리" | 폼 vs 상세·지식 사본 |
| 확인 항목 | "확인 필요" / "확인할 점" / "근거 문제" / "정할 값" | `checks.py`, `_macros.html`, `proposals.py` |
| 출처 | "출처" / "근거" / "참고" / "이유" | 제안은 출처, 리서치 제안 화면은 참고, 리서치 지식 사본은 근거·이유가 화면과 반대 |
| 제안 단계 | 상태 코드 `new/refining/outlined` vs 단계 키 `target/chat/outline` | `labels.py` vs `proposals.py` |

코드 값이 서로 겹치는 곳도 있다.

- 발굴 단계 `intake`(아이템 접수)와 대상 유형 `Intake`(올리기 묶음)가 같은 낱말이다.
- 활동 종류 `partner`(파트너 미팅)와 대상 유형 `Partner`가 같은 낱말이다.
- `tapping` 이 발굴 단계에서는 "사전 태핑", 활동 종류에서는 "고객 태핑"이다.

### 2.2 코드 속에만 있는(암묵적인) 관계

| 관계 | 지금 저장되는 방식 | 문제 |
|---|---|---|
| 수요 단서 → 고객 | `Activity.demand_signals[].customer` 에 고객 이름 글자 | 고객 기록과 연결되지 않아 고객 화면에서 볼 수 없다 |
| 후속 조치 → 담당자 | `follow_ups[].owner` 자유 글 | 사용자와 연결되지 않고, 행을 목록 순번으로 가리킨다 (번호 없음) |
| 방향·장 → 근거 자료 | `"solutions/1/card.md"` 같은 지식 사본 경로 글자 | 형식 정의가 `knowledge.py` 한 곳 외에 프롬프트 코드 6곳에 다시 적혀 있다. 사용자가 고친 출처는 검증하지 않는다 |
| 방향 → 솔루션 | `directions[].solutions[].solution_id` (JSON 안의 번호) | 솔루션을 지우면 낡은 번호가 남는다 |
| 제안 → 추가 후보 솔루션 | `extra_solution_ids` JSON 목록 | 위와 같다 |
| 리서치 제안 → 솔루션 | `suggestions[].solution_ids`, 글 속의 "id N" | 위와 같다. 솔루션 쪽에서는 자신을 언급한 리서치를 볼 수 없다 |
| 리서치 제안 → 등록된 후보 솔루션 | 솔루션 설명 글에 "리서치(날짜)에서 등록" | **해결됨 (단위 3)**: `solutions.origin_*` 연결 키. 옛 등록은 채우지 못했다 |
| 올린 파일 → 만들어진 기록 | `IntakeFile.target_type/target_id` | 활동 기록만 읽는다. 솔루션·파트너·고객 값은 쓰기만 하고 읽지 않는다 (읽기는 단위 5). **해결됨 (단위 3)**: 대상을 지우면 함께 비운다 |
| 올리기 묶음 → 만들어진 기록 | `Intake.result` JSON | **해결됨 (단위 3)**: 기록 쪽 `origin_type/origin_id` 키. 옛 기록은 `Intake.result` 로 한 번 되짚어 채웠다 |
| 솔루션 자료 ↔ 올린 파일 | 파일을 복사, 연결 키 없음 | 같은 파일이라는 사실이 남지 않는다 |
| 솔루션 태그·적용 유형 | 쉼표로 이은 글 | 글자 검색만 된다 |
| 이름으로 같은 대상 찾기 | `normalize_name`, `match_mentions` | 올리기·활동 초안에서만 쓰고, 직접 등록 화면은 이름 중복을 확인하지 않는다 |

### 2.3 같은 목록이 여러 곳에 정의된 곳

발굴 단계(4곳), 활동 종류(5곳), 장 종류(3곳), 정리안 항목 종류(4곳), 대상 유형별 이름·주소 표(4곳: `sources._SIMPLE`, `intake/detail.html`, `records.LINK_TYPES`, `tasks._MENTION_MODELS`), `"boxed"` 글자(4곳), 작업 상태 글자(6곳 이상).

### 2.4 지금 화면에서 건너갈 수 없는 조회

- 파트너 → 그 파트너의 솔루션이 들어간 제안 건, 그 솔루션에 관심을 보인 고객
- 고객 → 그 고객에게 이야기된 솔루션, 그 고객의 수요 단서와 남은 후속 조치
- 솔루션 → 이 솔루션이 이야기된 고객·기존 사업, 이 솔루션을 언급한 리서치 제안
- 기록(솔루션·활동·고객·파트너) → 어느 올리기 묶음 또는 리서치에서 만들어졌는지
- 후속 조치·수요 단서를 고객·담당·솔루션별로 모아 보기 (홈의 14일 목록뿐)

### 2.5 지금 상태 (단위 5 이후)

| 문제 | 상태 |
|---|---|
| 2.1 같은 개념의 다른 이름 (사업·제안·올리기·자료·일자 …) | 해결. 이름은 `ontology.label/prop/term` 한 곳. 화면·사본·프롬프트가 읽는다 (단위 1) |
| 2.1 겹치는 코드 값 (`intake`·`partner`·`tapping`) | 저장된 값은 그대로 두고 정의에서 이름 공간으로 구분했다 (Q5 결정) |

| 2.2 올린 파일 → 기록 (활동만 읽음), 묶음 → 기록 | 해결: 유래 열 (단위 3). 올린 파일의 대상 값은 이제 활동·솔루션·파트너·고객 모두 따라간다 (R21, 글 기반) |
| 2.2 리서치 제안 → 솔루션 (`solution_ids`) | **남음.** 여전히 JSON 안의 번호다. 솔루션 쪽에서 볼 수 있게 되었지만 (R18 해석기, "언급한 리서치 제안") 솔루션을 지워도 낡은 번호가 남는다 |
| 2.2 방향 → 솔루션, 제안 → 추가 후보 (JSON) | **남음.** 추가 후보(R15)는 해석기로 따라가고, 방향(R16)은 번호가 JSON 안의 일반 정수라 따라가지 않는다 |
| 2.2 근거 경로 글자 (R17) | **남음.** 해석은 `parse_rel` 한 곳으로 모았지만 저장은 글자 그대로이고 따라가지 않는다 |
| 2.2 솔루션 자료 ↔ 올린 파일 연결 키, 태그·적용 유형이 글 | **남음.** 바꾸지 않았다 |
| 2.2 이름으로 같은 대상 찾기 | **남음.** 직접 등록 화면은 이름 중복을 확인하지 않는다 |
| 2.3 같은 목록이 여러 곳에 | 해결. `ontology.py` 가 목록·유형 표를 가진다 (단위 1) |
| 2.4 건너갈 수 없는 조회 | 해결. 5장의 따라가서 얻는 관계와 `related()`, 11장 확인 질문 5개로 확인했다. "후속 조치·니즈를 고객·담당·솔루션별로 모아 보기" 중 담당별(내 할 일) 화면은 만들지 않았다 (조회는 R11 로 된다) |

## 3. 대상 유형

핵심 대상은 사업의 실제 대상이고, 부속 대상은 핵심 대상에 딸린 것, 작업 대상은 일을 처리하는 과정에서 생기는 것이다.

| 구분 | 대상 유형 (제안하는 이름) | 뜻 | 지금 코드 |
|---|---|---|---|
| 핵심 | **솔루션** | 파트너에게서 발굴해 고객에게 제안할 수 있는 제품·서비스 | `Solution` / `solutions` |
| 핵심 | **파트너** | 솔루션을 공급하는 회사 | `Partner` / `partners` |
| 핵심 | **고객** | 솔루션을 제안받는 회사 | `Customer` / `customers` |
| 핵심 | **프로젝트** (옛 "기존 사업") | 특정 고객과 하는(하게 된) 사업 한 건. 제안의 발판 | `Project` / `businesses` (물리 표 이름은 그대로) |
| 핵심 | **영업기회** (구현됨, 단위 4) | 한 고객의 니즈를 묶어 사업으로 만들어 가는 건. 수주하면 프로젝트가 된다 | `Opportunity` / `opportunities` |
| 핵심 | **BM** (구현됨, 단위 4) | 사업 모델. 고객에 묶이지 않는다 (특정 고객별로 나뉘는 것은 프로젝트) | `BM` / `bms` |
| 핵심 | **활동 기록** | 회의·통화·태핑·수요조사 등 한 번의 활동 | `Activity` / `activities` |
| 핵심 | **제안 건** | 특정 고객(과 프로젝트·영업기회)을 대상으로 한 제안 작업 한 건 | `Proposal` / `proposals` |
| 부속 | **자료** | 솔루션에 붙은 문서 파일 | `SolutionFile` / `solution_files` |
| 부속 | **후속 조치** | 활동에서 나온 할 일 | `FollowUp` / `follow_ups` (표). 옛 JSON 열 `activities.follow_ups` 는 복사만 하고 읽지 않는다 |
| 부속 | **고객 니즈** (옛 이름 "수요 단서", JSON 키는 `demand_signals` 그대로) | 활동에서 드러난 고객의 필요 | `CustomerNeed` / `customer_needs` (표). 옛 JSON 열 `activities.demand_signals` 는 복사만 하고 읽지 않는다. 영업기회에 묶이면 `opportunity_id` 가 채워진다 (단위 4) |
| 부속 | **제안 방향** | 제안 건에 대해 AI가 낸 솔루션 조합안 (최대 3개) | `Proposal.directions` (JSON) |
| 부속 | **구성안 장** | 제안서의 한 장 | `Proposal.outline.slides` (JSON) |
| 부속 | **확인 항목** | 방향·장·동향에 붙은 "확인할 것". 근거 문제 / 정할 값 두 종류 | `needs_check`, `checked` (JSON), `checks.py` |
| 작업 | **올리기 묶음** | 한 번에 올린 파일들과 그 정리 상태 | `Intake` / `intakes` |
| 작업 | **올린 파일** | 묶음 안의 파일 하나 | `IntakeFile` / `intake_files` |
| 작업 | **정리안 항목** | 묶음에 대해 AI가 제안한 저장 단위 | `Intake.plan.items` (JSON) |
| 작업 | **리서치 주제** | 주간 조사의 조사 항목 | `ResearchTopic` |
| 작업 | **리서치 실행** | 조사 한 회 | `ResearchRun` |
| 작업 | **리서치 보고서** | 분야별 동향 보고서 또는 발굴 방향 제안 | `ResearchReport` (+ `trends`, `insights`, `suggestions` JSON) |
| 시스템 | 사용자, AI 작업, 설정 | 로그인 계정, AI 대기열, 예약 설정 | `User`, `AIJob`, `AppSetting` |

대화 메시지(`ProposalMessage`)는 제안 건의 부속 기록으로만 다루고 별도 대상으로 올리지 않는다.

## 4. 속성

필수는 ●, 선택은 ○. "코드 값"은 정해진 목록에서 고르는 값이다.

**솔루션**

| 속성 | 자료형 | 필수 | 지금 필드 | 비고 |
|---|---|---|---|---|
| 이름 | 글 | ● | `name` | |
| 한 줄 소개 | 글 | ○ | `summary` | 지식 사본은 "한 줄 요약"이라 부름 |
| 상세 설명 | 긴 글 | ○ | `description` | |
| 발굴 단계 | 코드 값 | ● | `stage` | 아이템 접수 / 사전 태핑 / 수요조사 / 박스 등록 / 보류 |
| 활용 방향 | 글 | ○ | `usage_direction` | |
| 적용 가능 유형 | 글 | ○ | `applicable_types` | |
| 태그 | 글 목록 | ○ | `tags` (쉼표) | |

**파트너**: 이름 ●(`name`), 연락처 ○(`contact`, 여러 줄. 올리기의 "연락처 추가"가 줄을 덧붙임), 소개 ○(`description`), 메모 ○(`memo`)

**고객**: 이름 ●, 업종 ○(`industry`), 연락처 ○(`contact`), 메모 ○

**프로젝트** (옛 "기존 사업"): 이름 ●, 고객 ●, 설명 ○, 기간 ○(`period`, 글), 상태 ○(`status`, 정해진 목록에서 고른다: 준비 / 진행 / 완료 / 중단 / 유지보수, 정의 `ontology.PROJECT_STATUSES`. 비워 둘 수 있다. 목록에 없는 옛 자유 글은 고치지 않고 남기며 화면에는 "(이전 입력)" 을 붙여 보인다. 2026-11-22 베타 P), BM ○(`bm_id`), 메모 ○

**활동 기록**: 종류 ●(`kind`: 회의 / 파트너 미팅 / 고객 태핑 / 수요조사 / 기타), 일자 ○(`date`), 제목 ○(`title`), 원문 ●(`raw_text`), 정리본 ○(`summary_md`)

**제안 건**: 제목 ○(`title`), 요청 메모 ○(`request_memo`), 진행 단계 ●(`status`: 대상 지정 / 방향 검토 / 구체화 / 구성안 / 제안서 완료), 선택한 방향 ○(`selected_index`), 제안서 파일 ○(`deck_name`, `deck_built_at`)

**자료**: 원래 이름 ●, 자료 종류 ●(`kind`: 소개 / 스펙 / 관련), 글 추출 상태(`extract_status`), 크기

**후속 조치**: 할 일 ●(`task`), 담당 ○(`owner`, 글 + `owner_user_id`, 사용자 연결은 활성 사용자 이름과 정확히 같을 때만), 기한 ○(`due`, 날짜), 완료 ●(`done`). 활동 기록 안의 순서는 `position`

**고객 니즈** (옛 "수요 단서"): 고객 ○(`customer_name` 쓴 그대로 + `customer_id`, 등록된 고객과 정규화한 이름이 정확히 하나로 같을 때만 연결), 내용 ●(`content`), 영업기회 ○(`opportunity_id`, 단위 4에서 쓴다. 외래 키 제약 없는 번호 열)

**영업기회** (단위 4): 이름 ●(`name`), 고객 ●(`customer_id`), 단계 ●(`stage`: 발굴 / 제안 중 / 협상 / 수주 / 실패 / 보류, 기본 발굴, 순서 강제 없음), BM ○(`bm_id`), 프로젝트 ○(`project_id`, 수주 뒤 전환·연결로만 채워짐), 메모 ○(`memo`). 예상 금액·시기 같은 속성은 두지 않는다 (범위 밖)

**BM** (단위 4): 이름 ●(`name`), 한 줄 설명 ○(`summary`), 대상 고객 유형 ○(`target_customers`), 수익 구조 ○(`revenue_model`), 메모 ○. 작성자·생성·수정 시각은 붙고 유래 열은 없다

**올리기 묶음**: 메모 ○, 상태 ●(`status`: 올림 / 정리 중 / 확인 대기 / 저장 중 / 저장 완료 / 실패 / 버림)

**올린 파일**: 원래 이름 ●, 종류 ●(문서 / 사진 / 음성 / 기타), 읽기 상태 ●, 받아쓰기 진행률 ○

모든 핵심 대상에는 작성자(`created_by`)와 생성·수정 시각이 붙는다.

## 5. 관계

"구현"은 지금 저장 방식이다. **키** = 외래 키 또는 연결 표, **JSON** = JSON 안의 번호, **글** = 이름·경로 글자, **없음** = 저장되지 않고 다른 관계에서 따라가야만 알 수 있음.

| # | 관계 | 방향 | 수 | 구현 | 비고 |
|---|---|---|---|---|---|
| R1 | 파트너가 솔루션을 **공급한다** | 파트너 → 솔루션 | 1:N | 키 `solutions.partner_id` | 솔루션은 파트너가 없을 수 있다 |
| R2 | 고객이 프로젝트를 **가진다** | 고객 → 프로젝트 | 1:N | 키 `businesses.customer_id` | 프로젝트는 고객이 반드시 있다 |
| R3 | 솔루션에 자료가 **붙는다** | 솔루션 → 자료 | 1:N | 키 `solution_files.solution_id` | |
| R4 | 활동 기록이 솔루션을 **다룬다** | 활동 ↔ 솔루션 | N:M | 키 `activity_solutions` | |
| R5 | 활동 기록이 고객과 **관련된다** | 활동 ↔ 고객 | N:M | 키 `activity_customers` | |
| R6 | 활동 기록이 프로젝트와 **관련된다** | 활동 ↔ 프로젝트 | N:M | 키 `activity_businesses` | 단위 4 의 R6': 영업기회도 `activity_opportunities` 로 연결한다 (활동 기록 화면에서 직접 고른다. AI 가 언급해 만들지 않는다) |
| R7 | 활동 기록이 파트너와 **관련된다** | 활동 ↔ 파트너 | N:M | 키 `activity_partners` | |
| R8 | 활동 기록에서 후속 조치가 **나온다** | 활동 → 후속 조치 | 1:N | 외래 키 (`follow_ups.activity_id`) | 번호로 가리킨다. 활동 기록을 지우면 함께 지워진다 |
| R9 | 활동 기록에서 고객 니즈가 **나온다** | 활동 → 고객 니즈 | 1:N | 외래 키 (`customer_needs.activity_id`) | 활동 기록을 지우면 함께 지워진다 |
| R10 | 고객 니즈가 고객의 **것이다** | 고객 니즈 → 고객 | N:1 | 외래 키 (선택, `customer_needs.customer_id`) + 글 (이름) | 이름이 맞을 때만 연결. 고객을 지우면 연결만 풀리고 줄과 이름은 남는다. 고객 연결이 바뀌면(다른 고객이거나 없어지면) 묶여 있던 영업기회에서 풀린다 |
| R11 | 후속 조치를 사용자가 **맡는다** | 후속 조치 → 사용자 | N:1 | 외래 키 (선택, `follow_ups.owner_user_id`) + 글 (이름) | 활성 사용자 이름과 정확히 같을 때만 연결 |
| R12 | 제안 건이 고객을 **대상으로 한다** | 제안 건 → 고객 | N:1 | 키 `proposals.customer_id` | 필수 |
| R13 | 제안 건이 프로젝트를 **발판으로 한다** | 제안 건 → 프로젝트 | N:1 | 키 `proposals.business_id` | 선택. 그 고객의 프로젝트여야 한다 |
| R14 | 제안 건이 솔루션을 **조합한다** | 제안 건 ↔ 솔루션 | N:M | 키 `proposal_solutions` | 방향을 고른 뒤에만 채워진다 |
| R15 | 제안 건이 솔루션을 **후보에 더한다** | 제안 건 → 솔루션 | N:M | JSON `extra_solution_ids` | 후보 규칙은 "보류가 아닌 모든 솔루션 + 직접 추가한 솔루션"이라, 이 목록은 보류 솔루션을 후보로 넣을 때 쓴다 (보류가 아닌 솔루션은 이미 후보) |
| R16 | 제안 방향이 솔루션을 **쓴다** | 방향 → 솔루션 | N:M | JSON | 역할 글과 함께 |
| R17 | 방향·장·리서치 제안이 기록을 **근거로 삼는다** | 방향/장/제안 → 솔루션·자료·고객·프로젝트·파트너·활동·리서치 보고서·영업기회·BM | N:M | 글 (지식 사본 경로) | 경로 형식과 해석은 `ontology.parse_rel` 한 곳(옛 `businesses/N.md` 도 읽는다), 화면 표시는 `sources.describe_source`, 존재 확인은 `proposals.check_sources`. 저장된 글자는 고치지 않는다 |
| R18 | 리서치 제안이 솔루션을 **민다** | 리서치 제안 → 솔루션 | N:M | JSON `solution_ids` | |
| R19 | 리서치 제안에서 솔루션이 **등록된다** | 리서치 보고서 → 솔루션 | 1:N | 키 `solutions.origin_type='research'`, `origin_id`(보고서 번호), `origin_item`("suggestion:N"/"trend:N") | 번호는 응용 수준 키(제약 없음). 조사를 지우면 번호만 비운다. 같은 항목은 두 번 등록되지 않는다. 옛 등록은 비어 있다 |
| R20 | 올리기 묶음이 올린 파일을 **담는다** | 묶음 → 올린 파일 | 1:N | 키 | |
| R21 | 올린 파일이 기록의 **원본이다** | 올린 파일 → 활동/솔루션/파트너/고객 | N:1 | 종류+번호 (`target_type`, `target_id`) | 활동·솔루션·파트너·고객 모두 따라간다 (해석기). 대상을 지우면 함께 비운다 |
| R22 | 올리기 묶음에서 기록이 **만들어진다** | 묶음 → 솔루션/활동/고객/파트너 | 1:N | 키 `origin_type='intake'`, `origin_id`(묶음 번호) (네 표 모두) + JSON `Intake.result` | 새로 만든 기록만 (연결·덧붙임 제외). 유래 코드: 직접 입력 / 올리기 / 리서치, 비면 모름. 번호는 응용 수준 키 |
| R23 | 리서치 실행이 보고서를 **낸다** | 실행 → 보고서 | 1:N | 키 | |
| R24 | 사용자가 기록을 **작성한다** | 사용자 → 모든 핵심 대상 | 1:N | 키 `created_by_id` | 삭제 권한의 기준 |
| R25 | 파트너와 고객이 **같은 회사다** | 파트너 ↔ 고객 | 1:1 | 키 `partners.customer_id` (선택, 유일 색인) | 이름이 같아도 자동으로 잇지 않고 안내만 한다. 어느 쪽을 지워도 연결만 풀린다 |
| R26 | 고객 니즈가 영업기회로 **모인다** | 고객 니즈 → 영업기회 | N:1 | 키 `customer_needs.opportunity_id` (선택, 제약 없는 번호 열) | **구현됨.** 한 니즈는 영업기회 하나에만, 같은 고객의 니즈만 (묶인 니즈는 언제나 영업기회와 같은 고객이다: 묶은 니즈가 있으면 영업기회의 고객을 바꾸지 못하고, 니즈의 고객이 바뀌면 영업기회에서 풀린다). 영업기회를 지우면 비운다 |
| R27 | 영업기회가 고객의 **것이다** | 영업기회 → 고객 | N:1 | 키 `opportunities.customer_id` | **구현됨.** 필수 |
| R28 | 영업기회가 솔루션을 **검토한다** | 영업기회 ↔ 솔루션 | N:M | 키 `opportunity_solutions` | **구현됨.** 제안 후보 정렬에서 맨 앞 |
| R29 | 제안 건이 영업기회를 **위한 것이다** | 제안 건 → 영업기회 | N:1 | 키 `proposals.opportunity_id` | **구현됨.** 선택. 그 고객의 영업기회여야 한다 |
| R30 | 영업기회가 프로젝트로 **이어진다** | 영업기회 → 프로젝트 | 1:1 | 키 `opportunities.project_id` (유일 색인) | **구현됨.** 수주일 때 전환(새 프로젝트)하거나 같은 고객의 기존 프로젝트를 이어서 한 번만 |
| R31 | 프로젝트가 BM을 **따른다** | 프로젝트 → BM | N:1 | 키 `businesses.bm_id` | **구현됨.** 선택 |
| R32 | 영업기회가 BM으로 **접근한다** | 영업기회 → BM | N:1 | 키 `opportunities.bm_id` | **구현됨.** 선택 |
| R33 | BM이 솔루션으로 **구성된다** | BM ↔ 솔루션 | N:M | 키 `bm_solutions` | **구현됨.** 제안 후보 정렬에서 영업기회 다음 |

R1~R33 은 `app/ontology.py` 의 `RELATIONS` 와 같은 키다. 저장 방식이 키(fk·연결 표)인 관계는 물리 위치와 ORM 메타데이터로 자동으로 따라가고, JSON·글인 관계만 `ontology.RESOLVERS` 에 작은 해석기를 둔다.

- **JSON·글 기반(해석기)**: R15 (제안 건의 추가 후보 `extra_solution_ids`), R18 (리서치 제안의 `solution_ids`), R21 (올린 파일의 대상 종류+번호). 연결 목록에서 `storage` 가 `json`/`text` 로 표시된다.
- **따라가지 않음**: R16 (방향은 JSON 안에만 있어 출발할 기록이 없다), R17 (근거는 사본 경로 글자). 이유는 `ontology.UNTRAVERSED`.
- **연결 목록에서 뺌**: R24 (작성자는 모든 핵심 대상에 붙어 소음). `path_query` 로는 따라간다 (`ontology.QUIET_RELATIONS`).
- 새 관계를 `RELATIONS` 에 더하면 `tests/test_related.py` 가 따라가기 해석기와 보는 이름(`VIEW_LABELS`)이 없을 때 실패한다.

| D10 | 같은 회사 고객의 프로젝트 (파트너 → 프로젝트) | 파트너 —R25→ 고객 —R2→ 프로젝트 |

| D12 | 같은 회사 고객에게 한 제안 건 (파트너 → 제안 건) | 파트너 —R25→ 고객 ←R12— 제안 건 |
| D13 | 같은 회사 파트너가 공급하는 솔루션 (고객 → 솔루션) | 고객 ←R25— 파트너 —R1→ 솔루션 |

- 초안의 D6 "고객의 남은 후속 조치·고객 니즈(옛 수요 단서)" 중 고객 니즈는 저장된 R10 의 반대 방향(고객 ← 고객 니즈)이라 따로 정의하지 않았다. 고객 화면의 "고객 니즈" 그룹이 그것이다 (묶인 영업기회와 단계가 함께 보인다).
- 솔루션을 언급한 리서치 제안은 저장된 R18 의 반대 방향이고 JSON 기반이다 (`storage: json`).
- D14 는 "A 빼기 B" 로 정의한 첫 따라가서 얻는 관계다: `Derived.minus` 에 뺄 Derived 키를 적으면 엔진(`relations._derived_ids`·`_reach`)이 출발 기록마다 차집합을 구한다 (다른 관계도 같은 방식으로 정의할 수 있다).
- 경로의 문자열 원소(D4 의 `D7`)는 다른 따라가서 얻는 관계를 펼쳐 넣는다. 경로의 방향·유형이 저장된 관계 정의와 맞는지 시험이 검사한다.
- **공통 조회**: `ontology.related(db, 대상, viewer=…)` 가 대상 유형에 닿는 저장된 관계(양방향)와 출발하는 따라가서 얻는 관계를 그룹으로 돌려준다 (이름은 출발한 대상의 눈으로 본 `VIEW_LABELS`, 항목은 중복 없이 유형별 기본 순서, 그룹마다 10개까지와 전체 건수, 목록 화면에 걸러 보기가 있으면 "모두 보기" 주소, 따라가서 얻는 항목에는 "활동 기록 2건, 제안 건 1건을 거쳐" 같은 설명). 올리기 묶음에 닿는 그룹은 `viewer` 가 열 수 있는 것만 보인다. `ontology.path_query(db, 시작, ["R1", "R14", "R12"])` 는 관계 키를 차례로 따라가 닿은 기록을 돌려준다 (`"R6:project"` 로 도착 유형을 정하고 `"D7"` 처럼 따라가서 얻는 관계도 쓴다).
- **목록 걸러 보기**: `?customer_id= ?solution_id= ?partner_id= ?project_id= ?opportunity_id= ?bm_id=` 가 활동 기록·제안·영업기회·프로젝트·솔루션 목록에 있다 (`ontology.LIST_FILTERS`: 어느 관계 그룹과 뜻이 같은지). 숫자가 아니거나 없는 번호는 빈 목록이다. 연결 목록의 "모두 보기" 가 이 주소로 간다.

## 7. 한 정리 (코드 대응)

| 정리 | 한 일 | 단위 |
|---|---|---|
| 단일 정의 모듈 | `app/ontology.py` 에 대상 유형(이름·주소·사본 경로·속성 이름표), 코드 값 목록, 관계(R1~R33), 따라가서 얻는 관계(D1~D14), 보는 이름, 목록 걸러 보기를 둔다. `labels.py`·`sources`·`records`·`tasks`·템플릿의 유형 표가 이것을 읽는다 | 1 |
| 용어 통일 | 기존 사업 → 프로젝트, 수요 단서 → 고객 니즈, 제안 건/제안서, 올리기 묶음/올린 파일 | 1 |
| 암묵적 관계 명시 | 후속 조치·고객 니즈를 표로 분리(고객·사용자 연결), 기록의 유래 열, 파트너 ↔ 고객 "같은 회사" | 2, 3 |
| 참조 형식 하나로 | 근거 경로의 해석을 `ontology.parse_rel` 한 곳으로 (저장된 글자는 그대로) | 1 |
| BM·영업기회 | 활동 기록 → 고객 니즈 → 영업기회 → 프로젝트, BM | 4 |
| 공통 관계 조회 | `related()`·`path_query()`·`app/relations.py`. 모든 상세 화면의 "연결된 것" 구역(`templates/_related.html`)과 지식 사본 카드의 "## 연결"이 같은 조회를 쓴다 | 5 |

**하지 않은 것 (의도)**: 물리 표·열 이름 바꾸기(`businesses`·`business_id`·`activity_businesses` 그대로), 리서치의 "기존 솔루션 밀기" 를 솔루션 연결로 확장하기(박스 안에만), 방향 JSON 의 솔루션 번호를 표로 옮기기(여전히 일반 정수), 이름 중복 확인, 따라가서 얻는 관계의 저장(저장하지 않고 경로로만 정의한다).

**지식 사본의 "## 연결" 갱신 규칙**: 솔루션·고객·파트너·프로젝트·영업기회·BM 카드는 맨 아래 "## 연결" 에 저장된 관계와 건너서 연결된 것을 (그룹마다 8개까지, 나머지는 "외 N건") 경로와 함께 적는다. 관계가 바뀌면 `resync_related` 가 정의(레지스트리)로 한 걸음 닿는 사본 기록의 카드를 다시 쓴다. 따라가서 얻는 구역은 조금 늦을 수 있다: 그 카드가 다시 쓰일 때와 `rebuild-knowledge`(사본 형식을 올렸을 때 시작하며 자동) 때 맞춰진다. 올리기 묶음은 열 수 있는 사람이 정해져 있어 사본에 적지 않는다.

**하지 않은 것에 덧붙임**: `path_query` 는 앱 코드가 부르는 곳이 없다. 5장 "확인 질문"과 시험이 이것으로 따라가기를 검증하므로 두었다.

## 8. 새 기술이 필요한가

필요 없다. 대상 유형 20여 개, 저장된 관계 33개, 따라가서 얻는 관계 14개이고 가장 긴 조회가 4걸음(파트너 → 솔루션 → 활동 → 고객 …)이라 SQLite 의 IN 질의로 충분하다. 한 걸음이 질의 한 번이라 연결이 늘어도 질의 수는 늘지 않는다 (시험이 검사한다). 그래프 DB 는 도입하지 않았다.

## 9. 확장 여지 (지금은 만들지 않음)

- 사람(담당자·연락처)을 독립 대상으로: 지금은 파트너·고객의 연락처 글에 줄로 들어간다.
- 태그·적용 유형을 독립 대상으로 해서 태그별 묶어 보기.
- 계약·견적·매출 같은 거래 대상: 현재 기능에 없다.
- 고객 ↔ 파트너가 같은 회사인 경우를 하나의 "조직"으로 합치기.

## 10. 결정이 필요한 것

추측하지 않고 질문으로 남긴다. 각 항목의 추천안은 **굵게** 표시했다.

**Q1. 후속 조치를 독립된 기록으로 분리할까?**
지금은 활동 기록 안의 목록이라 번호가 없고, 고객·담당별로 모아 볼 수 없다.
- **A (추천): 표로 분리한다.** 후속 조치마다 번호가 생기고 고객·솔루션·담당별 조회가 된다. 기존 데이터를 옮겨야 한다 (원래 JSON은 지우지 않고 남겨 되돌릴 수 있게 한다).
- B: 지금처럼 두고 온톨로지에 "활동 기록의 부속"으로만 정의한다. 데이터 이전은 없지만 2.4의 조회는 느리고 제한적이다.

**Q2. 수요 단서의 고객을 고객 기록에 연결할까?**
- **A (추천): 표로 분리하고 고객에 연결한다.** 이름이 등록된 고객과 맞으면 연결하고, 맞지 않으면 이름 글자만 남긴다. 고객 화면에서 수요 단서를 볼 수 있게 된다.
- B: 지금처럼 이름 글자로 둔다.
- 추가 질문: 수요 단서를 **솔루션**과도 연결해야 하나? (예: "이 수요에는 이 솔루션") 지금 기능에는 없다.

**Q3. Business의 이름은 "기존 사업"으로 통일할까, "사업"으로 할까?**
- **A (추천): "기존 사업".** 메뉴와 대부분의 화면이 이미 이 이름이고, 솔루션 사업 자체와 헷갈리지 않는다.
- B: "사업".

**Q4. Proposal의 이름은?**
- **A (추천): 대상은 "제안 건", PPT 파일은 "제안서".** 메뉴 이름은 짧게 "제안"으로 둔다.
- B: 모두 "제안"으로.

**Q5. 겹치는 코드 값(`intake`, `partner`, `tapping`)을 바꿀까?**
- **A (추천): 저장된 값은 그대로 두고, 정의에서 "발굴 단계의 intake"와 "올리기 묶음 Intake"를 구분해 적는다.** 화면의 한국어 이름은 이미 다르다. 데이터 이전이 없다.
- B: 코드 값을 바꾼다 (예: 단계 `intake` → `received`). 깔끔하지만 저장된 데이터와 지식 사본을 모두 바꿔야 한다.

**Q6. 발굴 단계에 순서 규칙을 둘까?** (사업 규칙이라 추측하지 않았다)
지금은 아이템 접수에서 박스 등록으로 바로 가거나 뒤로 돌아가는 것이 모두 된다.
- A: 지금처럼 자유롭게 둔다.
- B: 접수 → 사전 태핑 → 수요조사 → 박스 등록 순서로만 앞으로 가고, 보류는 어디서든 가능하며 보류에서는 이전 단계로 돌아온다.

### 확인 결과

**1. 이 파트너의 솔루션이 들어간 제안 건은 무엇이고, 어느 고객 대상인가?**
- 경로: 파트너 —R1→ 솔루션 ←R14— 제안 건 (D3), 고객은 —R12→. `path_query(파트너, ["R1","R14","R12"])`
- 답 (그린에너지테크): 제안 건 "한빛 에너지 절감 제안" → 고객 한빛병원 (센스웍스는 "대성 온도 관제 제안" → 대성물류센터)
- 화면: 파트너 상세 "솔루션이 들어간 제안 건" 그룹, 고객은 그 제안 건 상세. "솔루션이 닿은 고객"(D4) 그룹에는 한빛병원이 "솔루션 1건, 활동 기록 2건 …을 거쳐" 로 보인다.

**2. 이 고객에게 지금까지 이야기된 솔루션과, 그중 아직 제안하지 않은 것은?**
- 경로: D14 = (D1 (고객 ← 활동 → 솔루션) ∪ 고객 ← 영업기회 → 검토 솔루션) − D2 (고객 ← 제안 건 → 솔루션)
- 답 (한빛병원): 이야기된 AI 공조 최적제어·스마트 조명 제어, 제안된 AI 공조 최적제어·태양광 자가소비 진단 → 아직 제안하지 않은 것은 **스마트 조명 제어**
- 화면: 이제 화면이 직접 보여 준다. 고객 상세 왼쪽 칸의 "이야기했지만 아직 제안하지 않은 솔루션" 카드(D14)에 스마트 조명 제어가 나오고 솔루션마다 "제안 만들기"(고객·솔루션이 미리 채워진 제안 만들기)가 붙는다. "이야기된 솔루션"(D1)과 "제안된 솔루션"(D2)은 옆 칸에 그대로 있다. 이 질문은 `tests/test_ux_features.py` 가 화면까지 검사한다. (처음 확인할 때는 두 그룹을 사람이 나란히 읽었다.)

**3. 이 솔루션에 관심을 보인 고객들의 남은 후속 조치는?**
- 경로: 솔루션 → D7 → 고객 → D6. `path_query(솔루션, ["D7","D6"])`
- 답 (설비 예지보전 센서): 관심 고객 대성물류센터·미래제조 → 대성물류센터 "계약 검토"·"현장 방문 일정", 미래제조 "설비 목록 요청" (완료한 "회의록 정리"는 제외)
- 화면: 솔루션 상세 "관심을 보인 고객" → 각 고객 상세의 "남은 후속 조치". 한 화면에 합쳐 보이지는 않는다.

**4. 이 프로젝트와 관련해 논의된 솔루션을 공급하는 파트너는?**
- 경로: 프로젝트 ←R6— 활동 —R4→ 솔루션 ←R1— 파트너. `path_query(프로젝트, ["R6","R4","R1"])` (이 경로의 이름 붙은 따라가서 얻는 관계는 정의하지 않았다)
- 답 (한빛병원 설비 유지보수): 논의된 솔루션 AI 공조 최적제어·스마트 조명 제어 → 공급 파트너 **그린에너지테크** (스마트 조명 제어는 파트너가 없다)
- 화면: 프로젝트 상세 "활동 기록" → 활동 상세 "솔루션" → 솔루션 상세의 파트너. 한 그룹으로는 보이지 않는다.

**5. 최근 올리기로 만들어진 활동 기록에서 나온 고객 니즈를 고객별로 묶으면, 그중 영업기회가 된 것은?**
- 경로: 올리기 묶음 —R22→ 활동 —R9→ 고객 니즈 —R10→ 고객, 영업기회는 —R26→. `path_query(묶음, ["R22:activity","R9"])`
- 답 (가장 최근 묶음 1번): 한빛병원 "야간 조명 전력 줄이기" (영업기회 아님), 미래제조 "설비 고장 예측" → **영업기회 "미래제조 예지보전" (발굴)**
- 화면: 고객 상세 "고객 니즈" 그룹에 니즈마다 묶인 영업기회와 단계가 보인다. "올리기 묶음별로 묶기"는 화면에 없다 (조회만 된다).

화면 길이 (예시 자료 복사본, 1280 / 390 너비, 단위 5 전 → 후): 고객 상세 896→1066 px / 933→1405 px, 솔루션 상세 1048→1275 px / 1346→1765 px. 연결된 것이 많아진 만큼 길어졌고 (고객 상세는 후속 조치·고객 니즈·제안된 솔루션, 솔루션 상세는 관심 고객·프로젝트·리서치 제안이 새로 보인다), 건너서 연결된 것이 네 그룹을 넘으면 접힌다.

## 13. BM · 영업기회 · 프로젝트 (결정됨, 단위 4 에서 구현)

검토에서 나온 설명: "BM은 사업 모델이고, 특정 고객별로 나뉘는 것은 프로젝트다. 고객 니즈들이 영업기회로 만들어져서 프로젝트가 된다."

흐름: **활동 기록 → 고객 니즈 → 영업기회 → 프로젝트.** BM 은 고객에 묶이지 않는다. 초안에서 제안한 선택지는 모두 추천안대로 받아들여졌다 (아래 "결정된 것").

```
활동 기록 ──나온다──▶ 고객 니즈(수요 단서) ──모인다──▶ 영업기회 ──수주되면──▶ 프로젝트
                          │                          │                      │
                          └────── 고객 ◀─────────────┴──────────────────────┘
                                                     │                      │
                                             제안 건 ─┘            BM(사업 모델) ◀─ 따른다
```

**대상 유형**

| 대상 | 뜻 | 코드 | 상태 |
|---|---|---|---|
| **프로젝트** | 특정 고객과 하는(하게 된) 사업 한 건 | `Project` / `businesses` | 단위 1 에서 이름을 바꿨다. 기존 데이터는 그대로 프로젝트가 되었다 |
| **고객 니즈** | 활동에서 드러난 고객의 필요 | `CustomerNeed` / `customer_needs` | 단위 2 에서 표로 분리했다 |
| **영업기회** | 한 고객의 니즈 하나 이상을 묶어 사업으로 만들어 가는 건 | `Opportunity` / `opportunities` | 단위 4 에서 만들었다 |
| **BM** | 사업 모델. 고객에 묶이지 않는다 | `BM` / `bms` | 단위 4 에서 만들었다 |

**관계 (코드의 `app/ontology.py` 와 같은 키)**

초안에서는 R25~R32 였으나 R25 를 단위 3 이 "같은 회사다"로 먼저 썼으므로 R26~R33 으로 밀었다.

| # | 관계 | 방향 | 수 | 비고 |
|---|---|---|---|---|

## 14. 열린 것 (일부러 하지 않았거나 남은 것)

- 물리 표 이름 바꾸기: `businesses`·`business_id`·`activity_businesses` 는 그대로다 (코드 이름만 프로젝트).
- 리서치 "기존 솔루션 밀기": 솔루션 연결은 여전히 박스 단계 안에서만 (지금 자동 후보는 보류가 아닌 솔루션).
- 방향 JSON 의 솔루션 번호는 일반 정수다. R16 은 따라가지 않고 솔루션을 지워도 낡은 번호가 남는다. R15·R18 의 JSON 번호도 같다 (해석기가 읽을 뿐 정리하지 않는다).
- 근거 경로 글자(R17)는 따라가지 않는다. 솔루션 자료 ↔ 올린 파일 연결 키는 없다.
- 지식 사본의 따라가서 얻는 구역은 조금 늦을 수 있다 (7장).
- 담당(내 할 일)별 후속 조치 모아 보기 화면은 없다. 제안 건(대상 구역)·활동 기록(후속 조치·니즈 구역)은 자기 특수 구역을 그대로 쓰고 연결 구역에는 나머지 관계만 나온다.
- PPT 슬라이드 디자인(배치) 개편은 회사 표준 템플릿 파일이 생길 때까지 미룬다 (아직 없음, 아래 15장).
- 프로젝트 상태의 옛 자유 글은 데이터를 바꾸지 않고 남겨 두었다 ("(이전 입력)" 표시). 한꺼번에 목록 값으로 옮기는 일은 하지 않았다: 어느 글을 어느 값으로 볼지 사람이 정해야 한다.
- 같은 회사 건너가기는 파트너 ↔ 고객 한 쌍(R25)뿐이다. "조직" 대상은 만들지 않았다 (9장).
