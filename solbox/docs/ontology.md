# 솔박스 온톨로지 (초안)

- 작성일: 2026-11-20
- 상태: **초안, 검토 요청 중.** 이 문서는 현황을 정리하고 정의를 제안할 뿐이고, 코드는 아직 바꾸지 않았다.
- 범위: `solbox/` 의 현재 기능에 실제로 쓰이는 대상·관계·행위만 다룬다. 쓰이지 않는 것은 9장 "확장 여지"에만 적는다.

## 1. 솔박스가 다루는 것

솔박스는 솔루션 사업 담당자들이 쓰는 사내 웹 시스템이다. 파트너에게서 솔루션을 발굴해 단계별로 관리하고, 고객·파트너와의 활동을 기록하며, 고객의 기존 사업에 맞는 솔루션 조합을 제안서로 만들고, 매주 시장·기술·정책 동향을 조사한다.

여기서 온톨로지는 다음 네 가지를 한곳에 정의하고 코드 전체가 그 정의를 따르게 하는 것을 뜻한다: **대상 유형, 속성, 관계, 행위.** 새 기술은 도입하지 않는다 (8장).

## 2. 현황에서 찾은 문제

### 2.1 같은 개념이 다른 이름으로 쓰이는 곳

| 개념 | 쓰이는 이름 | 위치 예 |
|---|---|---|
| Business | "기존 사업" / "사업" / "사업명" | 메뉴·제목은 기존 사업, 지식 사본(`knowledge.py`)과 고객 상세의 버튼은 사업 |
| Proposal | "제안" / "제안 건" / (PPT는 "제안서") | 메뉴·목록은 제안, 홈·솔루션 상세는 제안 건 |
| Intake | "올리기" / "묶음" / "올리기 묶음" / "올린 묶음" / "올린 파일" | `intake/detail.html` 한 화면에 세 가지가 섞임 |
| SolutionFile | "자료" / "자료 파일" / "솔루션 자료" | `_files.html`, `sources.py`, `knowledge.py` |
| Solution.summary | "한 줄 소개" / "한 줄 요약" | 화면 vs 지식 사본 |
| Solution.applicable_types | "적용 가능 유형" / "적용 대상" / "적용 가능 사업 유형" | 화면 vs 지식 사본 vs 설계 문서 |
| Activity.date | "일자" / "날짜" | 화면 vs 지식 사본 |
| Activity.summary_md | "정리본" / "정리" | 폼 vs 상세·지식 사본 |
| 확인 항목 | "확인 필요" / "확인할 점" / "근거 문제" / "정할 값" | `checks.py`, `_macros.html`, `proposals.py` |
| 출처 | "출처" / "근거" / "참고" / "이유" | 제안은 출처, 리서치 제안 화면은 참고, 리서치 지식 사본은 근거·이유가 화면과 반대 |
| 제안 단계 | 상태 코드 `new/refining/outlined` vs 단계 키 `target/chat/outline` | `labels.py` vs `proposals.py` |

코드 값이 서로 겹치는 곳도 있다.

- 발굴 단계 `intake`(아이템 접수)와 대상 유형 `Intake`(올리기 묶음)가 같은 낱말이다.
- 활동 종류 `partner`(파트너 미팅)와 대상 유형 `Partner`가 같은 낱말이다.
- `tapping` 이 발굴 단계에서는 "사전 태핑", 활동 종류에서는 "고객 태핑"이다.

### 2.2 코드 속에만 있는(암묵적인) 관계

| 관계 | 지금 저장되는 방식 | 문제 |
|---|---|---|
| 수요 단서 → 고객 | `Activity.demand_signals[].customer` 에 고객 이름 글자 | 고객 기록과 연결되지 않아 고객 화면에서 볼 수 없다 |
| 후속 조치 → 담당자 | `follow_ups[].owner` 자유 글 | 사용자와 연결되지 않고, 행을 목록 순번으로 가리킨다 (번호 없음) |
| 방향·장 → 근거 자료 | `"solutions/1/card.md"` 같은 지식 사본 경로 글자 | 형식 정의가 `knowledge.py` 한 곳 외에 프롬프트 코드 6곳에 다시 적혀 있다. 사용자가 고친 출처는 검증하지 않는다 |
| 방향 → 솔루션 | `directions[].solutions[].solution_id` (JSON 안의 번호) | 솔루션을 지우면 낡은 번호가 남는다 |
| 제안 → 추가 후보 솔루션 | `extra_solution_ids` JSON 목록 | 위와 같다 |
| 리서치 제안 → 솔루션 | `suggestions[].solution_ids`, 글 속의 "id N" | 위와 같다. 솔루션 쪽에서는 자신을 언급한 리서치를 볼 수 없다 |
| 리서치 제안 → 등록된 후보 솔루션 | 솔루션 설명 글에 "리서치(날짜)에서 등록" | 연결 키가 없다 |
| 올린 파일 → 만들어진 기록 | `IntakeFile.target_type/target_id` | 활동 기록만 읽는다. 솔루션·파트너·고객 값은 쓰기만 하고 읽지 않으며 지워도 정리되지 않는다 |
| 올리기 묶음 → 만들어진 기록 | `Intake.result` JSON | 기록 쪽에서는 어느 묶음에서 왔는지 알 수 없다 (활동 기록의 원본 파일 제외) |
| 솔루션 자료 ↔ 올린 파일 | 파일을 복사, 연결 키 없음 | 같은 파일이라는 사실이 남지 않는다 |
| 솔루션 태그·적용 유형 | 쉼표로 이은 글 | 글자 검색만 된다 |
| 이름으로 같은 대상 찾기 | `normalize_name`, `match_mentions` | 올리기·활동 초안에서만 쓰고, 직접 등록 화면은 이름 중복을 확인하지 않는다 |

### 2.3 같은 목록이 여러 곳에 정의된 곳

발굴 단계(4곳), 활동 종류(5곳), 장 종류(3곳), 정리안 항목 종류(4곳), 대상 유형별 이름·주소 표(4곳: `sources._SIMPLE`, `intake/detail.html`, `records.LINK_TYPES`, `tasks._MENTION_MODELS`), `"boxed"` 글자(4곳), 작업 상태 글자(6곳 이상).

### 2.4 지금 화면에서 건너갈 수 없는 조회

- 파트너 → 그 파트너의 솔루션이 들어간 제안 건, 그 솔루션에 관심을 보인 고객
- 고객 → 그 고객에게 이야기된 솔루션, 그 고객의 수요 단서와 남은 후속 조치
- 솔루션 → 이 솔루션이 이야기된 고객·기존 사업, 이 솔루션을 언급한 리서치 제안
- 기록(솔루션·활동·고객·파트너) → 어느 올리기 묶음 또는 리서치에서 만들어졌는지
- 후속 조치·수요 단서를 고객·담당·솔루션별로 모아 보기 (홈의 14일 목록뿐)

## 3. 대상 유형

핵심 대상은 사업의 실제 대상이고, 부속 대상은 핵심 대상에 딸린 것, 작업 대상은 일을 처리하는 과정에서 생기는 것이다.

| 구분 | 대상 유형 (제안하는 이름) | 뜻 | 지금 코드 |
|---|---|---|---|
| 핵심 | **솔루션** | 파트너에게서 발굴해 고객에게 제안할 수 있는 제품·서비스 | `Solution` / `solutions` |
| 핵심 | **파트너** | 솔루션을 공급하는 회사 | `Partner` / `partners` |
| 핵심 | **고객** | 솔루션을 제안받는 회사 | `Customer` / `customers` |
| 핵심 | **기존 사업** | 우리가 고객과 이미 하고 있는 사업. 제안의 발판 | `Business` / `businesses` |
| 핵심 | **활동 기록** | 회의·통화·태핑·수요조사 등 한 번의 활동 | `Activity` / `activities` |
| 핵심 | **제안 건** | 특정 고객(과 기존 사업)을 대상으로 한 제안 작업 한 건 | `Proposal` / `proposals` |
| 부속 | **자료** | 솔루션에 붙은 문서 파일 | `SolutionFile` / `solution_files` |
| 부속 | **후속 조치** | 활동에서 나온 할 일 | `Activity.follow_ups` (JSON) |
| 부속 | **수요 단서** | 활동에서 드러난 고객의 필요 | `Activity.demand_signals` (JSON) |
| 부속 | **제안 방향** | 제안 건에 대해 AI가 낸 솔루션 조합안 (최대 3개) | `Proposal.directions` (JSON) |
| 부속 | **구성안 장** | 제안서의 한 장 | `Proposal.outline.slides` (JSON) |
| 부속 | **확인 항목** | 방향·장·동향에 붙은 "확인할 것". 근거 문제 / 정할 값 두 종류 | `needs_check`, `checked` (JSON), `checks.py` |
| 작업 | **올리기 묶음** | 한 번에 올린 파일들과 그 정리 상태 | `Intake` / `intakes` |
| 작업 | **올린 파일** | 묶음 안의 파일 하나 | `IntakeFile` / `intake_files` |
| 작업 | **정리안 항목** | 묶음에 대해 AI가 제안한 저장 단위 | `Intake.plan.items` (JSON) |
| 작업 | **리서치 주제** | 주간 조사의 조사 항목 | `ResearchTopic` |
| 작업 | **리서치 실행** | 조사 한 회 | `ResearchRun` |
| 작업 | **리서치 보고서** | 분야별 동향 보고서 또는 발굴 방향 제안 | `ResearchReport` (+ `trends`, `insights`, `suggestions` JSON) |
| 시스템 | 사용자, AI 작업, 설정 | 로그인 계정, AI 대기열, 예약 설정 | `User`, `AIJob`, `AppSetting` |

대화 메시지(`ProposalMessage`)는 제안 건의 부속 기록으로만 다루고 별도 대상으로 올리지 않는다.

## 4. 속성

필수는 ●, 선택은 ○. "코드 값"은 정해진 목록에서 고르는 값이다.

**솔루션**

| 속성 | 자료형 | 필수 | 지금 필드 | 비고 |
|---|---|---|---|---|
| 이름 | 글 | ● | `name` | |
| 한 줄 소개 | 글 | ○ | `summary` | 지식 사본은 "한 줄 요약"이라 부름 |
| 상세 설명 | 긴 글 | ○ | `description` | |
| 발굴 단계 | 코드 값 | ● | `stage` | 아이템 접수 / 사전 태핑 / 수요조사 / 박스 등록 / 보류 |
| 활용 방향 | 글 | ○ | `usage_direction` | |
| 적용 가능 유형 | 글 | ○ | `applicable_types` | |
| 태그 | 글 목록 | ○ | `tags` (쉼표) | |

**파트너**: 이름 ●(`name`), 연락처 ○(`contact`, 여러 줄. 올리기의 "연락처 추가"가 줄을 덧붙임), 소개 ○(`description`), 메모 ○(`memo`)

**고객**: 이름 ●, 업종 ○(`industry`), 연락처 ○(`contact`), 메모 ○

**기존 사업**: 이름 ●, 설명 ○, 기간 ○(`period`, 글), 상태 ○(`status`, 자유 글. 정해진 목록 없음), 메모 ○

**활동 기록**: 종류 ●(`kind`: 회의 / 파트너 미팅 / 고객 태핑 / 수요조사 / 기타), 일자 ○(`date`), 제목 ○(`title`), 원문 ●(`raw_text`), 정리본 ○(`summary_md`)

**제안 건**: 제목 ○(`title`), 요청 메모 ○(`request_memo`), 진행 단계 ●(`status`: 대상 지정 / 방향 검토 / 구체화 / 구성안 / 제안서 완료), 선택한 방향 ○(`selected_index`), 제안서 파일 ○(`deck_name`, `deck_built_at`)

**자료**: 원래 이름 ●, 자료 종류 ●(`kind`: 소개 / 스펙 / 관련), 글 추출 상태(`extract_status`), 크기

**후속 조치**: 할 일 ●(`task`), 담당 ○(`owner`, 글), 기한 ○(`due`, 날짜), 완료 ●(`done`)

**수요 단서**: 고객 ○(`customer`, 지금은 이름 글자), 내용 ●(`content`)

**올리기 묶음**: 메모 ○, 상태 ●(`status`: 올림 / 정리 중 / 확인 대기 / 저장 중 / 저장 완료 / 실패 / 버림)

**올린 파일**: 원래 이름 ●, 종류 ●(문서 / 사진 / 음성 / 기타), 읽기 상태 ●, 받아쓰기 진행률 ○

모든 핵심 대상에는 작성자(`created_by`)와 생성·수정 시각이 붙는다.

## 5. 관계

"구현"은 지금 저장 방식이다. **키** = 외래 키 또는 연결 표, **JSON** = JSON 안의 번호, **글** = 이름·경로 글자, **없음** = 저장되지 않고 다른 관계에서 따라가야만 알 수 있음.

| # | 관계 | 방향 | 수 | 구현 | 비고 |
|---|---|---|---|---|---|
| R1 | 파트너가 솔루션을 **공급한다** | 파트너 → 솔루션 | 1:N | 키 `solutions.partner_id` | 솔루션은 파트너가 없을 수 있다 |
| R2 | 고객이 기존 사업을 **가진다** | 고객 → 기존 사업 | 1:N | 키 `businesses.customer_id` | 기존 사업은 고객이 반드시 있다 |
| R3 | 솔루션에 자료가 **붙는다** | 솔루션 → 자료 | 1:N | 키 `solution_files.solution_id` | |
| R4 | 활동 기록이 솔루션을 **다룬다** | 활동 ↔ 솔루션 | N:M | 키 `activity_solutions` | |
| R5 | 활동 기록이 고객과 **관련된다** | 활동 ↔ 고객 | N:M | 키 `activity_customers` | |
| R6 | 활동 기록이 기존 사업과 **관련된다** | 활동 ↔ 기존 사업 | N:M | 키 `activity_businesses` | |
| R7 | 활동 기록이 파트너와 **관련된다** | 활동 ↔ 파트너 | N:M | 키 `activity_partners` | |
| R8 | 활동 기록에서 후속 조치가 **나온다** | 활동 → 후속 조치 | 1:N | JSON | 순번으로 가리킨다 |
| R9 | 활동 기록에서 수요 단서가 **나온다** | 활동 → 수요 단서 | 1:N | JSON | |
| R10 | 수요 단서가 고객의 **것이다** | 수요 단서 → 고객 | N:1 | 글 (이름) | 연결되지 않음 |
| R11 | 후속 조치를 사용자가 **맡는다** | 후속 조치 → 사용자 | N:1 | 글 (이름) | 연결되지 않음 |
| R12 | 제안 건이 고객을 **대상으로 한다** | 제안 건 → 고객 | N:1 | 키 `proposals.customer_id` | 필수 |
| R13 | 제안 건이 기존 사업을 **발판으로 한다** | 제안 건 → 기존 사업 | N:1 | 키 `proposals.business_id` | 선택. 그 고객의 사업이어야 한다 |
| R14 | 제안 건이 솔루션을 **조합한다** | 제안 건 ↔ 솔루션 | N:M | 키 `proposal_solutions` | 방향을 고른 뒤에만 채워진다 |
| R15 | 제안 건이 솔루션을 **후보에 더한다** | 제안 건 → 솔루션 | N:M | JSON `extra_solution_ids` | 박스 등록이 아닌 솔루션을 후보로 넣을 때 |
| R16 | 제안 방향이 솔루션을 **쓴다** | 방향 → 솔루션 | N:M | JSON | 역할 글과 함께 |
| R17 | 방향·장·리서치 제안이 기록을 **근거로 삼는다** | 방향/장/제안 → 솔루션·자료·고객·기존 사업·파트너·활동·리서치 보고서 | N:M | 글 (지식 사본 경로) | 형식은 `knowledge.REL_FORMATS`, 해석은 `sources.describe_source` |
| R18 | 리서치 제안이 솔루션을 **민다** | 리서치 제안 → 솔루션 | N:M | JSON `solution_ids` | |
| R19 | 리서치 제안에서 솔루션이 **등록된다** | 리서치 보고서 → 솔루션 | 1:N | 글 (설명 속 문장) | 연결 키 없음 |

## 6. 행위

조건은 지금 코드가 실제로 강제하는 것만 적었다. "누구나"는 로그인한 사용자 모두다.

## 10. 결정이 필요한 것

추측하지 않고 질문으로 남긴다. 각 항목의 추천안은 **굵게** 표시했다.

**Q1. 후속 조치를 독립된 기록으로 분리할까?**
지금은 활동 기록 안의 목록이라 번호가 없고, 고객·담당별로 모아 볼 수 없다.
- **A (추천): 표로 분리한다.** 후속 조치마다 번호가 생기고 고객·솔루션·담당별 조회가 된다. 기존 데이터를 옮겨야 한다 (원래 JSON은 지우지 않고 남겨 되돌릴 수 있게 한다).
- B: 지금처럼 두고 온톨로지에 "활동 기록의 부속"으로만 정의한다. 데이터 이전은 없지만 2.4의 조회는 느리고 제한적이다.

**Q2. 수요 단서의 고객을 고객 기록에 연결할까?**
- **A (추천): 표로 분리하고 고객에 연결한다.** 이름이 등록된 고객과 맞으면 연결하고, 맞지 않으면 이름 글자만 남긴다. 고객 화면에서 수요 단서를 볼 수 있게 된다.
- B: 지금처럼 이름 글자로 둔다.
- 추가 질문: 수요 단서를 **솔루션**과도 연결해야 하나? (예: "이 수요에는 이 솔루션") 지금 기능에는 없다.

**Q3. Business의 이름은 "기존 사업"으로 통일할까, "사업"으로 할까?**
- **A (추천): "기존 사업".** 메뉴와 대부분의 화면이 이미 이 이름이고, 솔루션 사업 자체와 헷갈리지 않는다.
- B: "사업".

- **A (추천): 대상은 "제안 건", PPT 파일은 "제안서".** 메뉴 이름은 짧게 "제안"으로 둔다.
- B: 모두 "제안"으로.

**Q5. 겹치는 코드 값(`intake`, `partner`, `tapping`)을 바꿀까?**
- **A (추천): 저장된 값은 그대로 두고, 정의에서 "발굴 단계의 intake"와 "올리기 묶음 Intake"를 구분해 적는다.** 화면의 한국어 이름은 이미 다르다. 데이터 이전이 없다.
- B: 코드 값을 바꾼다 (예: 단계 `intake` → `received`). 깔끔하지만 저장된 데이터와 지식 사본을 모두 바꿔야 한다.

**Q6. 발굴 단계에 순서 규칙을 둘까?** (사업 규칙이라 추측하지 않았다)
지금은 아이템 접수에서 박스 등록으로 바로 가거나 뒤로 돌아가는 것이 모두 된다.
- A: 지금처럼 자유롭게 둔다.
- B: 접수 → 사전 태핑 → 수요조사 → 박스 등록 순서로만 앞으로 가고, 보류는 어디서든 가능하며 보류에서는 이전 단계로 돌아온다.
- C: 순서는 권장만 하고, 단계를 건너뛸 때 확인을 한 번 묻는다.
- 추천을 하려면 실제 업무에서 단계를 건너뛰는 일이 있는지 알아야 한다.

**Q7. "박스 등록" 단계만 제안 후보가 되는 규칙이 맞나?**
지금 코드는 박스 등록 단계의 솔루션과, 제안 건에 직접 추가한 솔루션만 AI에게 후보로 준다. 이 규칙을 온톨로지의 행위 조건으로 그대로 적어도 되는지 확인이 필요하다.

**Q8. 기록의 유래(어디서 만들어졌는지)를 관계로 남길까?**

**Q9. 후속 조치의 담당을 사용자에 연결할까?**
담당에는 우리 직원이 아닌 사람(고객사 담당자 등)도 들어간다.
- **A (추천): 글자는 그대로 두고, 이름이 사용자와 정확히 같을 때만 연결을 덧붙인다.** "내 할 일" 조회가 가능해진다.

지금은 경고만 한다. 행위 조건으로 무엇을 적을지의 문제다.
- **A (추천): 지금처럼 경고만.**
- B: "근거 문제"가 남은 장이 있으면 만들 수 없게 한다.

**Q11. 파트너와 고객이 같은 회사인 경우가 있나?**

## 13. BM · 영업기회 · 프로젝트 (추가 초안, 검토 요청)

검토에서 나온 설명: "BM은 사업 모델이고, 특정 고객별로 나뉘는 것은 프로젝트다. 고객 니즈들이 영업기회로 만들어져서 프로젝트가 된다."

이 흐름은 지금 시스템에 없다. 지금은 "기존 사업"(고객에 속함) 하나와 "수요 단서"(활동 기록 안의 글)만 있다. 아래는 이 설명을 대상과 관계로 옮긴 제안이고, 굵은 물음표가 붙은 곳은 추측하지 않고 질문으로 남긴다.

```
활동 기록 ──나온다──▶ 고객 니즈(수요 단서) ──모인다──▶ 영업기회 ──수주되면──▶ 프로젝트
                          │                          │                      │
                          └────── 고객 ◀─────────────┴──────────────────────┘
                                                     │                      │
                                             제안 건 ─┘            BM(사업 모델) ◀─ 따른다
```

**대상 유형 (바뀌거나 새로 생기는 것)**

| 대상 | 뜻 | 지금 코드 | 변화 |
|---|---|---|---|
| **프로젝트** | 특정 고객과 하는(하게 된) 사업 한 건 | `Business` ("기존 사업") | 이름을 바꾼다. 기존 데이터는 그대로 프로젝트가 된다 **(QD)** |
| **고객 니즈** | 활동에서 드러난 고객의 필요 | `Activity.demand_signals` ("수요 단서") | Q2대로 독립 기록으로 분리. 화면 이름을 "수요 단서"로 둘지 "고객 니즈"로 바꿀지 **(QF)** |
| **영업기회** | 한 고객의 니즈 하나 이상을 묶어 사업으로 만들어 가는 건 | 없음 | 새로 만든다 |
| **BM** | 사업 모델. 고객에 묶이지 않는다 | 없음 | 새로 만든다 **(QA)** |

**관계 (제안)**

| # | 관계 | 방향 | 수 | 비고 |
|---|---|---|---|---|
| R25 | 고객 니즈가 영업기회로 **모인다** | 고객 니즈 → 영업기회 | N:1 (선택) | 한 니즈는 영업기회 하나에만 **(QC)** |
| R26 | 영업기회가 고객의 **것이다** | 영업기회 → 고객 | N:1 (필수) | |
| R27 | 영업기회가 솔루션을 **검토한다** | 영업기회 ↔ 솔루션 | N:M | 넣을지 **(QC)** |
| R28 | 제안 건이 영업기회를 **위한 것이다** | 제안 건 → 영업기회 | N:1 (선택) | 제안 건의 대상은 지금처럼 고객(+프로젝트)이고, 영업기회 연결을 더한다 **(QE)** |
| R29 | 영업기회가 프로젝트로 **이어진다** | 영업기회 → 프로젝트 | 1:1 (선택) | 수주 뒤 프로젝트를 만들면 연결. 영업기회 없이 등록된 프로젝트도 있을 수 있다 (기존 데이터) |
| R30 | 프로젝트가 BM을 **따른다** | 프로젝트 → BM | N:1 (선택) | **(QA)** |
| R31 | 영업기회가 BM으로 **접근한다** | 영업기회 → BM | N:1 (선택) | **(QA)** |
| R32 | BM이 솔루션으로 **구성된다** | BM ↔ 솔루션 | N:M | **(QA)** |
| R2' | 고객이 프로젝트를 **가진다** | 고객 → 프로젝트 | 1:N | 지금의 R2 (이름만 바뀜) |
| R6' | 활동 기록이 프로젝트·영업기회와 **관련된다** | 활동 ↔ 프로젝트, 활동 ↔ 영업기회 | N:M | 프로젝트는 지금의 R6. 영업기회 연결을 더할지 **(QC)** |

**행위 (제안)**

| 대상 | 행위 | 조건 |
|---|---|---|
| 영업기회 | 만들기 | 고객 필수. 고객 니즈를 골라 묶을 수 있다 (같은 고객의 니즈만) |
| 영업기회 | 단계 변경 | 단계 목록 **(QB)** |
| 영업기회 | 프로젝트로 전환 | 수주 단계일 때. 프로젝트를 만들고 R29로 잇는다 |
| BM | 등록·수정·삭제 | 프로젝트·영업기회가 따르고 있으면 삭제 불가 (제안) |

**질문**

**QA. BM은 무엇으로 이루어지나?**
- 속성으로 무엇을 적나? 제안: 이름, 한 줄 설명, 대상 고객 유형, 수익 구조(글), 메모.
- 솔루션과의 관계: **A (추천): BM은 솔루션 여러 개로 구성된다 (N:M).** "이 BM에는 이 솔루션들이 들어간다"를 기록하고, 제안 건에서 BM을 고르면 그 솔루션들이 후보로 먼저 올라온다. / B: 솔루션과 직접 잇지 않는다.
- 프로젝트·영업기회는 BM 하나를 따른다(선택)로 두어도 되나, 여러 BM을 따를 수 있어야 하나?

**QB. 영업기회의 단계 목록은?**
제안: 발굴 → 제안 중 → 협상 → 수주 / 실패 / 보류. 실제로 쓰는 단계 이름이 있으면 알려 주면 그대로 쓴다. 예상 금액·예상 시기 같은 속성이 필요한지도 함께.

**QC. 니즈와 영업기회, 프로젝트의 수 관계**
- 한 고객 니즈는 영업기회 하나에만 속한다 (추천) / 여러 영업기회에 속할 수 있다.
- 영업기회 하나는 프로젝트 하나로 이어진다 (추천) / 여러 프로젝트로 나뉠 수 있다.
- 영업기회에 "검토 중인 솔루션"을 직접 연결할까 (추천: 연결한다. 제안 건을 만들 때 후보로 쓴다), 활동 기록을 영업기회에도 연결할까 (추천: 연결한다).

**QD. 지금 "기존 사업"으로 등록된 데이터는 모두 프로젝트로 옮겨도 되나?**
추천: 그대로 프로젝트가 된다 (표 이름과 번호는 유지하고 이름만 바꾼다. 데이터를 옮기거나 지우지 않는다).

**QE. 제안 건은 무엇을 대상으로 하나?**
- **A (추천): 지금처럼 고객(필수)과 프로젝트(선택)를 대상으로 하고, 영업기회(선택)를 더한다.** 기존 고객의 프로젝트에 얹는 제안과, 새 영업기회를 위한 제안을 모두 다룬다.
- B: 제안 건은 항상 영업기회에 속한다. 기존 제안 건에는 영업기회를 새로 만들어 붙여야 한다.

**QF. 화면 이름: "수요 단서"를 "고객 니즈"로 바꿀까?**
추천: "고객 니즈"로 바꾼다 (설명에 쓰신 말과 맞춘다).

**범위에 대한 알림.** BM과 영업기회는 지금 기능에 없는 새 대상이라, 온톨로지 정리와 함께 등록·목록·상세 화면과 AI 지시문 변경이 새로 필요하다. 적용 계획(3단계)에서 온톨로지 정리 단위와 새 대상 단위를 나눠 적는다.
