# 온톨로지 적용 계획

- 작성일: 2026-11-20
- 기준: `docs/ontology.md` (10·12·13장의 결정 포함). 13장의 질문 QA~QF는 모두 추천안으로 확정됐다.
- 원칙: 한 단위가 끝날 때마다 전체 테스트(`python -X dev -m pytest -q -W error`)가 통과해야 다음으로 넘어간다. 기존 기능과 데이터를 깨지 않는다.

## 확정된 모델 요약

- 핵심 대상: 솔루션, 파트너, 고객, **프로젝트**(옛 "기존 사업"), 활동 기록, 제안 건, **영업기회**(새), **BM**(새)
- 부속 대상: 자료, **후속 조치**(표로 분리), **고객 니즈**(옛 "수요 단서", 표로 분리), 제안 방향, 구성안 장, 확인 항목
- 영업기회 단계: 발굴 → 제안 중 → 협상 → 수주 / 실패 / 보류 (순서 강제 없음). 예상 금액·시기는 이번에 넣지 않는다.
- BM 속성: 이름, 한 줄 설명, 대상 고객 유형, 수익 구조, 메모. BM ↔ 솔루션 N:M. 프로젝트·영업기회는 BM 하나를 따를 수 있다(선택).
- 고객 니즈는 영업기회 하나에만 속한다(선택). 영업기회는 프로젝트 하나로 이어진다(선택).
- 제안 건의 대상: 고객(필수) + 프로젝트(선택) + 영업기회(선택).
- 제안 후보: 보류를 뺀 모든 단계의 솔루션 + 제안 건에 직접 추가한 솔루션.
- 파트너 ↔ 고객 "같은 회사" (1:1, 선택).
- 기록의 유래: 직접 입력 / 올리기 묶음 / 리서치 제안.

## 데이터 원칙 (모든 단위 공통)

- **기존 표와 열은 이름을 바꾸거나 지우지 않는다.** `businesses` 표, `business_id` 열, `activities.follow_ups`·`demand_signals` JSON 열은 그대로 둔다. 코드에서는 새 이름(`Project`, `project_id`)을 쓰고 ORM 에서 옛 물리 이름에 대응시킨다. 이 대응은 `app/ontology.py` 에 적는다. (물리 이름까지 바꾸는 것은 운영 데이터 구조를 바꾸는 일이라 이번에는 하지 않는다.)
- 새 구조는 **추가만** 한다: 새 표는 `create_all`, 새 열은 `migrate.py` 가 시작 때 만든다.
- 기존 데이터를 새 표로 옮기는 일은 **복사**다. 원래 JSON 값은 그대로 남는다. 복사는 한 번만 실행되고(`app_settings` 의 표시), 시작할 때 바꿀 것이 있으면 `migrate.py` 가 **DB 사본(`app.db.before-migrate-날짜시각`)을 시작 한 번에 하나만** 만든다. 열 추가·JSON 복사·유래 채우기 단계가 같은 사본을 나눠 쓰고, 사본은 첫 단계가 바꾸기 전에 (게으르게) 만든다. 바꿀 것이 없는 시작(두 번째 시작부터)은 사본을 만들지 않는다.
- **되돌리기:** 서버를 멈추고, 이전 버전 코드로 돌린 뒤, **새 버전으로 처음 시작했을 때 만들어진 `app.db.before-migrate-…` 사본**(새 버전을 시작한 뒤 만들어진 사본 중 가장 이른 것)을 `app.db` 로 복원한다 (`app.db-wal`·`app.db-shm` 파일이 있으면 지운다). 사본 이후에 입력한 내용은 사라진다. 옛 코드는 새 표·열을 무시한다.
  - **경고: 업그레이드한 뒤 사본 복원 없이 옛 버전으로 돌렸다가 다시 업그레이드하지 않는다.** 옛 버전에서 입력한 후속 조치·고객 니즈는 옛 JSON 열에만 들어가고, 새 버전의 복사는 이미 끝난 것으로 표시되어 있어 다시 복사하지 않는다 (새 표에 나타나지 않는다). 옛 버전으로 돌린다면 반드시 사본을 복원하고, 그 뒤에 다시 올릴 때 복사가 처음부터 다시 실행된다.
- 지식 폴더(`knowledge/`)는 사본이므로 구조가 바뀌면 전체를 다시 만든다 (`rebuild-knowledge`). 저장된 근거 경로(`businesses/3.md` 등)는 바꾸지 않고, 해석기가 옛 형식도 읽는다.

## 단위

### 단위 1. 단일 정의 모듈과 용어 통일 (DB 변경 없음)

- `app/ontology.py` 를 만든다: 대상 유형(코드, 한국어 이름, 모델, 목록·상세 주소, 지식 사본 경로 형식, 물리 표 이름), 코드 값 목록(발굴 단계, 활동 종류, 자료 종류, 제안 진행 단계, 올리기 상태 등), 관계 목록(이름·방향·수·저장 방식), 근거 참조 해석(`경로 ↔ (유형, 번호)`).
- `labels.py`, `sources.py`, `records.LINK_TYPES`, `tasks._MENTION_MODELS`, `knowledge.REL_FORMATS`, 템플릿의 유형 표, 프롬프트 코드의 경로 글자가 이 정의를 읽게 한다. `labels.py` 는 호환을 위해 이름을 다시 내보낸다.
- 코드 이름 `Business` → `Project` (표는 `businesses` 그대로), 주소 `/businesses` → `/projects` (옛 주소는 새 주소로 넘긴다), 지식 사본 `businesses/` → `projects/` (옛 경로도 해석).
- 화면·지식 사본·프롬프트의 용어를 통일한다: 프로젝트, 제안 건/제안서, 올리기 묶음, 자료, 한 줄 소개, 적용 가능 유형, 일자, 정리본, 고객 니즈, 확인 항목(근거 문제 / 확인할 점), 출처.
- 제안 후보 규칙을 바꾼다: 보류를 뺀 모든 단계.
- 검증: 기존 테스트 전부(문구가 바뀐 단정만 수정), 정의와 실제 모델·주소가 어긋나지 않는지 검사하는 테스트, 옛 근거 경로 해석 테스트.
- 데이터 이전: 없음. 되돌리기: 코드만 되돌린다.

### 단위 2. 후속 조치와 고객 니즈를 기록으로 분리

- 새 표 `follow_ups`(활동, 순서, 할 일, 담당 글, 담당 사용자(선택), 기한, 완료), `customer_needs`(활동, 순서, 고객 이름 글, 고객(선택), 내용, 영업기회(선택, 단위 4에서 사용)).
- 한 번의 복사: 모든 활동 기록의 JSON 을 새 표로. 고객은 이름이 등록된 고객과 정규화해 정확히 하나로 맞을 때만 연결하고, 담당은 사용자 이름과 정확히 같을 때만 연결한다.
- 읽고 쓰는 곳을 모두 새 표로 바꾼다: 활동 기록 저장·수정, 올리기 저장, 홈의 후속 조치, 완료 표시(번호 기준. 옛 순번 주소는 유지), 지식 사본, 중복 할 일 표시.
- 검증: 복사 전후 건수와 내용 일치 테스트, 두 번 실행해도 중복되지 않는 테스트, 옛 구조 DB 에서 시작하는 테스트.
- 데이터 이전: 복사(추가만). 되돌리기: 공통 원칙.

### 단위 3. 유래, 같은 회사, 올린 파일 연결 정리

- 솔루션·활동 기록·고객·파트너에 유래(`origin_type`: 직접 입력 / 올리기 / 리서치, `origin_id`) 열을 더한다. 올리기 저장과 리서치 "후보로 등록"이 채운다. 기존 기록 중 올리기로 만든 것은 `Intake.result` 로 되짚어 채운다 (리서치로 등록한 옛 솔루션은 채우지 못한다).
- 파트너 ↔ 고객 "같은 회사" 연결(`partners.customer_id`, 한 고객에 파트너 하나).
- `IntakeFile.target_*` 는 기록을 지울 때 함께 비운다.
- 검증: 유래 되짚기 테스트, 같은 회사 연결의 양방향 표시, 삭제 뒤 정리.

### 단위 4. BM 과 영업기회

- 새 표 `bms`, `bm_solutions`, `opportunities`(고객, 이름, 단계, BM(선택), 프로젝트(선택), 메모), `opportunity_solutions`, `activity_opportunities`. 새 열 `businesses.bm_id`, `proposals.opportunity_id`.
- 화면: BM 목록·상세·등록, 영업기회 목록·상세·등록, 고객 니즈를 골라 영업기회로 묶기(같은 고객의 니즈만), 영업기회 단계 변경, 수주한 영업기회를 프로젝트로 전환, 프로젝트·영업기회의 BM 선택, 제안 건의 영업기회 선택.
- 제안 후보: 영업기회의 검토 솔루션과 BM 의 솔루션을 후보 앞쪽에 둔다.
- 지식 사본에 BM·영업기회 파일을 더해 AI 가 읽을 수 있게 하고, 관련 프롬프트에 새 대상을 설명한다. AI 가 영업기회·BM 을 만들거나 고치게 하지는 않는다.
- 검증: 행위 조건 테스트(같은 고객의 니즈만, 전환은 한 번, BM 삭제 제한), 화면 확인.

### 단위 5. 공통 관계 조회와 검증

- `ontology.related(db, 대상)`: 정의된 관계(저장된 것과 따라가서 얻는 것)를 따라 연결된 대상을 돌려준다. 각 상세 화면에 "연결된 것" 구역을 이 함수로 그린다.
- 따라가서 얻는 관계: 고객에게 이야기된·제안된 솔루션, 파트너의 솔루션이 들어간 제안 건과 닿은 고객, 솔루션이 이야기된 프로젝트·영업기회, 고객의 남은 후속 조치·니즈, 기록의 유래.
- 지식 사본의 각 카드에 관계 요약을 넣어 AI 가 같은 구조를 근거로 쓰게 한다.
- 검증: 관계 조회 테스트, `docs/ontology.md` 11장의 질문 5개를 예시 데이터로 확인, 최종 문서 갱신(`ontology.md` 를 초안에서 기준 문서로, `CLAUDE.md`).
