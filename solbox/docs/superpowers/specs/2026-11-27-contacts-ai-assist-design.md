# 담당자 관리 부담 줄이기 (영업 D 후속: 회의 참석자 연결 · 메모 일괄 정리 · 명함 변경 제안 · 의사결정자 접촉 공백)

작성 2026-11-27. 상태: **승인 (2026-11-27)**. 앞 설계: `2026-11-26-sales-crm-d-design.md`.

## 1. 왜 하나

D 단계로 담당자(사람) 기록이 생겼지만, 영업기회에 담당자를 잇는 일·회사마다 옛 연락처 메모를 나누는 일·직함이 바뀐 사람을 고치는 일이 **사람 손에 남아 있다**. 사용자의 요구는 "담당자 관리가 또 일이 되면 안 된다, AI 를 최대한 써서 사용자는 거의 손대지 않게" 이다 (2026-11-27).

원칙 (사용자와 합의한 컨설팅 결과)
1. 따로 입력하는 화면을 늘리지 않는다. 담당자 정보는 **회의 메모·명함을 올리는 기존 흐름의 덤**으로 생긴다.
2. AI·코드가 제안하고 사람은 한 번 누르거나 그대로 저장만 한다. 확신이 높은 것만 미리 체크한다.
3. 안 해도 손해가 없다. 필수 칸·"역할을 정하세요" 같은 경고는 두지 않는다.
4. 개인 정보 규칙은 그대로: AI 에는 이미 보내는 회의 메모와 담당자 이름·직함만 간다. 전화·이메일은 보내지 않고, 대조는 코드가 한다.

## 2. 고른 것 (사용자 결정 2026-11-27)

컨설팅의 ①·③·④·⑤ 를 한다 (② 역할 AI 추정은 하지 않는다: 역할은 지금처럼 사람이 정한다).

| 번호 | 내용 | 고른 방식 |
|---|---|---|
| ① | 회의 메모 → 참석 담당자 연결 | **C: AI 추출 + 코드 찾기** (AI 정리 때는 AI 가 외부 참석자를 이름·직함·회사로, 직접 입력·AI 꺼짐 때는 코드가 메모에서 담당자 이름을 찾는다) |
| ③ | 옛 연락처 메모 일괄 정리 | **가: 메모 글은 그대로, 화면에서 옮긴 줄을 접어 숨김** (관리자 화면에서 한 번) |
| ④ | 명함으로 바뀐 직함·연락처 | **제안으로 올림** (AI 제안함에서 [반영]·[모두 반영]) |
| ⑤ | 의사결정자 접촉 공백 | 코드 계산, 브리핑 카드 한 줄 + AI 분석 입력 |

## 3. 목표 · 하지 않을 것 · 실패로 볼 것

목표
- 활동 기록을 저장하면 참석한 담당자가 활동 기록에 이어지고, 그 활동 기록이 이어진 영업기회에도 이어진다 (영업기회 폼을 열 일이 거의 없다).
- 관리자가 한 번 눌러 모든 회사의 확실한 연락처 줄을 담당자로 옮긴다.
- 명함·올리기에서 같은 사람의 바뀐 직함·새 번호는 한 번 누르면 반영된다.
- 의사결정자와 오래 접촉이 없으면 영업기회 브리핑에 한 줄로 보인다.

하지 않을 것
- 역할 AI 추정 (②), 역할 미입력 경고, 담당자 필수 입력, 담당자 전체 목록 메뉴.
- AI·코드가 사람 확인 없이 **새 담당자를 만들거나 기존 담당자 칸을 고치는 것** (①의 새 사람은 체크 안 된 칩, ④는 제안). ③만 예외: 관리자가 건수를 보고 한 번 확인한다.
- 우리 직원(사용자 계정)을 담당자로 만들기.
- 활동 기록 목록·보드에 담당자 칸 추가.

실패로 볼 것
- 동명이인·우리 직원이 엉뚱한 회사 담당자로 이어진다 (미리 체크는 "그 활동의 고객·파트너 담당자 중 이름이 정확히 하나 맞음" 일 때만).
- 일괄 정리가 원래 메모 글을 잃는다 (글은 바꾸지 않는다).
- 같은 제안이 명함을 올릴 때마다 계속 쌓인다 (같은 담당자·같은 칸·같은 새 값의 열린 제안은 하나).
- AI 가 꺼져 있으면 활동 기록을 저장하지 못한다.

## 5. 동작

### 5.1 ① 회의 메모 → 참석 담당자

**AI 쪽 (활동 기록 AI 정리 `activity_structure`, 올리기 정리 `intake_analyze` 의 활동 항목)**
- 출력 `attendees` 를 글 목록과 함께 객체도 받는다: `{"name", "title", "company"}` (회사는 원문에 나온 고객·파트너 이름, 모르면 빈 글). 글만 온 옛 모양도 그대로 받는다 (이름만). 프롬프트에 "우리 회사 사람(작성자 포함)은 `internal: true`" 를 더해 직원을 가른다.
- 정리본의 "## 참석자" 구역은 지금처럼 이름(직함) 글로 남는다.

**코드 쪽 (`app/contacts.py` 한 곳: `match_attendees`)**
- 대상 범위: 그 활동 기록에 연결된 고객·파트너(확인 화면에서 고른 것)의 담당자.
- 참석자마다: 이름(공백 무시)이 범위 안 담당자와 **정확히 하나** 맞으면 "맞음" (미리 체크). 둘 이상이면 "여럿" (체크 없이 후보를 보임). 없으면 "새 사람".
- `internal` 이거나 이름이 사용자 계정의 이름·아이디와 같으면 버린다.
- 코드 찾기 (AI 가 없을 때·직접 입력 폼·AI 가 놓친 사람): 메모 원문(정리본 포함)에 범위 안 담당자 이름(2자 이상, 공백 무시)이 나오면 "맞음" 으로 더한다. 직접 입력 폼은 저장 전 화면이 없으므로 아래 "직접 입력" 규칙을 따른다.

**확인 화면 (AI 정리 결과 폼, 올리기 확인 화면의 활동 항목)**
- 연결 구역에 "참석한 담당자" 칩 줄: `☑ 최현수 · 상무` `☐ 김서윤?` (여럿이면 후보 고르기) `☐ + 박도윤 (새 담당자: 한빛물류)`.
- 새 사람 칩은 연결된 고객·파트너가 **하나뿐일 때만** 보이고 처음에는 체크하지 않는다. 체크하고 저장하면 그 회사에 담당자를 만든다 (이름·직함, 유래 = 그 활동의 유래).
- 고객 고르기를 바꾸면 범위가 바뀐다: 스크립트가 있으면 칩을 다시 그리고(HTMX), 없으면 저장할 때 범위 밖 담당자는 버린다.

**직접 입력 폼·활동 기록 수정 폼**
- "참석한 담당자" check_picker (연결된 고객·파트너의 담당자). 만들 때는 메모 글에서 코드가 찾은 이름을 미리 체크한다. 수정 폼은 저장된 연결을 보인다.

**영업기회로 번지기**
- 활동 기록을 저장할 때, 그 활동 기록에 이어진 영업기회마다 참석한 담당자 중 **그 영업기회 고객의 담당자**를 영업기회 담당자에 더한다 (빼지는 않는다). 영업기회 담당자를 손으로 뺀 뒤 같은 사람이 다음 회의에 또 나오면 다시 더해진다 (내 판단: 회의에 나온 사람은 관여자다).

### 5.2 ③ 옛 연락처 메모 일괄 정리 (관리 › 중복 정리 옆 "연락처 메모 정리", 관리자만)
- 화면: "옮길 수 있는 줄 n줄 (회사 m곳)" 요약과 회사별 미리보기 표(접힘), [모두 담당자로 옮기기] 하나. 폼 표(한 번만).
- 옮기는 줄 = `contacts.split_rows` 에서 이름과 휴대폰·이메일이 잡히고 같은 사람이 없는 줄 (D 의 나누기 화면이 처음부터 체크하는 줄과 같은 규칙). 유래 = 직접 입력, 만든 사람 = 누른 관리자.
- 연락처 메모 글은 바꾸지 않는다. 회사 상세의 "연락처 메모" 는 담당자 기록과 같은 사람인 줄을 접어 "담당자로 옮긴 n줄 보기" 로 숨긴다 (보이는 줄만 계산, 글은 그대로). 이 접기는 일괄 정리와 상관없이 늘 적용된다 (D 의 나누기 화면·손 입력으로 옮긴 줄도).
- 끝나면 결과 알림 "담당자 n명을 만들었어요. 남은 줄 k줄은 회사 화면에서 나눌 수 있어요."

### 5.3 ④ 명함·올리기의 변경 제안
- 올리기·명함 저장에서 사람이 `same_person` 으로 같은 사람에 걸려 건너뛸 때 ("이미 있는 담당자"), 들어온 값과 지금 값을 견준다.
  - 직함: 둘 다 있고 정규화(공백·대소문자)해 다르면 → 제안 `title`.
  - 휴대폰: 들어온 휴대폰이 있고 지금 휴대폰과 숫자가 다르면 → 제안 `phone` (지금 값이 비었어도 제안).
  - 이메일: 들어온 이메일이 지금 이메일들에 없으면 → 제안 `email`.
- 저장 결과 줄: "이정민 (이미 있는 담당자, 바뀐 정보 1건 제안)".
- **이름만 같고 휴대폰·이메일이 모두 다른 사람** (사용자 결정 2026-11-27: 제안으로 묻기): 같은 회사에 이름(공백 무시)이 같은 담당자가 있고 들어온 휴대폰·이메일이 그 사람과 하나도 맞지 않으면, 담당자를 바로 만들지 않고 제안 하나(field `person`)를 올린다: "이정민: 새 번호 010-… — [같은 사람: 정보 반영] [다른 사람: 새 담당자로 추가]". 같은 사람을 누르면 위 반영 방식대로 휴대폰·이메일·직함을 반영하고, 다른 사람을 누르면 들어온 값으로 새 담당자를 만든다 (유래 = 그 묶음). 제안에 들어온 값 전체(`new_value` JSON)를 담는다. 같은 이름이 둘 이상이면 첫 담당자 기준으로 묻는다.
- AI 제안함(`app/ai_inbox.py`)에 출처 `contact` 로 올린다: "한빛물류 · 이정민 — 직함: 차장 → 부장 (명함 11월 27일)". [반영] 은 그 칸만 바꾸고 이력이 남는다(guards), [무시] 는 닫는다. 같은 화면에 [담당자 제안 모두 반영]. 담당자 상세에도 열린 제안을 같은 단추와 함께 보인다.
- 반영할 때 지금 값이 제안 때 `old_value` 와 다르면 (그사이 사람이 고쳤으면) 반영하지 않고 "그사이 바뀌어 반영하지 않았어요" 로 닫는다.
- 담당자를 지우면 제안도 지워진다 (CASCADE).

### 5.4 ⑤ 의사결정자 접촉 공백
- `app/opportunities.py` 한 곳: 진행 중 영업기회의 담당자 중 역할 `decision` 인 사람마다 "마지막 접촉일" = 그 사람이 참석한(R53) 활동 기록의 가장 늦은 날짜(활동 날짜, 없으면 만든 날). 참석 기록이 없으면 이 영업기회에 이어진 담당자가 된 날(연결 시각을 따로 두지 않으므로 담당자 만든 날)부터 센다 (내 판단: 표를 늘리지 않는다).
- 30일(온톨로지 상수, 멈춘 건 기준과 같은 곳) 넘게 지났으면 브리핑 카드 맨 위에 한 줄: "최현수(의사결정자) 마지막 접촉 41일 전". AI 분석이 없어도 보인다 (코드 숫자).
- B 단계 AI 분석 프롬프트의 담당자 줄에 "마지막 접촉 41일 전" 을 붙인다 (이름·직함·역할과 같이, 전화·이메일 없음).
- 의사결정자가 없을 때는 아무것도 보이지 않는다.

## 6. 접근 방법 (고려한 것)
- ①: A AI 추출만 / B 코드 찾기만 / **C 둘 다** (사용자 결정). A 만이면 AI 꺼짐·직접 입력에서 연결이 안 생기고, B 만이면 새 사람·직함을 못 잡는다.
- ③: **가 숨김** / 나 메모에서 지움 / 다 그대로 (사용자 결정). 나는 파서 오인 때 글을 잃고, 다는 같은 사람이 두 번 보인다.
- ④: **제안** / 자동 반영 (사용자 결정). 자동은 "올리기는 기존 기록을 고치지 않는다" 규칙을 깨고 남의 명함으로 덮어쓸 수 있다.

## 7. 시험 (요지)
- `match_attendees`: 정확히 하나·여럿·새 사람·직원 제외·범위 밖 제외·코드 찾기(2자 이상, 공백 무시).
- AI 정리 결과 폼의 칩(미리 체크·새 사람 칩은 회사 하나일 때만), 저장 → 활동·영업기회 연결, 새 사람 만들기와 유래. 옛 `attendees` 글 모양도 받기. AI 꺼짐 직접 입력의 미리 체크.
- 올리기 활동 항목도 같은 연결.
- 일괄 정리: 관리자만, 건수·옮김·같은 사람 건너뜀·메모 글 그대로·두 번 눌러도 한 벌 (폼 표).
- 상세의 접힘: 옮긴 줄만 숨김.
- 변경 제안: 직함·휴대폰·이메일 각각, 중복 제안 없음, 반영·무시·모두 반영, 그사이 바뀌면 반영 안 함, AI 제안함 건수.
- 의사결정자 공백: 30일 경계, 참석 기록 없을 때, 프롬프트 줄, 진행 중이 아닐 때 없음.
- 레지스트리(`test_related`·`test_ontology`), `POST_NOTICES`, 사본(`KNOWLEDGE_FORMAT` 16: 활동 기록 사본의 "참석한 담당자" 줄).

## 8. 검토 뒤 정한 것 (내 판단, 2026-11-27)
- **메모 화면의 "저장"(AI 없이 바로 저장)**: 연결된 고객·파트너가 있으면 메모 글에 이름이 정확히 나온 그 회사 담당자만 자동으로 잇는다 (확인 화면이 없는 경로라 미리 체크 대신 바로 연결. 이름이 둘 이상 맞으면 잇지 않는다). 수정 화면에서 뺄 수 있다.
- **새로 만드는 고객·파트너**: "연결된 회사가 하나뿐" 을 셀 때 이 저장에서 새로 만들 회사도 센다. 저장 순서는 회사 → 담당자이고, 새 사람을 만들 때 같은 저장에서 이미 생긴 담당자(올리기 새 회사 분리 포함)와 `same_person` 으로 견줘 두 번 만들지 않는다.
- **번지는 영업기회**: 활동 기록에 직접 이어진 영업기회와 고객 니즈로 이어진 영업기회(`records.linked` 와 같은 규칙) 모두.
- **명함 가져오기의 같은 사람**: 확인 화면에서 처음부터 제외되는 같은 사람 명함도, 저장할 때 지금 값과 견줘 제안을 만든다 (담당자는 만들지 않는다). 확인 화면의 제외 글은 "같은 담당자(이정민)가 이미 있어요 — 바뀐 정보는 저장할 때 제안으로 올려요".
- **제안 반영 방식**: 직함은 바꾼다. 이메일은 지금 목록 뒤에 덧붙인다 (옛 주소를 잃지 않는다). 휴대폰은 바꾸고 옛 번호는 메모 끝에 "이전 휴대폰 010-…" 로 남긴다. `old_value` 대조는 칸 전체 글로 한다.
- **AI 제안함**: 담당자 제안도 건수(`pending_count`, 홈·사이드 배지)에 넣는다. [반영]·[무시] 는 로그인한 누구나 (담당자 고치기와 같은 권한).
- 30일 기준은 `OPPORTUNITY_QUIET_DAYS` 를 함께 쓴다.
- (계획 때) 올리기 확인 화면의 활동 항목에는 칩을 두지 않고, 저장 때 정확히 맞는 담당자만 자동으로 잇는다 (메모 "저장" 과 같은 규칙). 새 사람은 만들지 않는다. 올리기 확인 화면은 이미 항목이 많아서다. 직접 입력 새 폼도 칩 없이 같은 자동 연결이다 (글을 쓰는 중이라 미리 체크할 수 없다).
