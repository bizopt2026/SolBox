# 고객니즈 관리 (2단계) 설계

2026-11-27. 1단계 메뉴 재편(`2026-11-27-menu-regroup-design.md`) 다음 단계.

## 왜
고객 니즈는 지금 활동 기록 안의 한 줄로만 있고(칸: 고객·내용·묶인 영업기회), 모아 보는 화면이 없다. 사용자는 두 가지 일을 함께 하려 한다 (사용자 결정):
1. **고객별로 챙기기**: 니즈마다 상태를 두고 고객별로 묶어 본다.
2. **신규 BM 재료로 쓰기**: 여러 고객의 니즈를 분야로 모아 본다. 3단계(사업기획 › 신규 BM, AI)가 이 목록을 재료로 읽는다.

## 목표
- 소스 묶음에 메뉴 "고객니즈" (`/needs`): 목록·상세·추가·수정.
- 니즈마다 **상태**와 **분야**(솔루션 분야 목록을 같이 씀), 메모.
- 활동 기록 없이 **직접 추가**할 수 있다.
- 활동 기록을 지워도 관리 중인 니즈는 남는다.

## 하지 않는 것
- 같은 니즈 합치기, 니즈 전용 주제 목록, 자유 태그 (방법 B·C 는 고르지 않았다).
- 고객관리(접촉 이력) 화면 정리: 2단계 다음 작은 단계로 따로 한다.
- 지식 사본에 니즈 파일 더하기: 3단계(신규 BM AI)에서 한다. 이 단계에서 직접 입력한 니즈는 활동 기록 사본에 나오지 않는다.
- AI 가 니즈를 만들거나 고치는 일은 지금처럼 활동 기록 정리·올리기에서 "초안"으로만. 저장은 사람이 한다.

## 방법 (사용자 선택: A)
- **A (선택)**: 지금의 `customer_needs` 표를 넓힌다. 기존 연결(활동 기록 줄 저장, 영업기회 묶기, 고객 상세, 검색, 합치기, 업무 보고 건수)이 그대로 산다. 표를 한 번 다시 만드는 마이그레이션이 든다.
- B: 니즈를 독립 기록으로 두고 활동 기록과 N:M 으로 잇는다. 같은 니즈를 여러 활동에서 하나로 모을 수 있지만 활동 저장·AI 정리·올리기·영업기회·보고·사본을 모두 고쳐야 해 과하다.
- C: (분야 매기기 안) 자유 태그 — 표기가 흩어져 모아 보기가 약하다.

## 데이터 (`customer_needs` 다시 만들기)
| 칸 | 바뀌는 것 |
|---|---|
| `activity_id` | NOT NULL → 비어도 됨. 외래 키 `ON DELETE CASCADE` → `ON DELETE SET NULL` |
| `status` (새) | 문자열 코드, 기본 `new`. 저장하는 값은 `new`·`reviewing`·`hold`·`resolved` 넷 |
| `field_id` (새) | `solution_fields.id` 외래 키, 비어도 됨, `ON DELETE SET NULL` |
| `memo` (새) | 글, 기본 빈 글 |
| `created_by_id`·`updated_by_id` (새) | `users.id`, 비어도 됨 (옛 줄은 빈 값). 모델은 `Stamped` |
| 나머지 | 그대로 (`position`·`customer_name`·`customer_id`·`content`·`opportunity_id`·시각) |

- `migrate.py` 에 `rebuild_proposals_nullable_customer` 와 같은 12단계 방법으로 `rebuild_customer_needs()` 를 더한다 (DB 복사본 → 외래 키 끄기 → 새 표 → 모든 줄 그대로 옮기기 → 옛 표 지우기·이름 바꾸기 → 색인 다시 → `foreign_key_check` 로 새 위반이면 되돌림). "이미 했는가"는 표 구조(`activity_id` notnull 이 0)로 가른다. 새 DB 는 처음부터 새 모양이다.
- 옛 줄의 상태는 `new` (묶인 줄은 아래 규칙으로 "영업기회로"로 보인다).
- **병합 전에 사용자에게 알린다** (마이그레이션).

## 상태 (사용자 확정)
코드 목록 `ontology.NEED_STATUSES`: `new` 새 니즈 · `reviewing` 검토 중 · `opportunity` 영업기회로 · `hold` 보류 · `resolved` 해결됨 (이 순서). 배지 색은 `CODE_TONES`.
- **보이는 상태** = `opportunity_id` 가 있으면 `opportunity`, 없으면 저장된 `status`. 한 함수(`needs.effective_status`)와 같은 뜻의 SQL 조건 하나로만 판단한다.
- 영업기회에 묶을 때 저장된 상태가 `new` 이면 `reviewing` 으로 바꾼다. 그래서 풀리면 "검토 중"으로 돌아간다 (사용자 확정).
- 사람이 고르는 상태는 `new`·`reviewing`·`hold`·`resolved`. 묶인 동안 폼의 상태 칸은 "영업기회로 (영업기회에서 풀면 바꿀 수 있어요)"로 잠긴다.

## 분야 (사용자 선택: 솔루션 분야 같이 쓰기)
- 고르기는 솔루션과 같은 규칙: 사용 중인 분야만 새로 고를 수 있고, 사용을 끈 분야도 이미 붙은 니즈는 그대로 가진다 (`solution_fields.resolve_form` 의 일반화).
- 분야 지우기 막기(`solution_fields.delete_problem`)가 니즈 수도 센다.
- 관리 › 솔루션 분야 화면의 쓰는 수에 니즈 수를 함께 보인다.
- AI 활동 기록 정리 프롬프트(`activity_structure.md`)의 `demand_signals` 에 `field`(목록의 이름 하나 또는 빈 글)를 더하고, 활동 기록 폼의 니즈 줄에 분야 선택 칸을 둔다(AI 제안이 미리 골라져 있음). 올리기 정리(`intake_analyze`)의 니즈도 같은 칸을 받는다. 이름 → 번호는 `solution_fields.suggest_id`.

## 화면
대상 유형 `customer_need` 에 주소를 준다: 목록 `/needs`, 상세 `/needs/{id}`, 메뉴 "고객니즈", 묶음 `source` (솔루션·파트너·리서치 다음). 메뉴 아이콘 하나 더한다.

**목록** (`list_head` + `list_tools` + `list-table` + `pager`, 다른 목록과 같은 틀)
- 구분 탭: 전체(기본) · 새 니즈 · 검토 중 · 영업기회로 · 보류 · 해결됨. 탭 건수는 검색·걸러 보기 적용 뒤 (`ui.seg_tabs`).
- 묶어 보기: 없음 / 고객 / 분야 (솔루션 목록의 묶어 보기와 같은 방식, 쿠키로 기억).
- 걸러 보기: `?customer_id=`, `?field_id=`, 검색 `q` (내용·고객 이름·메모).
- 칸: 니즈(내용 첫 줄, 상세로 링크) · 고객 · 분야 · 상태 배지 · 나온 곳(활동 기록 날짜·제목 링크, 없으면 "직접 입력") · 영업기회(있으면 이름) · 만든 날.
- 정렬: 최신순(기본) / 고객 이름순.
- 제목 줄 동작: "+ 니즈 추가".

**상세** (`detail_head` + `.dgrid`)
- 왼쪽: 내용, 메모, 기본 정보(고객·분야·상태·나온 곳·영업기회).
- 오른쪽: "연결된 것"(관계 엔진: 고객 R10, 나온 활동 기록 R9, 영업기회 R26), 기록 정보.
- 제목 줄: 삭제 → 수정 → 다음 동작 하나 = 고객이 있고 영업기회가 없으면 "영업기회 만들기"(`/opportunities/new?customer_id=&need_id=`, 이미 있는 미리 채우기).

**추가·수정 폼**
- 칸: 고객(등록된 고객 선택, 직접 추가일 때 필수 — 아래 "검토에서 정한 것" 1) · 내용(필수) · 분야(선택) · 상태(새 니즈·검토 중·보류·해결됨) · 메모.
- 추가는 폼 표(`form_token`·`form_once`), 수정은 고침 표시(`rev_fields`·`check_rev`).
- 직접 추가한 니즈의 `customer_name` 은 고른 고객의 이름. 수정에서 고객을 바꾸면 `opportunities.retarget_need_customer` 로 영업기회에서 푼다.
- 활동 기록에서 나온 니즈도 이 폼에서 내용·고객을 고칠 수 있다 (같은 줄이다).
- 고객 상세의 "고객 니즈" 묶음에 "+ 니즈 추가"(`/needs/new?customer_id=`).

## 행위 규칙 (새 모듈 `app/needs.py` 한 곳)
- **손대지 않은 니즈** (`needs.is_untouched`): 저장된 상태 `new`, 영업기회 없음, 메모 빈 글. 분야는 따지지 않는다 (AI 가 채웠을 수 있다).
- **활동 기록 폼에서 줄을 지울 때** (`activity_rows.reconcile_needs`): 손대지 않은 줄은 지운다(지금처럼). 아니면 지우지 않고 `activity_id` 만 비워 고객니즈 목록에 남긴다.
- **활동 기록을 지울 때**: 같은 규칙. 손대지 않은 줄은 지우고 나머지는 남긴다 (`Activity.needs` 관계의 delete-orphan 은 이 규칙을 응용 코드에서 처리하도록 바꾼다). 확인 화면 글(`ontology.DELETE_EFFECTS`)도 고친다.
- **니즈 지우기** (`/needs/{id}/delete`, 확인 화면 `routers/confirm.py` SPECS 한 줄): 작성자 또는 관리자. 작성자가 없는 옛 줄은 나온 활동 기록의 작성자 또는 관리자. 영업기회에 묶여 있으면 묶임이 같이 사라진다.
- **영업기회 묶기** (`opportunities.bundlable_needs`·`needs_of`): 활동 기록이 없는 니즈도 나오도록 바깥 조인으로 바꾸고, 차례는 (활동 날짜 또는 만든 날) 순.
- 같은 고객 규칙·고객이 바뀌면 풀림 규칙은 그대로.
- 관계 R9 설명: "활동 기록을 지우면 손대지 않은 니즈는 지워지고 나머지는 남는다(나온 곳이 비워진다)". R9 는 이제 선택.

## 검토에서 정한 것 (설계자 판단, 사용자가 고칠 수 있음)
1. **고객이 연결 안 된 옛 니즈**: 수정 폼의 고객 칸은 직접 추가일 때만 필수다. 활동에서 나온 니즈는 비워 둘 수 있고, 칸 옆에 "쓴 이름: ○○ (등록된 고객과 연결되지 않음)"을 보인다. 고객을 고르면 `customer_name` 도 그 고객 이름으로 바꾼다 (활동 기록 폼이 같은 글을 보여 다음 저장 때 다시 풀리지 않게). 고객으로 묶어 보기·`?customer_id=` 에서 연결 안 된 줄은 "고객 미연결" 묶음으로 간다.
2. **권한**: 추가·수정은 누구나 (앱의 다른 기록과 같다). 지우기만 작성자·관리자.
3. **두 폼이 같은 줄을 쓸 때**: 니즈를 바꾸면 `guards` 가 이미 그 활동 기록의 `updated_at` 을 올리므로, 열어 둔 옛 활동 기록 폼은 저장할 때 고침 표시 충돌(409)이 난다. 니즈 수정 폼은 니즈 자신의 고침 표시를 쓴다. 따로 더할 장치는 없고, 이 두 경우를 시험으로 고정한다.
4. **지식 사본**: 형식은 바꾸지 않는다 (`KNOWLEDGE_FORMAT` 그대로). 영업기회 사본·"## 연결"에서 니즈의 나온 활동이 없으면 "직접 입력"으로 적는다. 니즈를 저장·지운 뒤에는 나온 활동 기록·묶인 영업기회·고객의 사본을 다시 쓴다 (지금 활동 기록 저장 뒤와 같은 도구).
5. **기록 칸**: `CustomerNeed` 를 `Stamped` 로 만든다 (`created_by_id`·`updated_by_id`). 작성자는 그 줄을 저장한 사람 (활동 기록 폼·올리기 저장·니즈 폼 모두). 옛 줄은 빈 값.
6. **표 다시 만들기**: 모델에서 새 표를 한 번에 만든다 (새 칸·활동 외래 키 SET NULL·분야 외래 키를 한 단계로). `opportunity_id` 는 지금처럼 외래 키 없는 번호 열로 둔다 (옛 DB 에 남은 어긋난 번호 때문에 다시 만들기가 실패할 위험을 피한다. 비우는 일은 지금처럼 `opportunities.py`).
