# 영업 CRM 보강 D 단계: 고객·파트너 담당자

작성 2026-11-26. 상태: **승인 (2026-11-26)**. 화면 시안: claude.ai 아티팩트 "솔박스 영업 D 단계 시안". 로드맵은 `2026-11-26-sales-crm-a-design.md` 2장.

## 1. 왜 하나

지금 고객·파트너의 사람 정보는 `contact` 글 한 칸에 "이름 직함 전화 이메일 (출처)" 줄로 쌓인다. 누가 의사결정자인지, 같은 사람이 두 번 들어왔는지, 그 사람이 어느 영업기회에 관여하는지 알 수 없다. Salesforce 의 Contact 처럼 **사람을 기록 단위로** 두어 역할을 표시하고, 영업기회에 잇고, 찾을 수 있게 한다.

이것은 `docs/ontology.md` 19장(2026-11-24)의 "담당자(인물) 대상 유형은 더하지 않는다, 필요해지면 다시 정한다" 를 **바꾸는 결정**이다. 같은 장의 "명함 연락처 개인 정보를 AI 로 보내지 않는다" 는 그대로 지킨다.

## 2. 정해진 것 (사용자 결정 2026-11-26)

- 담당자는 **고객·파트너 모두**에 둔다 (한 구조).
- **역할은 담당자마다 하나**: 의사결정자 · 실무자 · 영향자 · 기타 (비워 둘 수 있음).
- 기존 연락처 글은 화면의 **"담당자로 나누기"**: 코드가 줄마다 이름·직함·전화·이메일을 읽어 후보로 보여 주고 사람이 확인해 저장한다. **AI 를 쓰지 않는다.** 연락처 글은 "연락처 메모" 로 그대로 남는다.
- 올리기·명함 가져오기에서 **사람 이름이 있는 연락처는 담당자 기록만 만든다** (연락처 글에는 덧붙이지 않는다). 이름이 없는 연락처(대표번호 등)는 지금처럼 글에 덧붙인다. 같은 회사에 같은 휴대폰·이메일 담당자가 있으면 건너뛴다.

## 3. 목표 · 하지 않을 것 · 실패로 볼 것

목표
- 고객·파트너 상세에 담당자 카드(이름·직함·역할·전화·이메일·메모), 담당자 추가·고치기·지우기.
- 영업기회에 담당자 잇기(그 고객의 담당자 중에서 고르기), 상세에 역할 배지와 함께.
- 전체 검색에서 담당자 이름·이메일·전화로 찾기, 담당자 상세(어느 회사·이어진 영업기회).
- 올리기·명함 가져오기가 담당자 기록을 만든다 (추가만 하는 규칙 유지).
- 합치기(고객·파트너)에서 담당자도 옮긴다.

하지 않을 것
- 담당자 목록 메뉴(전체 사람 목록) — 회사 상세와 검색으로 찾는다.
- 활동 기록에 담당자 연결, AI 가 회의 메모에서 사람을 찾아 잇기 (다음에).
- 담당자 중복 정리 화면, 퇴사·이직 이력.
- 영업기회마다 다른 역할 (사용자 결정: 담당자에 하나).

실패로 볼 것
- 같은 사람이 계속 두 번 생기는 것 → 같은 사람 판단 (`app/contacts.py` 한 곳, 내 판단): 같은 회사 안에서 휴대폰 숫자가 같거나 이메일(소문자)이 같으면 같은 사람. 새 담당자에 휴대폰·이메일이 둘 다 없으면 이름(공백 무시)이 같은 담당자를 같은 사람으로 본다. 올리기·명함은 저장할 때 건너뛰고("이미 있는 담당자"), 명함 확인 화면의 처음 제외 표시도 이 규칙으로 담당자 기록과 견준다. 손으로 만들 때는 경고 후 [그래도 저장]. 나누기 화면은 "이미 있음" 으로 처음부터 넣지 않음.
- 연락처 글을 나누다가 원래 글을 잃는 것 → 연락처 글은 건드리지 않는다.

## 4. 데이터 (DB 변경: 병합 전 사용자에게 알린다)

### 4.1 새 표 `contacts` (Stamped, Origin)
| 칸 | 뜻 |
|---|---|
| customer_id · partner_id (FK CASCADE, 정확히 하나) | 속한 회사 |
| name (필수) · title(직함, 부서 포함 한 줄) · role(코드, 빈 값 가능) | |
| phone(휴대폰) · office_phone(사무실) · email · note | |
| origin_type · origin_id | 유래 (직접 입력·올리기·파일 가져오기·나누기는 직접 입력) |

역할 코드 `ontology.CONTACT_ROLES = {"decision": "의사결정자", "user": "실무자", "influencer": "영향자", "other": "기타"}`.

### 4.2 새 연결 표 `opportunity_contacts` (opportunity_id, contact_id, CASCADE)
같은 고객의 담당자만 (응용 규칙, `opportunities.py`). 영업기회의 고객을 바꾸면 다른 고객의 담당자 연결은 푼다.

### 4.3 온톨로지
- 새 대상 유형 `contact` ("담당자", 핵심 아님·부속, 주소 `/contacts/{id}`, 메뉴 없음, 사본 없음: 회사 사본에 줄로).
- 관계: 담당자 → 고객 (N:1 fk), 담당자 → 파트너 (N:1 fk), 영업기회 ↔ 담당자 (N:M link). `VIEW_LABELS`·`LIST_FILTERS` 등 등록 규칙(CLAUDE.md "온톨로지" ①~④)대로.
- 합치기(`merge._move`·`link_counts`)에 `contacts.customer_id`·`contacts.partner_id` 를 더하고 `tests/test_beta_ae.py` 의 외래 키 목록을 고친다.

## 5. 동작

### 5.1 회사 상세의 담당자 카드
- 고객·파트너 상세 왼쪽 위쪽에 "담당자 n" 카드: 줄마다 이름(담당자 상세 링크) · 직함 · 역할 배지 · 휴대폰 · 이메일, 오른쪽 [고치기]. 카드 머리 [+ 담당자].
- 연락처 글(`contact`)은 이름표를 "연락처 메모" 로 바꿔 그대로 보인다. 글에 이름이 잡히고 아직 담당자 기록에 없는(위 같은 사람 규칙) 줄이 하나라도 있으면 "연락처 메모를 담당자로 나누기 (n줄)" 링크 (내 판단: 따로 저장하지 않고 볼 때마다 계산한다).
- 담당자 폼(`/contacts/new?customer_id=|partner_id=`, `/contacts/{id}/edit`): 이름(필수)·직함·역할·휴대폰·사무실 전화·이메일·메모. 만들기는 폼 표, 고치기는 고침 표시. 같은 회사에 같은 휴대폰·이메일이 있으면 "같은 사람일 수 있어요: ○○" 경고 후 [그래도 저장] (기존 `duplicate_warning` 방식).
- 지우기: 확인 화면(`SPECS`), 영업기회 연결만 풀린다.
- 담당자 상세 `/contacts/{id}`: 회사 링크, 칸들, 이어진 영업기회, 유래·기록 정보.

### 5.2 연락처 메모를 담당자로 나누기 (`/customers/{id}/contacts/split`, `/partners/{id}/contacts/split`)
- `app/contact_split.py` 가 연락처 글을 줄마다 읽는다: 이메일(정규식), 전화(휴대폰 010·011…, 그 밖의 번호는 사무실), 끝의 `(…)` 출처 꼬리는 메모로, 남은 글의 첫 낱말이 한글 2~4자 또는 영문 이름이면 이름, 나머지는 직함. 이름을 못 찾은 줄도 후보로 보이되 처음부터 "넣지 않음".
- 화면: 후보마다 체크(넣기) + 칸(이름·직함·역할·휴대폰·사무실·이메일·메모)을 고칠 수 있는 표. 이미 같은 휴대폰·이메일 담당자가 있는 줄은 "이미 있음" 으로 처음부터 넣지 않음.
- 저장(폼 표): 체크한 줄만 담당자로 만든다. 연락처 글은 바꾸지 않는다.

### 5.3 영업기회와 담당자
- 영업기회 폼 "연결" 구역에 "담당자" 고르기(그 고객의 담당자, 이름 · 직함 · 역할).
- 상세 기본 정보에 "담당자: 김부장(의사결정자) · 이대리(실무자)". 보드·목록에는 넣지 않는다.
- B 단계 AI 분석 프롬프트의 영업기회 칸에 이어진 담당자의 이름·직함·역할을 넣는다 (이미 고객 기록에 있는 정보라 새로 보내는 개인 정보가 아니다; 전화·이메일은 넣지 않는다).

### 5.4 올리기·명함 가져오기
- 회사의 옛 연락처 글에 같은 사람 줄이 있어도 담당자 기록이 없으면 담당자 기록을 만든다 (내 판단: 사람을 기록으로 옮기는 것이 목적이다. 그 줄은 이후 나누기 화면에서 "이미 있음" 으로 보인다).
- 정리안 항목 `add_contact` 의 `person` 이 있으면 저장할 때 그 회사에 담당자 기록을 만든다 (이름·직함(role 칸)·휴대폰/사무실(전화 칸을 나눔)·이메일·메모, 유래 = 그 묶음). 같은 회사에 같은 휴대폰 숫자·이메일 담당자가 있으면 건너뛴다 ("이미 있는 담당자"). `person` 이 없으면 지금처럼 연락처 글에 덧붙인다.
- 새 회사 항목(`new_customer`·`new_partner`, 명함이든 AI 정리든)은 저장할 때 그 항목의 (사람이 확인 화면에서 고쳤을 수도 있는) 연락처 글을 `contact_split` 파서로 다시 읽어, 이름이 잡힌 줄은 담당자 기록으로 만들고 새 회사의 연락처 글에서는 뺀다. 이름이 없는 줄만 새 회사의 연락처 메모로 남는다 (내 판단: 정리안 형식을 바꾸지 않아 옛 정리안도 그대로 저장된다).
- 주소·팩스·집 전화처럼 담당자 칸이 없는 값은 담당자 메모에 "주소: …" 처럼 붙인다 (내 판단: DB 칸을 늘리지 않는다).
- 확인 화면의 문구 "연락처 추가" 는 그대로 두고, 저장 결과 줄에 "담당자 n명 추가" 를 더한다.
- AI 정리 프롬프트는 바꾸지 않는다 (지금도 사람·직함·전화·이메일 칸을 낸다).

### 5.5 검색·사본·지우기
- 전체 검색 `FIELDS` 에 담당자(name, title, email, phone, office_phone, note) — 결과 줄에 회사 이름.
- 회사 지식 사본에 "## 담당자" 구역 (이름 · 직함 · 역할 · 휴대폰 · 이메일) — `KNOWLEDGE_FORMAT` 14. 담당자 자체 사본은 없다.
- 고객·파트너를 지우면 그 담당자도 지워진다 (`DELETE_EFFECTS` 글에 적는다).

## 6. 접근 방법 (고려한 것)
- **역할 자리**: (가) 담당자에 하나 / (나) 영업기회 연결마다. → (가) (사용자 결정).
- **회사 연결**: (가) 고객·파트너 칸 둘 중 하나 / (나) 회사 종류+번호 한 쌍. → (가). 외래 키로 지우기·합치기를 데이터베이스가 지킨다.
- **나누기**: (가) 코드 규칙 + 사람 확인 / (나) AI. → (가) (사용자 결정, 개인 정보).

## 7. 시험 (요지)
- 모델·관계 레지스트리(`test_related`·`test_ontology`), 합치기 외래 키 목록.
- 담당자 폼(만들기·고치기·충돌·같은 사람 경고·지우기 확인), 회사 상세 카드, 담당자 상세.
- 나누기 파서 표(여러 줄 모양: 이름 직함 휴대폰 이메일 (출처) / 이름만 / 번호만 / 영문 이름), 화면 저장(체크한 줄만, 이미 있음 건너뜀).
- 올리기·명함 저장이 담당자를 만들고 글에는 덧붙이지 않음, 이름 없는 연락처는 글, 같은 사람 건너뜀, 유래.
- 영업기회 담당자 잇기(다른 고객 담당자 거절, 고객 바꾸면 풀림), 검색, 사본, 옛 DB 이관.
