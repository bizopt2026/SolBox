# 팀 업무 보고 (일·주·월 실적 + 다음 계획) 설계

작성 2026-11-25. 상태: 검토자 질문 반영, 사용자 승인 대기.

## 1. 무엇을, 왜

팀이 윗선에 올리는 **내부 업무 보고서**를 솔박스 안에서 만든다. 보고 단위는 일·주·월 중 하나다.

- **실적**: 그 기간에 팀 전체가 솔박스에 남긴 기록(활동 기록·후속 조치·고객 니즈·영업기회·제안 건·새 솔루션·고객)을 모은다. 작성자는 따지지 않는다 (팀 보고).
- **지난 계획 점검**: 지난 보고에서 확정한 계획 항목마다 "완료 / 진행 중 / 미착수 / 취소"를 표시한 표.
- **다음 계획**: Claude CLI 가 실적과 지난 계획 점검을 보고 다음 기간(같은 단위: 일→다음 날, 주→다음 주, 월→다음 달) 계획 초안을 내고, 보고를 만드는 사람과 대화로 방향을 다듬은 뒤 확정한다. 확정한 계획은 **항목별로 저장**되어 다음 보고의 "지난 계획 점검"이 된다.
- **파일**: 같은 내용을 PPT·워드(docx)·MD 중 골라 받는다.

왜: 팀 실적 보고를 손으로 모아 쓰는 시간을 줄이고, 계획 → 실적 → 다음 계획이 끊기지 않게 한다 (지난 계획을 지켰는지가 보고서에 자동으로 남는다).

## 2. 목표 / 비목표 / 실패 기준

목표
- 일·주·월 보고 건을 만들고, 실적 집계는 코드로 정확하게 낸다 (숫자는 DB 에서 바로).
- 지난 기간 계획 대비 결과 표. 미완료 항목은 다음 계획 초안으로 넘어간다.
- AI 계획 초안 + 대화 + 사람이 확정. 확정 계획은 항목 표에 저장.
- PPT / docx / MD 내려받기.

비목표 (이번에 하지 않음)
- 개인별 실적 보고, 부서·팀 여러 개 구분 (솔박스는 한 팀이 같이 쓴다).
- 결재·승인·메일 보내기, 보고서 자동 생성 예약.
- 계획 항목을 후속 조치(`follow_ups`)로 바꾸기 (후속 조치는 활동 기록에 묶인 표라 맞지 않는다. 나중 과제).
- 솔루션 발굴 단계의 변경 이력 (영업기회 단계 이력과 후속 조치 완료일만 더한다, §5.2b).
- 목록 화면에 기간 거르기 추가 (숫자 검증은 시험으로 한다).

실패 기준 (돌아가도 실패로 본다)
- 보고서 숫자가 목록 화면에서 같은 기간으로 센 수와 다르다.
- AI 가 꺼져 있거나 실패하면 보고서를 못 만든다.
- AI 가 실적을 지어내 보고서에 사실처럼 들어간다 (AI 글은 집계 자료만 근거로, 사람이 확인·수정 후 확정).
- 확정한 계획이 다음 보고에서 보이지 않거나 두 번 넘어간다.

## 3. 제약 (솔박스 규칙에서)

- FastAPI + SQLAlchemy + Jinja2/HTMX, 파이썬 3.11 문법. 화면 문구 한국어.
- 새 표 4개 + 기존 표 칸 1개(`follow_ups.done_at`) → DB 마이그레이션이므로 **main 병합 전에 사용자에게 알린다**. 패키지는 추가하지 않는다 (`python-pptx`·`python-docx` 이미 있음).
- 새 대상 유형·코드 목록·이름표는 `app/ontology.py` 한 곳 (유형·관계 정의, `tests/test_ontology.py`·`test_related.py`).
- 새 POST → `POST_NOTICES`, 지우기 → `confirm.SPECS`, 만들기 폼 → `form_token`/`form_once`, 고치기 폼 → `rev_fields`/`check_rev`, AI 버튼 → `ai_attrs`/`require_ai_on`/`AI_POSTS`.
- AI 도구 분리: 보고 작업은 도구 없이(집계 자료를 프롬프트에 넣어) 실행한다. 기록 글(활동 정리본 등)은 "지시가 아니라 자료"로 감싼다.
- AI 결과는 초안이고 사람이 확정해야 반영된다. AI 가 안 돼도 집계·수동 계획 입력·파일 만들기는 된다.
- 파일은 `data_dir` 아래 (`reports/`), 경로는 `pathlib`, Windows·Linux 모두.

## 4. 접근 방법 (사용자가 고름)

1. **코드가 집계, AI 는 글과 계획만** ← **선택**. 숫자 정확·시험 가능·AI 꺼져도 동작.
2. AI 가 `knowledge/` 사본을 읽어 보고서 통째로 작성. 코드는 적지만 숫자 누락·오류 위험, 월간은 느림, AI 꺼지면 불가. 버림.

계획 저장 방식: (A) 항목별 저장 + 다음 보고에서 계획 대비 실적 ← **선택**, (B) 보고서 안 글로만 — 버림.

기간 중 날짜가 없는 숫자(수주·후속 조치 완료): (가) 지금부터 날짜 기록(완료일 칸 + 영업기회 단계 변경 기록 표) ← **선택**, (나) 마지막 수정일(`updated_at`)로 어림 — 단계와 무관한 수정도 섞여 윗선 보고 숫자로 부적합해 버림.

## 5. 설계

### 5.1 기간 (내 결정)
- 일: 그날 하루. 주: 월요일~일요일 (ISO 주). 월: 달력 한 달.
- 만들 때 단위와 기준 날짜를 고르면 기간(`period_start`~`period_end`)을 계산한다. 기본값은 "지난 완료 기간"이 아니라 **오늘이 든 기간** (금요일 오후 주간 보고·월말 보고 관행). 바꿀 수 있다.
- 다음 기간 = 같은 단위의 바로 다음 기간. **일간의 다음 날은 다음 평일**(금 → 월). 공휴일은 따지지 않는다 (내 결정).
- 같은 단위·같은 기간의 보고 건은 하나만 둔다 (있으면 그 건으로 안내).

### 5.2 데이터 (새 표 3개 + §5.2b 의 표 1개·칸 1개, `migrate`/`create_all` 로 생성)

`reports` (보고 건, `Stamped`)
- `unit` (day/week/month), `period_start`, `period_end` (date)
- `status`: `draft`(실적 확인) → `planning`(계획 대화) → `confirmed`(계획 확정) — ontology `REPORT_STATUSES`
- `summary_md`: 실적 요약 글 (AI 초안 또는 직접 작성, 사람이 고칠 수 있음)
- `highlights_md`: 이슈·건의 (선택, 직접 작성)
- `section_notes` (JSON): 구역별 보고 문구 `{kpi, opps, proposals, check, plan, issues: [문장 1~2개]}` (§5.6a). AI 초안 또는 기본 문장, 사람이 고칠 수 있다. 확정 때 스냅숏과 함께 고정.
- `snapshot` (JSON): 확정 시점의 집계 결과 (확정 뒤 기록이 바뀌어도 보고서 숫자가 그대로 남게). 확정 전에는 화면을 열 때마다 새로 집계.
- `active_job_id`, `chat_from_id` (제안 건과 같은 쓰임)
- `file_names` (JSON: 형식 → 마지막으로 만든 파일 이름), `files_built_at`

`report_messages` (계획 대화): `report_id`, `role`, `content`, `created_at` — `ProposalMessage` 와 같은 모양.

`report_plan_items` (계획 항목)
- `report_id` (이 계획을 **세운** 보고), `position`, `task`(글), `owner`(담당, 쓴 그대로), `due`(date, 선택), `note`
- 연결(선택): `customer_id`, `opportunity_id`, `project_id` — 대화 중 AI 가 이름으로 제안하면 `activity_rows.LinkIndex` 의 정확히 하나 일치 규칙으로만 잇는다.
- `result`: 다음 보고에서 점검한 결과 `done/doing/todo/dropped` (빈 값 = 아직 점검 안 함), `result_note`, `checked_in_report_id`
- `carried_from_id`: 지난 계획에서 넘어온 항목이면 원래 항목 번호 (두 번 넘기지 않기 위한 표시).

### 5.2b 날짜 기록 (선택 가, 지금부터)
- `follow_ups.done_at` (datetime, null): `done` 이 거짓→참이 될 때 지금 시각, 참→거짓이면 비움. `done` 을 바꾸는 곳이 여러 군데(`activity_rows`, `routers/activities.py` 토글, `relations.py` 합치기, 올리기 저장)라 **`guards` 의 flush 처리기 한 곳**에서 속성 변경 이력을 보고 채운다. 합치기로 옮길 때는 원래 `done_at` 을 그대로 가져간다.
- 새 표 `opportunity_stage_changes`: `opportunity_id`, `from_stage`(만들 때는 빈 값), `to_stage`, `changed_at`, `changed_by_id`. 영업기회를 만들 때와 `stage` 가 바뀔 때 같은 flush 처리기에서 한 줄 넣는다 (`idmarks` 의 번호 정하기보다 먼저 세션에 더해지도록 처리기 순서를 지킨다). 영업기회를 지우면 함께 지운다.
- 기존 기록: 시작 때 채우지 않는다. 이미 완료된 후속 조치는 `done_at` 이 비고, 기존 영업기회는 이력이 없다. 보고서는 이런 기록을 기간 숫자에 넣지 않고, 해당 건이 있으면 "기능 도입(날짜) 전 기록은 완료·단계 변경 날짜를 몰라 빠졌다" 안내 한 줄을 단다.

### 5.3 실적 집계 (`app/reports.py`, 순수 함수 + 시험)

기간 [start, end] 기준. 날짜 기준은 활동 기록은 `Activity.date`(없으면 `created_at`), 나머지는 `created_at`/`updated_at`.

| 구역 | 내용 |
|---|---|
| 요약 숫자 | 활동 기록 수(종류별), 새 고객 니즈 수, 새 영업기회 수, 기간 중 수주(`won` 으로 바뀐 단계 변경 기록) 수, 새 제안 건 수·제안서 만든 건 수(`deck_built_at`), 새 솔루션·고객·파트너 수, 후속 조치 완료 수(`done_at`), 기한 지남 수(**기간 마지막 날 기준**: `due` < 기간 끝이고 기간 끝까지 완료되지 않음 — 다시 열어도 같은 값) |
| 주요 활동 | 기간 활동 기록 목록 (날짜·종류·제목·고객·정리본 첫 줄). 월간은 고객별로 묶어 상위 N건 + "외 n건" |
| 영업기회 | 기간 중 단계가 바뀐 영업기회 (이전 → 이후, 단계 변경 기록 기준) + 기간 중 새로 생긴 것 |
| 제안 | 기간 중 만들거나 진행한 제안 건과 현재 단계 |
| 후속 조치 | 기간 중 완료한 것, 기한이 지났는데 안 된 것 (다음 계획 재료) |
| 지난 계획 점검 | **같은 단위에서 이 기간보다 앞서는 가장 최근 확정 보고**의 계획 항목과 그 점검 결과 (기간을 건너뛰어도 끊기지 않는다. 그 보고의 항목을 이미 다른 보고가 점검했으면 그 보고는 건너뛴다) |

질의 수는 기록 수와 무관하게 유지한다 (홈·검색과 같은 원칙).

### 5.4 화면 흐름 (제안 화면과 같은 틀)

메뉴: 사이드 메뉴 "관리" 묶음 위 또는 "오늘" 묶음에 **"업무 보고"** (`/reports`). 목록은 공통 목록 틀 (단위 구분 탭: 전체/일/주/월).

`/reports/new`: 단위 + 기준 날짜 → 만들기 (폼 표).

`/reports/{id}` 상세 — 단계 띠 4칸:
0. 단계 순서는 강제하지 않는다: 점검을 다 하지 않아도 계획 초안을 만들 수 있다.
1. **실적** — 집계 구역들을 보여 줌. "AI 요약 쓰기" 버튼(요약 글 초안) + 요약 글 직접 고치기 (고침 표시).
2. **지난 계획 점검** — 앞 보고 계획 항목마다 결과 선택(완료/진행 중/미착수/취소) + 한 줄 메모. 앞 보고가 없으면 "처음 보고" 안내로 건너뜀.
3. **다음 계획** — "AI 계획 초안" 버튼 → 계획 항목 초안(미완료 지난 항목은 넘어온 표시와 함께 맨 앞) + 대화창(제안 대화처럼 답이 나오는 대로 보임). 대화 답마다 AI 는 고친 계획 항목 목록을 함께 돌려주고, 화면의 계획 항목 편집 표가 그 초안으로 바뀐다(사용자가 "이 초안 쓰기"를 눌러야 반영). 항목 표는 직접 추가·수정·삭제 가능. 넘어오는 대상은 결과가 **미착수·진행 중·아직 점검 안 함**인 항목이다 (완료·취소는 넘기지 않는다). 확정 전에는 점검 결과를 바꾸면 넘어온 항목을 다시 맞춘다 (새로 완료·취소가 된 항목에서 넘어온 줄은 빼고, 새로 미완료가 된 것은 더한다; 사용자가 고친 넘어온 줄도 빠진다는 점을 화면에 알린다). 한 항목은 한 번만 넘어간다 (`carried_from_id` 유일).
4. **확정·파일** — "계획 확정" (스냅숏 저장, 상태 `confirmed`) → 형식 고르기(PPT / 워드 / MD) → 만들기·내려받기. 확정 뒤에도 "확정 풀기"로 고칠 수 있다(다음 기간 보고가 아직 점검하지 않았을 때만).

### 5.4b 권한·동시 수정 (내 결정)
- 팀원 누구나(관리자 구분 없음) 보고 건 만들기·고치기·확정·확정 풀기·지우기를 할 수 있다.
- 요약 글·이슈·계획 항목 표·점검 표는 모두 고치기 폼이라 고침 표시(`rev_fields`/`check_rev`)를 단다. 계획 항목·점검 결과를 바꾸면 보고 건의 `updated_at` 도 올린다(`guards` 처리기). 만들기·확정·AI 버튼은 폼 표/AI 규칙을 따른다.

### 5.4c 연결된 기록을 지우거나 합칠 때 (내 결정)
- 계획 항목의 고객·영업기회·프로젝트를 지우면 그 연결만 비운다 (항목 글은 남는다). 합치면(`merge.py`) 남는 쪽으로 옮긴다. 지우기 영향 안내(`ontology.DELETE_EFFECTS`·`impact`)에 "업무 보고 계획 항목 연결 n건이 비워진다"를 더한다.
- 확정한 보고의 스냅숏 안 이름은 고치지 않는다 (그때의 보고 그대로).

### 5.6a 구역별 보고 문구 (사용자 요청 2026-11-25)
워드·MD 보고서는 표만 두지 않는다. **표가 있는 구역마다 그 표를 풀어 쓴 보고 문구 1~2줄**을 소제목 바로 아래, 표 위에 둔다 (워드는 `○` 글머리, MD 는 일반 문단).
- 대상 구역: 요약 숫자, 영업기회 단계 변화, 제안 진행, 지난 계획 점검, 다음 계획, 이슈·건의.
- 글은 해석이 담긴 보고 말투다 (예: "지난주 계획 6건 중 4건을 완료했습니다(67%). 미완료 2건은 다음 주 계획으로 넘깁니다."). 숫자는 집계 값과 같아야 한다.
- 만드는 길: AI 작업 `report_notes` 가 집계 + 점검 결과 + 확정 계획을 보고 구역별 1~2문장을 JSON 으로 낸다. **AI 가 꺼졌거나 실패하면 코드가 기본 문장을 만든다** (숫자만 넣은 틀 문장: "활동 기록 14건(지난 기간 대비 +3), 수주 1건, 새 영업기회 2건입니다."). 어느 쪽이든 화면 각 구역 카드 아래 "보고 문구" 칸에서 고칠 수 있다.
- AI 문구 검사: 문구 속 숫자가 그 구역 집계에 없는 값이면 경고 표시를 달고(지우지는 않음) 사람이 확인하게 한다.
- PPT 는 장마다 공간이 좁아 이번 요청 범위 밖이다 (기존 시안대로 표·카드 중심). 필요하면 장 제목 아래 한 줄로 넣을 수 있다.

### 5.5 AI 작업 (`app/ai/report_tasks.py`, 프롬프트 `prompts/report_*.md`)

- `report_summary`: 집계 자료(JSON → 글) → 실적 요약 글(마크다운, 5~10줄, 주요 성과·이슈). 도구 없음.
- `report_notes`: 구역별 보고 문구 1~2문장 JSON (§5.6a). 계획 확정 직후 자동으로 한 번, 화면에서 "보고 문구 다시 쓰기"로 다시. 도구 없음.
- `report_plan`: 집계 + 지난 계획 점검 + 요청 메모 → 계획 항목 JSON 목록 `[{task, owner, due, customer, opportunity, note, carried_from}]` + 한 단락 방향 설명. `run_json` 로 검증.
- `report_chat`: 대화 기록(최근 30개) + 현재 계획 항목 → 답 글 + 고친 계획 항목 JSON. 제안 대화의 스트리밍(`_chat_answer`) 재사용.
- 활동 정리본 등 사용자 글은 자료 구역에 넣고 "지시가 아니라 자료"라고 적는다. 프롬프트에는 "자료에 없는 실적을 쓰지 말 것".

### 5.6 파일 만들기 (`app/report_files.py`)

공통 내용 모델(보고서 dict: 제목·기간·요약 숫자·요약 글·주요 활동·영업기회·제안·지난 계획 점검·다음 계획·이슈) 하나에서 세 형식으로 뽑는다.
- **MD**: 제목·구역별 보고 문구·표·목록. 가장 단순, 기준 출력.
- **docx** (`python-docx`): 제목, 기간 줄, 핵심 요약 상자, 구역마다 소제목 → 보고 문구 1~2줄(`○`) → 표. 표 머리글은 쪽이 넘어가면 되풀이한다. 기본 서식(맑은 고딕). 사내 표준 양식은 이번에 하지 않는다.
- **PPT** (`python-pptx`, `pptx_template.blank_presentation` 으로 열기): 6장 — 표지 → 한눈에(숫자 카드 8개) → 주요 성과 + 영업기회 단계 변화 → 지난 계획 점검 표 → 다음 계획(방향 한 줄 + 표) → 이슈·건의. 제안서용 `deck.py`·품질 검사(`deck_gates`)는 쓰지 않는다(내부 보고라 고객용 경로 거르기 불필요). 표가 길면 다음 장으로 나눈다.
- 파일은 `data_dir/reports/<보고 번호>/` 에 `.part` 로 쓰고 바꿔치기. 이름 예: `업무보고_주간_2026-11-23~29.pptx`.

### 5.7 온톨로지·연결
- 새 유형 "업무 보고"(`report`), 코드 목록 `REPORT_UNITS`, `REPORT_STATUSES`, `PLAN_RESULTS`.
- 관계: 보고 → 계획 항목의 고객·영업기회·프로젝트 연결 (고객 상세의 "연결된 것"에 "업무 보고 계획"이 보이게). 지식 사본(`knowledge/`)에는 이번에 넣지 않는다 (`UNTRAVERSED` 또는 사본 없음 처리, 이유 적기).

## 5.8 시안
화면 시안 5장(목록·실적·지난 계획 점검·다음 계획+대화·확정·파일)과 결과물 견본(PPT 6장·워드 A4·MD)을 2026-11-25 사용자에게 보였다. 시안 데이터는 예시.

## 6. 알려진 한계
- 기능 도입 전에 완료된 후속 조치·바뀐 영업기회 단계는 날짜를 몰라 기간 숫자에서 빠진다 (안내 한 줄로 알린다).
- 솔루션 발굴 단계는 이력이 없어 "기간 중 새로 등록한 솔루션" 수만 센다.
- 일간의 "다음 평일"은 공휴일을 모른다.

## 7. 만드는 사람에게 맡김
- 집계 구역의 세부 표 모양·월간 묶음 상위 N 값, PPT/docx 디자인 세부(색은 `docs/디자인컨셉.md` 토큰을 따름).
- 프롬프트 문구, 대화 답의 JSON 모양 검증 세부.
- 시험 구성 (집계 숫자는 같은 조건으로 따로 센 질의와 비교하는 시험 필수, `done_at`·단계 변경 기록이 모든 변경 경로(폼·토글·합치기·올리기·영업기회 수주 전환)에서 남는지 시험 필수, 세 형식 파일이 열리는지 시험 필수).
- 문서 갱신: `docs/화면구성도.md`, `help.html`, `docs/ontology.md`, `docs/rules/` 에 새 영역 파일 "업무-보고.md".
