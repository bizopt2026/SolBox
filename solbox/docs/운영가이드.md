# 솔박스 운영 가이드

처음에는 담당자의 PC(예: 10.231.0.5)에서 운영해 보고, 충분히 써 본 뒤에 서버 PC(예: 10.231.1.254)로 옮기는 순서를 기준으로 쓴 문서입니다. 아래의 주소와 포트는 예시입니다. 실제 값은 `config.toml` 과 명령 인자로 정하며, 코드에는 주소가 들어 있지 않습니다.

> **Windows 실행 확인 필요:** `scripts` 폴더의 PowerShell 스크립트 3개(`run_server.ps1`, `install_autostart.ps1`, `open_firewall.ps1`)는 Linux에서 작성되어 Windows에서 실행해 보지 못했습니다. 처음 실행할 때 내용을 읽어 보고, 오류가 나면 알려 주세요.

PowerShell 명령은 한 줄씩 따로 실행합니다. 이 저장소(bizopt2026)는 앱마다 폴더를 나눠 관리하고, 솔박스는 `solbox` 폴더에 있습니다. 아래 명령은 모두 **앱 폴더**(예: `C:\bizopt2026\solbox`)에서 실행한다고 가정합니다.

> **실행 정책:** Windows 10/11 PC는 기본 설정(Restricted)에서 `.ps1` 스크립트 실행을 막습니다. 그래서 이 문서의 스크립트는 모두 `powershell -ExecutionPolicy Bypass -File .\scripts\<이름>.ps1 <인자>` 형태로 실행합니다. 이 옵션은 그 한 번의 실행에만 적용되고 PC 설정은 바꾸지 않습니다.

## 1. 준비물

- Python 3.11 이상 (설치할 때 "Add python.exe to PATH" 체크)
- Claude CLI: 설치한 뒤 **앱을 실행할 Windows 계정으로** 한 번 로그인합니다. 다른 계정이나 다른 PC에서 로그인한 것은 소용없습니다.
- Git (코드 받기·업데이트용). 없으면 저장소의 zip 파일을 내려받아 풀어도 됩니다.

확인:

```powershell
python --version
```

```powershell
claude --version
```

## 3. 설정 파일 (config.toml)

```powershell
copy config.example.toml config.toml
```

이미 `config.toml` 이 있으면(`Test-Path config.toml` 이 `True`) 복사하지 마세요. 덮어써서 `secret_key` 와 `data_dir` 를 잃습니다. 기존 파일을 그대로 쓰고 아래 표의 항목만 확인합니다.

메모장으로 `config.toml` 을 열어 고칩니다. 설정 파일은 저장소에 올리지 않습니다.

| 설정 | 설명 |
| --- | --- |
| `secret_key` | 길고 무작위한 값. `python -c "import secrets; print(secrets.token_urlsafe(32))"` 로 만듭니다. `change-me` 면 시작되지 않습니다. |
| `data_dir` | 데이터 폴더. Windows 경로는 `C:/solbox/data` 처럼 `/` 로 씁니다. |
| `host` | 나만 쓰면 `127.0.0.1`. **다른 직원이 접속하게 하려면 `0.0.0.0`** |
| `port` | 기본 8443. 다른 프로그램과 겹치면 바꿉니다. |
| `ssl_certfile`, `ssl_keyfile` | 인증서와 키 경로 (4번에서 만듭니다). 둘 다 적으면 HTTPS 입니다. |
| `backup_dir` | 백업 폴더. 생략하면 `data_dir` 옆의 `backups`. |
| `ai_concurrency` | AI 작업 동시 처리 개수 (기본 1). 음성 받아쓰기를 쓰면 12번의 "워커 수" 안내를 읽으세요. |
| `transcriber` | 음성 받아쓰기 엔진. `none`(사용 안 함, 기본) 또는 `faster-whisper`. 다른 값이면 서버가 시작되지 않습니다. 켜는 법은 12번. |
| `transcribe_model`, `transcribe_language`, `transcribe_threads`, `transcribe_max_minutes` | 받아쓰기 모델 크기·언어·CPU 스레드 수·최대 길이(분). 12번 참고. 잘못된 값이면 서버가 시작되지 않고 이유가 나옵니다. |

설정을 마친 뒤 점검합니다 (서버를 멈춘 상태에서 실행. 서버가 켜져 있으면 포트 줄이 "문제"로 나오는 것이 정상입니다).

```powershell
python -m app.cli check
```

점검이 끝나면 관리자 계정을 한 번 만듭니다. 비밀번호는 입력창에서 두 번 받으므로 **사람이 직접 터미널에서** 실행합니다. 비밀번호를 명령줄(`--password`)이나 파일에 적지 않습니다. 설정 파일이 먼저 있어야 하므로 반드시 이 순서입니다.

```powershell
python -m app.cli create-admin --username admin --name 관리자
```

## 4. HTTPS 인증서

다른 직원이 접속하게 하려면 접속 주소(IP 또는 이름)를 넣어 인증서를 만듭니다. 로컬 PC 예시:

```powershell
python -m app.cli make-cert --host 10.231.0.5
```

이름으로도 접속하게 하려면 `--host` 를 여러 번 씁니다. 첫 항목이 대표 이름입니다.

```powershell
python -m app.cli make-cert --host 10.231.0.5 --host solbox.local
```

명령이 출력한 두 줄(`ssl_certfile`, `ssl_keyfile`)을 `config.toml` 에 붙여 넣습니다. 인증서는 `certs\` 폴더에 만들어지고 유효기간은 10년입니다. 접속 주소가 바뀌면(서버로 이관 등) 새 주소로 `--overwrite` 를 붙여 다시 만들고 서버를 재시작합니다.

자체 서명 인증서라서 직원 PC 브라우저에 처음에는 경고가 나옵니다. 둘 중 하나를 고릅니다.

- **경고 넘기기:** 브라우저의 "고급" → "계속 진행". 간단하지만 PC·브라우저마다 반복됩니다.
- **인증서 신뢰 등록(권장):** `certs\server.crt` 를 직원 PC로 복사해 관리자 권한 PowerShell 에서 실행하면 경고가 사라집니다.

```powershell
Import-Certificate -FilePath .\server.crt -CertStoreLocation Cert:\LocalMachine\Root
```

`server.key` 는 비밀 파일이므로 직원 PC로 복사하지 않습니다.

## 5. 방화벽

다른 PC가 접속하려면 포트를 엽니다. 이 단계는 **관리자 권한 PowerShell** 이 필요합니다. 시작 메뉴에서 PowerShell 을 "관리자 권한으로 실행"하면 **새 세션**이 열리므로, 먼저 저장소 폴더로 이동합니다 (이관 지시서를 쓴다면 변수 블록도 다시 실행합니다). 그다음 `config.toml` 의 `port` 값을 넣어 실행합니다.

```powershell
cd C:\bizopt2026\solbox
```

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\open_firewall.ps1 -Port 8443
```

규칙 이름은 "SolutionBox" 이고, 도메인·개인 네트워크에서만 열립니다. 네트워크가 "공용"으로 잡혀 접속이 안 되면 `Get-NetConnectionProfile` 로 확인하세요. 규칙을 지우려면 같은 방법(관리자 PowerShell)으로 `-Remove` 를 붙입니다.

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\open_firewall.ps1 -Port 8443 -Remove
```

## 6. 실행과 자동 시작

직접 실행해 보기:

```powershell
python -m app
```

브라우저에서 `https://10.231.0.5:8443` (실제 주소와 포트) 를 엽니다. 이렇게 직접 실행한 서버의 종료는 `Ctrl+C` 입니다 (자동 시작으로 켠 서버는 아래 "서버 멈추기와 다시 시작" 을 따릅니다).

죽으면 10초 뒤 다시 시작하는 실행 스크립트 (콘솔 출력은 `data\logs\server-console.log` 에 쌓입니다. 가상환경을 쓰면 `-PythonExe` 로 python.exe 전체 경로를 넘깁니다):

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\run_server.ps1
```

콘솔 로그가 10MB 를 넘으면 서버를 (다시) 시작할 때 `server-console.log.1` 로 옮겨 새로 씁니다. 로그 폴더가 `data\logs` 가 아니면 `-LogDir <폴더>` 를 붙입니다.

Windows에 로그온하면 자동으로 시작되게 등록 (작업 스케줄러의 "SolutionBox" 작업). **서버를 실행할 Windows 계정으로** 실행하세요. 이 스크립트는 지금 로그인한 계정(`$env:USERNAME`)을 작업 소유자로 등록하고, Claude CLI 로그인도 그 계정의 것을 쓰기 때문입니다. 작업 등록에 권한이 더 필요한 PC에서는 "액세스가 거부되었습니다" 가 나올 수 있습니다. 그때는 **같은 계정으로** PowerShell 을 관리자 권한으로 새로 열어(저장소 폴더로 이동한 뒤) 다시 실행합니다. 다른 계정의 관리자 창에서 실행하면 작업이 그 계정으로 등록되어 서버가 엉뚱한 계정으로 돌므로 피합니다.

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\install_autostart.ps1
```

등록 직후 바로 시작하려면:

```powershell
Start-ScheduledTask -TaskName SolutionBox
```

등록을 지우려면:

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\install_autostart.ps1 -Remove
```

### 서버 멈추기와 다시 시작

자동 시작으로 켠 서버는 창이 숨겨져 있어 `Ctrl+C` 로 멈출 수 없습니다. 작업을 멈추고, 포트를 쓰는 프로그램이 없어졌는지 확인합니다 (8443 은 예시이고 실제 값은 `config.toml` 의 `port` 입니다).

```powershell
Stop-ScheduledTask -TaskName SolutionBox
```

```powershell
Get-NetTCPConnection -LocalPort 8443 -State Listen -ErrorAction SilentlyContinue
```

아무것도 나오지 않으면 멈춘 것입니다. 계속 `Listen` 이 보이면 `OwningProcess` 의 프로그램이 python 인지 `Get-Process -Id <OwningProcess>` 로 확인하고, 사람이 확인한 뒤에만 종료합니다. 다시 시작하려면 아래 명령을 실행하고 10초쯤 기다린 뒤 위 `Get-NetTCPConnection` 으로 `Listen` 을 확인합니다.

```powershell
Start-ScheduledTask -TaskName SolutionBox
```

**자동 로그온:** Claude CLI 로그인은 Windows 계정별이라 서비스가 아니라 "로그온한 계정"으로 서버를 돌립니다. 그래서 PC를 재부팅했을 때 누군가 로그온해야 서버가 켜집니다. 서버 PC에서는 보안 정책이 허용할 때에 한해 해당 계정의 자동 로그온을 설정하세요 (`netplwiz` 실행 → "사용자 이름과 암호를 입력해야 이 컴퓨터를 사용할 수 있음" 체크 해제). 자동 로그온은 PC의 물리적 보안이 확보된 경우에만 쓰고, 화면 잠금 정책은 담당자와 상의합니다. 서버로 옮기는 작업은 `docs/서버이관_Claude용.md` 를 따릅니다.

## 7. 사용자 PC에서 쓰던 데이터를 서버로 옮기기

서버 이관 때의 순서입니다 (자세한 단계는 `docs/서버이관_Claude용.md`).

1. 기존 PC의 서버를 멈춥니다. 직접 실행했다면 실행 창에서 `Ctrl+C`, 자동 시작을 썼다면 6번의 "서버 멈추기와 다시 시작" 대로 `Stop-ScheduledTask -TaskName SolutionBox` 를 실행하고 `Get-NetTCPConnection -LocalPort <포트> -State Listen` 에 아무것도 나오지 않는지 확인합니다.
2. 서버에 이미 `data` 가 있으면 지우거나 덮어쓰지 말고 이름을 바꿉니다 (`Rename-Item data data-before-migration-20261118-1030` 처럼 날짜시각을 붙임). 그러면 `data` 가 없는 상태가 되어, 두 설치가 섞이거나 옛 `app.db-wal`·`app.db-shm` 이 새 `app.db` 옆에 남지 않습니다.
3. 기존 PC의 `data` 폴더 전체를 서버의 `data_dir` 로 복사합니다. `app.db-wal`, `app.db-shm` 이 있으면 `app.db` 와 함께 복사하고 지우지 않습니다 (서버가 멈춘 상태면 보통 없습니다).
4. 서버에서 사본 폴더를 다시 만듭니다.

```powershell
python -m app.cli rebuild-knowledge
```

## 8. 백업과 복원

- **자동 백업:** 서버가 켜져 있는 동안 매일 02:00 이후 한 번, `backup_dir` (기본: `data_dir` 옆 `backups`) 에 `20261118-020000` 같은 날짜-시각 이름의 폴더를 만듭니다. 안에는 `app.db`, `uploads`, `decks`, `backup.json` 이 있습니다. `knowledge` 는 DB에서 다시 만들 수 있어 백업하지 않습니다. 음성 받아쓰기 모델(`data_dir/models/`)도 백업하지 않습니다 (크기가 크고 `stt-setup` 으로 다시 받을 수 있습니다. 백업은 `app.db`, `uploads`, `decks` 만 복사합니다). 받아쓴 글(`uploads/intake/<묶음>/*.transcript.txt`)은 `uploads` 안에 있어 백업됩니다. 14일(`backup_keep_days`)이 지난 백업은 지우고, 가장 최근 것 하나는 항상 남깁니다.
- **올리기 폴더:** 올리기로 올린 원본은 `data_dir` 의 `uploads/intake/<묶음 번호>/` 에 있어 위 백업(`uploads`)에 포함됩니다. 원본은 저장·버리기·실패 뒤에도 지우지 않으므로 올릴수록 `uploads/intake` 가 계속 커지고 백업도 그만큼 커집니다 (자동으로 비우는 기능은 없습니다. 디스크 여유를 가끔 확인하세요). `intake_work/` 는 AI가 읽는 작업 사본(글로 바꾼 문서, 줄인 사진)이라 필요할 때 원본에서 다시 만들어지므로 백업하지 않습니다. 저장이 끝나거나 묶음을 버리면 지워지고, **실패한 묶음은 "다시 정리"를 위해 남겨 둡니다.** 남아 있어도 지워도 됩니다 (정리를 시작할 때 없으면 다시 만듭니다).
- **올리기 AI의 파일 접근 범위:** 올리기 정리 작업은 묶음의 작업 폴더에서 `Read(./**)`, `Glob(./**)`, `Grep(./**)` 처럼 그 폴더 안으로 한정된 파일 도구만 미리 허용해 실행합니다. 그래서 업로드 자료 속 글이 AI에게 `../` 나 절대 경로로 다른 묶음·지식 폴더·`config.toml` 을 읽으라고 시켜도 Claude CLI 가 거절합니다 (이 서버의 Claude CLI 2.1.328 에서 확인). Claude CLI 를 크게 올린 뒤에는 README 의 올리기 확인 목록으로 다시 확인하세요. 웹 도구는 없어 읽은 내용이 서버 밖으로 나가지 않습니다. **한계:** (1) 이 제한은 Claude CLI의 허용 규칙 동작에 기대므로 CLI 버전이 바뀌면 달라질 수 있습니다. (2) 서버 계정의 Claude 설정 파일(사용자 설정이나 프로젝트 설정)에 더 넓은 허용 규칙이 있으면 제한이 풀릴 수 있으니, 서버 계정에는 `Read` 를 넓게 허용하는 설정을 두지 마세요. (3) Linux 에서만 확인했고 Windows 에서는 확인하지 못했습니다. 설치 직후와 CLI 업데이트 뒤에 README "Claude CLI 수동 확인"의 16번으로 직접 확인하세요. 확인이 안 되면 작업 폴더는 보안 경계가 아니라고 보고, 믿을 수 없는 출처의 문서는 올리지 않도록 안내하세요 (웹 도구가 없으므로 읽은 내용이 서버 밖으로 나가지는 않고, 올린 사람의 정리안 화면에만 보입니다).
- **지금 백업:** 관리 → 시스템 화면의 "지금 백업" 버튼, 또는 명령.

```powershell
python -m app.cli backup
```

- **백업 확인:**

```powershell
python -m app.cli backup --verify C:\bizopt2026\solbox\backups\20261118-020000
```

- **복원 절차 (자동화하지 않았습니다):**
  1. 서버를 멈춥니다 (6번의 "서버 멈추기와 다시 시작": `Stop-ScheduledTask -TaskName SolutionBox` 후 포트에 `Listen` 이 없는지 확인).
  2. 현재 `data` 폴더를 다른 이름으로 바꿔 둡니다 (예: `Rename-Item data data-broken`). 지우지 않습니다.
  3. 새 `data` 폴더를 만들고, 복구할 백업 폴더를 `--verify` 로 확인한 뒤, 그 안의 `app.db`, `uploads`, `decks` 를 새 `data` 폴더로 복사합니다.
  4. 사본 폴더를 다시 만듭니다.

```powershell
python -m app.cli rebuild-knowledge
```

  5. **서버가 복원한 폴더를 보게 하기:** 서버는 `config.toml` 의 `data_dir` 가 가리키는 폴더만 씁니다. 3번에서 원래 이름 그대로 새 `data` 폴더를 만들었다면 설정을 바꿀 필요가 없습니다. 다른 위치(다른 드라이브·폴더)에 복원했다면 `config.toml` 의 `data_dir = "D:/solbox/data"` 처럼 그 폴더를 적습니다 (상대 경로는 설정 파일이 있는 폴더 기준). `python -m app.cli check` 의 "데이터 폴더"·"데이터베이스" 줄이 복원한 폴더를 가리키는지 확인합니다.
  6. **`secret_key`:** 새 서버로 옮겼다면 `config.toml` 의 `secret_key` 는 원래 값을 그대로 쓰는 것이 좋습니다. 값이 달라지면 모든 사용자의 로그인이 풀려 다시 로그인해야 합니다 (기록은 영향이 없습니다). 비밀번호는 `app.db` 안에 있어 백업과 함께 돌아옵니다.
  7. **`backup_dir`:** 생략하면 `data_dir` 옆의 `backups` 폴더입니다. 복원한 서버에서도 백업이 같은 곳(또는 다른 드라이브)에 쌓이도록 `backup_dir` 을 확인하세요. `data_dir` 안의 `uploads`·`decks` 폴더 안에는 둘 수 없습니다. 방금 만든 백업의 위치는 관리자 "시스템" 화면의 알림과 "최근 백업" 줄에서 볼 수 있습니다.
  8. 서버를 시작하고 화면에서 확인합니다.
- 백업은 같은 PC의 다른 폴더입니다. 디스크가 고장 나면 함께 사라지므로 `backup_dir` 을 다른 드라이브나 공유 폴더로 두거나 주기적으로 복사해 두세요.

1. 최근 백업이 있는지 확인합니다 (관리 → 시스템).
2. 서버를 멈추고 (6번의 "서버 멈추기와 다시 시작") 새 코드를 받습니다.

```powershell
git pull
```

3. 의존 패키지를 갱신합니다.

```powershell
python -m pip install -e .
```

4. 서버를 다시 시작합니다 (`Start-ScheduledTask -TaskName SolutionBox`, 직접 실행했다면 `python -m app`). 새 버전이 필요로 하는 DB 표·컬럼은 시작할 때 자동으로 추가되며, 바꾸기 전에 `app.db` 를 `app.db.before-migrate-날짜시각` 이름으로 복사해 둡니다 (시작 한 번에 하나만 만들고, 바꿀 것이 없는 시작에서는 만들지 않습니다). 문제가 생기면 그 파일로 되돌릴 수 있습니다 (아래 "업데이트 되돌리기").
5. 점검합니다.

```powershell
python -m app.cli check
```

zip 으로 받은 경우에는 `data`, `config.toml`, `certs` 를 제외하고 코드만 덮어씁니다.

### 온톨로지 업데이트(영업기회·BM·프로젝트 이름 정리)에서 처음 시작할 때 일어나는 일

이 버전으로 **처음** 시작할 때 한 번만 일어나고, 두 번째 시작부터는 하지 않습니다.

- 새 표(후속 조치, 고객 니즈, 영업기회, BM 등)와 새 컬럼이 더해지고, 기존 표·컬럼은 이름도 값도 바꾸지 않습니다.
- `app.db.before-migrate-날짜시각` 복사본이 **하나** 만들어집니다 (위 4번). 옛 활동 기록의 후속 조치·수요 단서(JSON)를 새 표로 **복사**하고(원래 값은 그대로 남습니다), 올리기로 만든 옛 기록에 유래를 채웁니다.
- `knowledge` 폴더가 **한 번 통째로 다시 만들어집니다.** 기록이 많으면 첫 시작이 오래 걸릴 수 있으니 화면이 뜰 때까지 기다리세요 (`data\logs\app.log` 로 진행을 볼 수 있습니다).
- 옛 `/businesses` 주소(북마크·옛 링크)는 `/projects` 로 자동 이동합니다. 업그레이드 때 열려 있던 옛 화면의 저장도 새 주소로 넘어갑니다.

### 프로젝트 상태가 고르는 칸이 된 업데이트 (베타 P)

- 프로젝트의 "상태"는 자유 글에서 고르는 목록(준비·진행·완료·중단·유지보수)으로 바뀝니다. **저장된 데이터는 바뀌지 않습니다** (이전·변환·새 컬럼 없음, 첫 시작 때 하는 일도 없습니다).
- 옛 자유 글(예: "진행 중")은 그대로 남고 화면에는 "진행 중 (이전 입력)" 으로 보입니다. 그 프로젝트를 고칠 때 그 글이 골라진 항목으로 나오므로, 다른 칸만 고쳐도 상태는 그대로이고 원하면 목록 값으로 바꿀 수 있습니다.
- "(이전 입력)" 은 화면(목록·상세·고치기·관계 카드)에만 붙습니다. 지식 사본(`knowledge/projects/`, AI 가 읽는 파일)의 상태 줄에는 붙이지 않고 저장된 글 그대로 적습니다 (사용자 결정 2026-11-22).

### AI 생성 표시가 더해진 업데이트 (베타 R)

- 올리기·리서치로 AI 가 만든 솔루션·활동 기록·고객·파트너에 화면의 "AI 생성" 배지와 지식 사본(`knowledge/`)의 `- AI 생성: 예 (올리기 묶음 #3 에서 AI 가 정리)` 줄이 더해집니다. **저장된 데이터·DB 는 바뀌지 않습니다** (새 열·이전 작업 없음). 기준은 기록의 유래입니다.
- 화면 배지는 업데이트 즉시 보입니다. 지식 사본은 업데이트 뒤 서버를 처음 시작할 때 한 번 자동으로 다시 만들어져, 이미 있는 기록에도 줄이 붙습니다 (따로 할 일은 없습니다).
- 사람이 직접 만든 기록을 "AI 초안 받기"·"AI 정리" 로 채운 경우는 유래가 직접 입력이라 표시되지 않습니다. AI 가 쓴 글인지는 기록마다 사람이 알아야 합니다.

### 업데이트 되돌리기

1. 서버를 멈춥니다.
2. 이전 버전 코드로 되돌립니다 (`git checkout <이전 버전>`).
3. **새 버전으로 처음 시작했을 때 만들어진 `data\app.db.before-migrate-날짜시각` 파일 하나**를 `data\app.db` 로 복원합니다. 새 버전을 시작한 뒤에 만들어진 파일 중 가장 이른 것이 그것입니다 (날짜시각 이름이 업데이트 직후 처음 시작한 때와 같습니다). `app.db-wal`, `app.db-shm` 이 있으면 함께 지웁니다.
4. 서버를 시작합니다. 사본 이후에 입력한 내용은 사라집니다.

**주의:** 업그레이드한 뒤 사본을 복원하지 않고 옛 버전을 돌렸다가 다시 업그레이드하지 마세요. 옛 버전에서 입력한 후속 조치·고객 니즈는 옛 JSON 열에만 들어가고, 새 버전은 복사를 이미 끝낸 것으로 보아 다시 복사하지 않으므로 새 화면에 나타나지 않습니다. 옛 버전으로 돌아갈 때는 꼭 위 사본을 복원하세요.

## 10. 문제 해결

먼저 점검 명령을 실행합니다 (서버를 멈춘 상태에서).

```powershell
python -m app.cli check
```

한 줄씩 "정상" 또는 "문제: …" 가 나오고, 문제가 있으면 종료 코드가 1입니다. 항목: 설정 파일, Python 버전(3.11 이상), 데이터 폴더, 데이터베이스, 지식 폴더, Claude CLI, 음성 받아쓰기, 인증서, 포트. 관리 → 시스템 화면도 같은 점검을 돌리며 Claude CLI 는 `claude --version` 을 5초(명령줄은 30초)까지만 기다립니다. 넘으면 "확인 못 함"으로 보이고 그 명령과 자식 프로세스(Windows 의 npm `claude.cmd` 껍데기가 띄운 node 포함)를 함께 종료합니다 (Linux 에서만 시험했고 Windows 의 `.cmd` 껍데기는 확인하지 못했습니다). 결과는 1분 동안 다시 쓰고 버전 줄은 200자까지만 보입니다.

- **제안 "대화로 구체화" 에서 답이 오지 않을 때:** 대화 구역 안의 말풍선이 상태를 보여 줍니다. "대기 중 · 앞에 AI 작업 n개" 는 다른 AI 작업(주간 리서치, 올린 파일 정리 등)이 먼저 도는 중이라는 뜻이고 끝나면 저절로 시작합니다 (`ai_concurrency` 기본값 1). 말풍선이 "다시 시도" 와 함께 빨간 글로 바뀌면 "자세한 오류" 를 펼쳐 보세요 (Claude CLI 가 낸 마지막 글). 아무 변화 없이 "대기 중" 만 계속되면 AI 작업 처리기가 꺼져 있는지(`ai_worker_enabled`) 보세요 (꺼진 서버는 새 AI 작업을 받지 않으므로 보통은 대기 줄이 생기지 않고 "AI 꺼짐" 안내가 나옵니다). 실시간 글이 안 나오는 환경(CLI 버전 등)에서는 한 번 자동으로 스트리밍 없는 실행으로 바꿔 답을 받고, 그 사실은 `data\logs\app.log` 에 "스트리밍 실패, 스트리밍 없는 실행으로 대체합니다" 로 남습니다.
- **로그 위치:** 앱·대기열·스케줄러 로그는 `data\logs\app.log` (5MB씩 5개까지 회전). `run_server.ps1` 로 실행하면 콘솔 출력이 `data\logs\server-console.log` 에 쌓입니다. 최근 줄 보기:

```powershell
Get-Content data\logs\app.log -Tail 50 -Encoding UTF8
```

- **서버를 다시 시작한 뒤 AI 작업이 "서버가 다시 시작되어 작업이 중단되었습니다"로 보일 때:** 돌던 작업이 재시작으로 끊긴 것입니다. 화면의 "다시 시도"로 다시 보냅니다.
- **AI 연결 확인:** 관리 → 시스템 → "AI 연결 확인". "AI 연결 정상" 이 나오면 됩니다. 실패하면 이유가 한국어로 나옵니다 (로그인 필요, 사용 한도, 네트워크 등). 로그인 문제는 오류 출력에서 "invalid x-api-key", "Please run /login", "401 Unauthorized", "OAuth token has expired" 같은 분명한 표현으로만 알아봅니다 (글 속에 401 이나 oauth 가 들어 있다고 로그인 문제가 되지는 않습니다). 로그인 문제는 **서버를 실행하는 계정으로** `claude` 를 실행해 다시 로그인합니다. 위쪽 줄이 "AI 사용 불가"여도 화면의 AI 버튼은 막히지 않습니다(다시 시도하면 연결을 다시 확인하고, 성공한 AI 작업이 하나 나오면 상태가 저절로 풀립니다). 위쪽 줄이 "AI 꺼짐"(`ai_worker_enabled = false`)이면 서버가 새 AI 작업을 받지 않습니다: AI 버튼이 비활성이고, 올린 파일은 보관만 되며, 예약 조사도 실행을 만들지 않습니다 (켜면 예정 시각 뒤 6일 안에는 그 주 조사를 시작합니다).
- **포트 충돌:** "포트 N을 다른 프로그램이 쓰고 있습니다" 가 나오면 누가 쓰는지 확인하고, 다른 프로그램이면 `config.toml` 의 `port` 를 바꿉니다 (방화벽 규칙도 새 포트로 다시 엽니다).

```powershell
Get-NetTCPConnection -LocalPort 8443 | Select-Object LocalAddress, State, OwningProcess
```

- **직원이 비밀번호를 잊었을 때:** 13절의 관리자 절차(임시 비밀번호 정하기 → 본인이 로그인하며 바꾸기)를 따릅니다.
- **접속이 안 됨:** `host` 가 `127.0.0.1` 이면 다른 PC에서 접속할 수 없습니다. `0.0.0.0` 으로 바꾸고 방화벽을 엽니다.
- **자동 시작이 안 됨:** 작업 스케줄러에서 "SolutionBox" 의 마지막 실행 결과를 보고, `data\logs\server-console.log` 를 확인합니다.

## 11. 리서치 설정 (관리자)

관리 → 리서치 설정 화면에서 합니다.

- **주제:** 분야(시장·기술·정책)마다 조사할 주제를 추가합니다. 이름과 쉼표로 구분한 키워드를 적습니다. 사용 여부를 끄거나 삭제할 수 있습니다. 사용 중인 주제가 없으면 조사가 시작되지 않습니다.
- **실행 주기:** 기본은 매주 월요일 06:00 (서버 PC 현지 시각)입니다. 요일·시·분을 바꾸거나 자동 실행을 끌 수 있습니다. 서버가 꺼져 있다가 켜지면, 가장 최근 예정 시각의 조사를 한 번 따라잡습니다 (6일이 넘게 지난 예정은 건너뜁니다). 따라잡기는 **그 예정 시각에 이미 사용 중인 주제가 하나라도 있었을 때만** 합니다. 새로 설치했거나 한 주 동안 주제가 없다가 첫 주제를 추가한 경우에는 지나간 예정 시각의 조사를 시작하지 않으므로, 주제를 여러 개 입력하는 중에 조사가 시작되지 않습니다. 다음 예정 시각까지 기다리거나 "지금 조사" 버튼을 누르세요. AI 작업 처리기가 꺼져 있는 동안(`ai_worker_enabled = false`)에는 예약 조사가 실행을 만들지 않습니다. 진행 중이던 조사가 있는 채로 처리기를 끄고 서버를 시작하면 분야 조사가 모두 끝난 조사도 "진행 중"으로 남고(화면에 "AI 처리기가 꺼져 있어 지금은 진행되지 않아요"가 보입니다) 제안 작업은 만들지 않습니다. 처리기를 켜고 서버를 다시 시작하면 이어서 진행합니다. 이번 주 예약 조사를 삭제해도 같은 예정 시각의 조사는 다시 시작되지 않습니다.
- **주의:** 주중에 요일·시각을 바꾸면, 새 예정 시각이 이미 지난 시점이면 이번 주에 조사가 한 번 더 실행될 수 있습니다. 이미 이번 주 조사를 했다면 요일을 바꾸기 전에 이 점을 감안하세요.
- **동시에 도는 조사:** `config.toml` 의 `ai_concurrency` 는 1로 둡니다. 수동 조사가 한창일 때 예정 시각이 되면 예약 조사는 시작하지 않고, 수동 조사가 끝난 뒤 다음 점검(1분 이내)에 이어서 실행됩니다 (6일 안일 때).
- **지금 조사:** 같은 화면의 버튼으로 바로 실행합니다. 한 번에 한 실행만 돌고, 분야당 몇 분이 걸립니다. 진행 상황은 같은 화면과 리서치 메뉴에 나옵니다.
- 결과는 "리서치" 메뉴에서 모든 사용자가 보고, 발굴 방향 제안을 솔루션 후보로 등록할 수 있습니다. 보고서 삭제는 관리자만 합니다.

## 12. 음성 받아쓰기 (선택)

**먼저 알아 둘 것:** 이 기능은 개발 환경에서 모델을 받을 수 없어 **실제로 한 번도 돌려 보지 못했습니다.** 서버 PC에서 아래 순서로 확인하고, README "수동 확인" 17~20번을 해 보세요. 속도·정확도는 아래 표가 아니라 직접 잰 값을 믿으세요.

**설치와 켜기** (서버를 멈춘 상태, 처음 한 번만 인터넷이 필요합니다):

```powershell
python -m pip install -e ".[stt]"
```

**설치가 실패하면 (wheel):** 받아쓰기 패키지 중 `ctranslate2`, `av`(PyAV), `onnxruntime` 은 컴파일된 배포본(wheel)이 서버의 Python 버전·운영체제에 맞게 있어야 합니다. 위 명령이 "no matching distribution" 이나 컴파일 오류로 끝나면 그 패키지의 wheel 이 이 Python 버전에 아직 없는 것입니다. 이때는 (1) 서버의 Python 을 이 패키지들이 지원하는 한 단계 낮은 버전으로 맞추거나, (2) 설치를 `python -m pip install -e ".[stt]" -v` 로 다시 해서 어느 패키지에서 막혔는지 보고 관리자에게 알립니다. 설치 뒤 `python -m app.cli check` 가 "faster-whisper 미설치" 나 "불러오지 못했습니다" 를 보이지 않는지 확인하세요. `[stt]` 는 PyAV 를 `av<19` 로 묶어 둡니다 (아래 문제 해결 참고. faster-whisper 가 PyAV 19 를 지원하면 `pyproject.toml` 의 핀을 풀 수 있습니다).

`config.toml` 에 다음을 적습니다.

```toml
transcriber = "faster-whisper"
transcribe_model = "small"
```

```powershell
python -m app.cli stt-setup
```

모델을 `data_dir\models\` 에 받고 무음 1초로 자체 점검을 합니다 (서버가 인터넷에 접속하는 유일한 곳입니다. 서버 실행 중에는 접속하지 않습니다). 자체 점검은 음성 구간 검출(`vad_filter`)을 끄고 돌리므로 모델의 인코더·디코더가 실제로 실행됩니다. 즉 "모델 파일이 읽히고, 라이브러리와 오디오 읽기가 동작한다"까지만 증명하고, 한국어 정확도와 속도는 알 수 없습니다 (무음이라 글이 없는 것이 정상. 실패하면 원인(예외 종류와 내용)이 함께 나옵니다). 이어서 실제 녹음으로 속도를 잽니다.

```powershell
python -m app.cli stt-test C:\녹음\시험.m4a
```

글, 걸린 시간, 속도(녹음 1분을 몇 분에 받아쓰는지)가 나옵니다. 마지막으로 `python -m app.cli check` 에서 "음성 받아쓰기: 정상 (faster-whisper, small, CPU)" 를 확인하고 서버를 다시 시작합니다.

**설정 키:** `transcribe_model` (tiny, base, small, medium, large-v3, large-v3-turbo 또는 받아 둔 모델 폴더 경로. 기본 small), `transcribe_language` (기본 `ko`, 자동은 `auto`), `transcribe_threads` (0 이면 라이브러리 기본값. 서버에서 다른 일도 한다면 코어 수보다 작게), `transcribe_max_minutes` (기본 120. 더 긴 음성은 모델을 부르기 전에 길이만 보고 실패로 두며 나눠 올리라고 안내), `transcribe_chunk_minutes` (기본 10. 긴 음성을 이 길이씩 나눠 받아쓰므로 작을수록 메모리를 덜 씁니다. 조각은 끝쪽 10초 안의 가장 조용한 곳에서 잘라 낱말 중간이 잘리지 않게 합니다). `transcribe_language` 는 Whisper 언어 코드나 `auto` 만 받습니다 (잘못 적으면 서버 시작 때 알려 줍니다).

**모델 크기 안내 (대략의 안내이고 측정값이 아닙니다):** 클수록 정확하지만 느리고 디스크·메모리를 더 씁니다. tiny·base 는 빠르지만 한국어 고유명사에 약하고, small 이 시작점으로 무난하며, medium·large-v3 는 정확하지만 GPU 없는 CPU에서는 녹음 길이보다 오래 걸릴 수 있습니다. large-v3-turbo 는 large-v3 보다 빠르게 만든 모델입니다. 디스크는 모델당 대략 수십 MB(tiny)에서 수 GB(large)까지입니다. `stt-test` 로 우리 서버의 실제 속도를 재서 정하세요.

**메모리(RAM) 안내:** 음성은 `transcribe_chunk_minutes` 길이씩 읽어 받아쓰므로, 녹음이 길어도 음성 부분의 메모리는 조각 하나 분량으로 한정됩니다. 개발 중 합성 음성으로 측정한 값 (실제 한국어 모델이 아니라 무작위 가중치의 아주 작은 모델이라 **모델 자체의 메모리는 포함되지 않습니다**, 서버 PC 에서 직접 재세요): 60분 음성을 조각 없이 한 번에 읽어 받아쓰는 옛 방식은 최고 3384 MB, 이 방식은 10분 조각으로 845 MB, 5분 조각으로 548 MB 였습니다. 여기에 선택한 모델의 메모리(small 이 대략 1 GB 안팎이라고 알려져 있으나 측정하지 않았습니다)를 더해 잡으세요. **모델은 한 번 불러오면 서버 프로세스가 끝날 때까지 메모리에 계속 올라가 있습니다** (첫 받아쓰기 때 불러오고 그 뒤로는 받아쓰지 않을 때도 그대로). 서버 메모리가 모자라면 `transcribe_chunk_minutes` 를 줄이거나 작은 모델을 쓰세요.

**CPU만 쓰는 서버에서 기대할 것:** GPU가 없으므로 긴 녹음은 오래 걸립니다 (1시간짜리가 수십 분~그 이상일 수 있음). 받아쓰는 동안 CPU를 많이 씁니다. 받아쓰기는 프로세스 전체에서 한 번에 하나만 돌고, 여러 묶음을 올리면 차례로 처리됩니다. 사용자 화면에는 진행률이 보이고 화면을 떠나도 됩니다.

**워커 수와 다른 AI 작업 (절충):** 받아쓰는 정리 작업은 AI 워커 스레드 하나를 그동안 계속 씁니다. `ai_concurrency` 기본값이 1이므로 **받아쓰는 동안 다른 AI 작업(활동 기록 정리, 제안, 리서치 등)은 끝날 때까지 대기열에서 기다립니다.** 이 절충은 대기열을 바꾸지 않고 그대로 둔 것입니다. 녹음을 자주 올리면 `ai_concurrency = 2` 로 올리세요. 워커가 둘 이상이면 받아쓰기가 필요한 정리 작업은 다른 받아쓰기가 도는 동안 대기열에서 건너뛰어, 한 워커가 받아쓰는 사이 다른 워커가 짧은 작업을 처리합니다 (Claude 호출이 겹쳐 돌 수 있으니 한도에 주의).

**저장 위치:** 모델은 `data_dir\models\` (Windows 에서 링크를 못 만들면 복사본이 생겨 크기가 더 커질 수 있음), 받아쓴 글은 원본 옆 `uploads\intake\<묶음>\<저장 이름>.transcript.txt` 입니다. 모델 폴더는 백업하지 않습니다 (8번). 받아쓴 글 파일을 지우면 다음 "다시 정리"에서 다시 받아씁니다.

**문제 해결:**
- "faster-whisper 미설치" → `python -m pip install -e ".[stt]"`.
- "받아쓰기 프로그램(faster-whisper)을 불러오지 못했습니다 (ImportError…)" → 설치가 깨졌거나 Windows 에 Visual C++ 재배포 가능 패키지가 없는 경우입니다. 재배포 패키지를 설치하고 `python -m pip install --force-reinstall -e ".[stt]"` 를 다시 실행하세요.
- "받아쓰기 프로그램 오류입니다. 관리자에게 알려 주세요 (TypeError)" → 파일 탓이 아니라 라이브러리 문제입니다. 가장 흔한 원인은 PyAV 19 입니다: faster-whisper 1.2.1 이 `av.open(..., metadata_errors=...)` 를 부르는데 PyAV 19 는 이 인자를 받지 않습니다. `python -m pip list` 로 `av` 가 19 이상이면 `python -m pip install "av<19"` 로 낮추세요 (`.[stt]` 는 이미 `av<19` 를 요구합니다). 자세한 내용은 `data\logs\app.log` 의 오류 기록에 있고, `python -m app.cli stt-setup` 의 자체 점검도 같은 원인을 보여 줍니다.
- "모델 'small'이 아직 없습니다" → `python -m app.cli stt-setup` (인터넷 필요). 인터넷이 막힌 서버라면 다른 PC에서 받은 모델 폴더를 옮기고 `transcribe_model` 에 그 폴더 경로를 적습니다 (폴더에 `model.bin` 이 있어야 함).
- "음성이 너무 깁니다" → 나눠서 올리거나 `transcribe_max_minutes` 를 올립니다.
- "음성을 받아쓰지 못했습니다. 파일이 손상되었거나…" → 파일 자체를 읽지 못한 경우입니다 (오디오 디코더가 "잘못된 데이터"라고 한 때만 이 문구가 나옵니다). 자세한 원인은 `data\logs\app.log` 에 있습니다. 다른 형식(wav, mp3)으로 바꿔 올려 보세요.
- 엔진을 나중에 켰는데 이전에 "받아쓰기 필요"로 올라간 음성이 있으면: 묶음 화면에 "이제 음성을 받아쓸 수 있어요. 다시 정리를 눌러 주세요." 가 보입니다. "정리 시작"·"다시 정리"를 누르면 받아쓰기 대기로 바뀝니다 (저장 완료·버린 묶음은 그대로).
- 받아쓰는 도중 서버가 멈췄다면 묶음이 "실패"로 바뀝니다. "다시 정리"를 누르면 끝난 파일은 건너뛰고 이어서 합니다.
- 받아쓰기 결과가 이상하게 반복되거나 엉뚱하면 더 큰 모델을 써 보세요 (`stt-test` 로 속도 확인).

**알아 둘 동작:** 음성 트랙이 여러 개인 파일(일부 화면 녹화)은 첫 번째 트랙만 받아씁니다. 길이를 알 수 없는 파일(브라우저 녹음 webm 등)은 진행률이 0%로 보이지만 받아쓰기는 진행됩니다. 언어를 `auto` 로 두면 말이 처음 나온 구간의 언어로 정해 끝까지 씁니다.

**아직 확인하지 못한 것:** 실제 한국어 녹음의 정확도와 속도, 큰 모델(특히 `large-v3-turbo`)의 저장소 파일 구성과 내려받기, m4a 이외 형식(특히 wma 디코딩), Windows 에서의 설치·모델 저장·콘솔 글자(한글이 깨지면 `?`로 바뀌어 나옵니다), 장시간(2시간) 녹음의 실제 소요 시간입니다. 개발 환경은 모델 저장소에 접속할 수 없어 무작위 가중치의 작은 모델과 합성 음성으로 "라이브러리 연결·조각 나누기·시간 표시·진행률·묶음 흐름"만 확인했습니다. 서버 PC 에서 README 수동 확인 17~20번으로 직접 확인하세요.

## 13. 계정과 비밀번호, 동시에 고칠 때의 보호

### 비밀번호 (직원이 직접)
- 왼쪽 메뉴 맨 아래 내 이름(또는 `/account` "내 정보")에서 직원이 스스로 비밀번호를 바꿉니다: 현재 비밀번호, 새 비밀번호, 확인. 바꾸면 **다른 곳(다른 기기·브라우저)의 로그인은 끝나고** 지금 화면은 그대로 쓸 수 있습니다. 이름·아이디·권한은 보기만 되고, 이름·권한은 관리자가 바꿉니다.
- **규칙:** 8자 이상, 아이디와 같지 않음, 같은 글자 하나로만 되어 있지 않음. 직원이 바꿀 때와 관리자가 사용자를 만들거나 비밀번호를 다시 정할 때 모두 같은 규칙입니다. 규칙이 생기기 전의 짧은 비밀번호도 **로그인은 계속 됩니다**(아무도 잠기지 않습니다). 다만 그런 사용자는 로그인하면 "내 정보" 화면으로 가서 새 비밀번호로 바꾸라는 안내를 봅니다. (`python -m app.cli create-admin` 의 첫 관리자 비밀번호에는 이 규칙을 적용하지 않습니다. 직접 넉넉히 정하세요.)
- 사용이 중지된 계정으로 **맞는 비밀번호**로 로그인하면 "사용이 중지된 계정입니다. 관리자에게 문의하세요." 가 나옵니다. 비밀번호가 틀리면 계정이 있는지 알 수 없는 일반 문구("아이디 또는 비밀번호가 올바르지 않습니다.")만 나옵니다.

### 비밀번호를 잊었을 때 (관리자 절차)
1. 관리 → 사용자에서 그 사용자 줄의 "새 비밀번호" 칸에 임시 비밀번호(규칙에 맞게)를 쓰고 저장합니다.
2. 임시 비밀번호를 본인에게 직접 알려 줍니다 (메신저에 남기지 않습니다).
3. 본인은 그 비밀번호로 로그인하면 **비밀번호 바꾸기 화면으로만** 갑니다 (다른 화면은 바꿀 때까지 열리지 않고, 로그아웃은 됩니다). 새 비밀번호로 바꾸면 평소처럼 쓸 수 있습니다. 사용자 목록의 "변경 대기" 표시가 사라집니다.
- 관리자가 사용자를 새로 만들 때 정한 비밀번호도 똑같이 처음 로그인한 뒤 바꾸게 됩니다. 관리자 자신이 자기 줄에서 정한 비밀번호는 바꾸라고 하지 않고, 그 로그인도 그대로 유지됩니다.
- 로그인 상태는 서버에 저장하지 않고 브라우저의 서명된 쿠키에 있으므로, 쿠키에 비밀번호 버전 표시를 함께 넣어 비밀번호가 바뀌면 옛 쿠키를 거절합니다. 이 표시가 생기기 전에 한 로그인은 한 번 받아 주고 그때부터 따라갑니다. 사용 중지는 그 전부터 다음 요청에 바로 적용됩니다.

### 두 탭·두 사람이 같은 기록을 고칠 때
- 모든 고치기 화면(솔루션·파트너·고객·프로젝트·영업기회·BM·활동 기록과 그 후속 조치·니즈 줄·제안 대상, 사용자 줄)은 열 때의 "고침 표시"를 숨겨 두었다가 저장할 때 지금 기록과 비교합니다. 다르면 **저장하지 않고** 같은 화면을 쓴 내용 그대로 다시 보여 주며 이유를 알립니다.
  - "다른 곳에서 이 기록이 바뀌었습니다": "현재 내용 새 탭에서 열기"로 확인한 뒤, 내 내용이 맞으면 "그래도 내 내용으로 저장"을 누릅니다 (사용자 줄은 목록을 새로 고쳐 다시 고칩니다).
  - "잠시 후 다시 시도해 주세요"(503): 다른 사람이 저장하는 중이거나 백업이 쓰기 잠금을 쥐고 있어 저장 차례를 5초 기다리고도 오지 않은 것입니다(잠금을 풀지 못한 채 끝나는 경우 화면이 뜨기까지 약 10초까지 걸릴 수 있습니다). 만들기·고치기·지우기 어느 저장에서든 같고, 아무것도 저장되지 않았습니다 (제안 건 만들기의 방향 작업, 제안 대화의 메시지, 올리기 "다시 정리"의 고친 메모도 함께 저장되지 않으니 다시 보내면 정확히 한 번만 들어갑니다). 예외는 솔루션 자료를 여러 개 한꺼번에 올릴 때와 올리기 "다시 정리"입니다. 자료는 파일마다 따로 저장하므로, 저장된 파일이 하나도 없는 채로 막히면(이미 있는 자료나 큰 파일로 건너뛴 파일은 저장이 아닙니다) 503 이고, 앞에 저장된 파일이 있으면 503 대신 "저장하지 못한 파일" 안내가 뜨고 앞 파일은 저장돼 있습니다(그 파일만 다시 올리면 됩니다). 올리기 "다시 정리"의 고친 메모는 정리 작업과 함께 저장되지만, 그 앞에서 올린 파일의 읽기 상태(파일을 읽어 본 결과)는 따로 저장되므로 503 이어도 읽기 상태는 갱신돼 있을 수 있고 다음 시도가 다시 계산합니다. "뒤로 가기"로 돌아가 다시 저장하면 되고(만들기 폼도 같은 폼 표로 다시 낼 수 있습니다) 첨부했던 파일은 다시 골라야 합니다. 자주 나면 백업 시각과 겹치는지 봅니다.
  - "이 기록은 삭제되고 같은 번호로 새 기록이 만들어졌습니다": 다른 기록이라 저장할 수 없습니다. 쓴 내용은 화면에 남아 있으니 복사해 둡니다.
- 표시가 없는 저장(업그레이드 전에 열어 둔 화면, 브라우저가 아닌 클라이언트)은 지금까지처럼 한 번 받아 줍니다.
- **번호 재사용:** SQLite 는 `AUTOINCREMENT` 없이 만든 표에서 가장 큰 번호의 기록을 지우면 그 번호를 다음 새 기록에 다시 줍니다. 기존 표는 다시 만들지 않으므로, 대신 작은 표 `id_marks`("표마다 지금까지 쓴 가장 큰 번호")를 두고 새 기록의 번호를 항상 그보다 크게 정합니다(`app/idmarks.py`). 이 표는 새 버전을 처음 시작할 때 자동으로 만들어지고 기존 기록은 건드리지 않습니다. **한계:** 이 기능이 켜지기 전에 이미 지워진 번호는 알 방법이 없어, 그 번호는 다시 쓰일 수 있습니다(옛 북마크가 다른 기록을 열 수 있음). 그 경우에도 옛 화면에서의 저장은 고침 표시가 "다른 기록"으로 막습니다. 새로 만든 번호부터는 지운 뒤에도 다시 쓰이지 않고, 옛 주소는 "항목을 찾을 수 없습니다" 화면이 됩니다. 백업을 복원하면 `id_marks` 도 함께 복원됩니다.
- 같은 만들기 폼을 연타하거나 여러 번 보내도(같은 폼을 복제한 탭 포함) 기록이 하나만 만들어지고 처음 만든 기록으로 이동합니다 (폼마다 한 번 쓰는 표를 `form_tokens` 표에 1시간 두고, 매일 작업과 새로 쓸 때 지웁니다). 따로 열어 둔 두 탭은 서로 다른 표를 가지므로 같은 내용을 각각 저장하면 두 기록이 됩니다.
- 누구나 다른 사람의 기록을 고칠 수 있는 권한은 그대로입니다. 대신 상세 화면의 "기록 정보"에 **고친 사람·고친 날**이 나옵니다 (이 기능 이후에 고친 기록부터; 이력은 남기지 않습니다).

## 보안 참고

- (선택) Claude CLI가 사용자·프로젝트 설정 파일을 읽지 않게 하는 강화 설정입니다. 대상 PC에서 `claude --help` 에 `--restricted` 가 있는지 확인하고, 있을 때만 `config.toml` 에 `claude_cmd = ["claude", "--restricted"]` 를 적은 뒤 서버를 다시 시작하고 관리 → 시스템 → "AI 연결 확인" 이 여전히 "AI 연결 정상" 인지 확인하세요. 목록에 없거나 확인이 실패하면 되돌립니다.
- **웹 조사는 내부 파일을 볼 수 없습니다.** 웹을 검색하는 AI 작업은 파일을 읽는 도구가 없고, 빈 작업 폴더(`data_dir\research_work`)에서 실행됩니다. 지식 폴더를 읽는 작업은 웹 도구가 없습니다. 두 가지가 한 작업에 섞이지 않으므로 내부 자료가 웹으로 나가지 않습니다.
- 웹에서 가져온 글과 업로드한 자료, 메모, 대화는 **신뢰할 수 없는 글**로 취급합니다. 프롬프트에서 구분해 두고 그 안의 지시는 따르지 않게 합니다. AI가 만든 내용은 초안이며 출처를 직접 확인해야 합니다.
- **고객에게 보내기 전에 사람이 "고객용 PPT"를 처음부터 끝까지 읽어야 합니다.** 앱이 자동으로 옮기는 것은 **작성자에게 하는 말처럼 쓰인 줄**("확인 필요", "금액 기재 예정", "이 슬라이드 삭제" 같은 말투)과 **채우지 않은 자리표시**(`XX%`·`○○`·`OO`·`TBD`·`(수치 입력)` 같은 괄호 입력 표시)뿐이고, 내부 경로도 고객용 파일에서 뺍니다. **"초안"·"내부 검토용"·"작성자"·"팀장님"·"오타"·"폰트" 같은 내부 낱말은 걸러 내지 않습니다** (사용자 결정 2026-11-22: 고객 문장이 낱말 때문에 슬라이드에서 빠지면 안 됩니다). 말투 판정도 어림이라 메모를 놓칠 수 있습니다 (검토자의 표본에서 메모의 약 절반이 슬라이드에 남았습니다). 자동 옮기기는 안전망이지 검수가 아닙니다.
- `config.toml`, `certs\server.key`, `data` 폴더, 백업 폴더에는 비밀번호 해시와 내부 자료가 있습니다. 접근 권한을 제한하고 저장소에 올리지 않습니다.
- 인증서 신뢰 등록을 하면 그 PC는 이 인증서를 믿게 됩니다. `server.key` 가 유출되면 `make-cert --overwrite` 로 새로 만들고 다시 배포합니다.
